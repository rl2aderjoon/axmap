## 좌측 패널 순서

노드를 누르면 이 순서로 나온다. **핵심이 전체 코드보다 먼저다.**

1. **지금** — 그 파일을 누가 선점/수정 중인지 (감시 정보가 있을 때)
2. **전역 신호** — 이 파일이 쓰는 허브 채널
3. **요약** — LLM 한 문단, 스트리밍
4. **핵심** — LLM 이 고른 "반드시 볼 곳" 최대 3군데 + 왜 그런지
5. **코드** — 260줄 이하면 전체, 넘으면 구성 목록만

핵심 구간은 LLM 이 고르되 **줄 번호를 파일 길이로 잘라 검증**한다.
없는 줄을 가리키면 버린다.

| 조작 | 동작 |
|---|---|
| 클릭 | 그 노드를 선택 + **이해의 시작점**으로 지정 |

### 시각 채널을 의미별로 나눴다

3D 로 가면 원근감도 보통 크기·투명도로 표현하는데, 투명도는 이미
"시작점에서의 그래프 거리"(D8)가 쓰고 있다. **같은 채널을 두 의미가 다투면 둘 다 못 읽는다.**

| 채널 | 뜻 |
|---|---|
| 투명도 | 시작점에서의 **그래프 거리** (의미) |
| 크기 · 가림 | 카메라에서의 **화면 거리** (원근) |

안개(거리에 따른 흐림)는 최대 25% 만 건다. 더 걸면 "멀리 있는 것"과 "관련 없는 것"이 섞인다.
노드는 먼 것부터 그려 앞의 것이 뒤를 가리게 한다 — 가림이 원근의 두 번째 단서다.

## 로컬 LLM (선택)

없어도 전부 동작한다. 요약만 비활성화된다.

```bash
winget install --id Ollama.Ollama -e --scope user
ollama pull qwen2.5-coder:7b
node app/server.mjs <경로>            # 모델을 자동으로 찾아 미리 올린다
```

RTX 5060 Laptop(VRAM 8GB) 기준 **7~8B 가 적정**이다. 27B 는 VRAM 을 넘겨 RAM 으로 밀려난다.
은행 서버 얘기와 노트북 얘기는 분리해야 한다.
9.7B(`qwen3.5:9b`, 6.6GB)는 올라가긴 하지만 13% 가 CPU 로 밀리고, **품질도 더 낫지 않다**
— [아래 실측](#모델을-바꾸면-나아지는가--qwen359b-실측).

환경변수: `AXMAP_MODEL` (기본 `qwen2.5-coder:7b`), `OLLAMA_HOST`, `AXMAP_KEEP_ALIVE` (기본 `30m`).

### 실측 — RTX 5060 Laptop 8GB, qwen2.5-coder:7b (Q4_K_M), 100% GPU

| 파일 | 크기 | 모델에 넣은 것 | 첫 글자 | 전체 |
|---|---|---|---|---|
| `cmd_mux_node.py` | 130줄 | 전체 | 0.5초 | 2.5초 |
| `manual_drive_bridge.py` | 222줄 | 전체 | 0.7초 | 3.2초 |
| `escape_recovery.py` | 801줄 | 앞 130줄 + 구성 | 1.9초 | 5.5초 |
| 캐시 적중 | — | — | — | **4~32ms** |

생성 속도는 41 tok/s 로 일정하다. **변하는 것은 프롬프트 평가 시간**이므로
병목은 "얼마나 쓰느냐"가 아니라 **"얼마나 읽히느냐"**다.

### 그래서 이렇게 했다

- **스트리밍** — 다 끝날 때까지 빈 화면을 보여주면 실제 속도와 무관하게 느리게 느껴진다.
  첫 글자가 0.5~1.9초에 나오는 것이 전체가 5초에 끝나는 것보다 체감에 크게 작용한다.
- **모델을 미리 올린다** — 콜드 스타트는 **44초**다(4.7GB 적재, 실측).
  서버가 뜰 때 한 번 부르고 `keep_alive: 30m` 으로 붙잡는다. 기본값 5분이면
  잠깐 딴짓하고 돌아올 때마다 44초를 다시 기다린다.
- **파일 크기에 따라 넣는 것을 바꾼다** — 고정 줄 수로 자르면 정확도를 잃는다.
  222줄 파일을 160줄로 자르자 뒤쪽 62줄에 있던 채널 두 개(`/bbiyong/manual_drive_status`,
  `/tmp/orincar_drive.json`)를 통째로 놓쳤다. 260줄 이하는 전체를, 그 이상은
  앞 130줄 + 함수 목록을 준다. D6(적응형 노드)와 같은 원리다.
- **content hash 캐시** — `app/.cache/`. 파일이 안 바뀌면 다시 돌리지 않는다.

### prefetch

노드를 클릭하면 그 요약이 끝난 뒤 **깊이 1~3 을 미리 만든다.** 깊이 순서대로 하므로
가장 클릭할 만한 것부터 준비된다. 다른 노드를 선택하면 즉시 취소한다.

e101 의 `cmd_mux_node.py` 기준 깊이 1~3 은 **40개**(7 + 15 + 18)라
전부 준비되는 데 약 2분 걸린다. 상단에 `주변 요약 4/40` 으로 진행이 보인다.

### 검증 가능한 출력

LLM 이 말한 채널 이름은 **파일에 그 문자열이 실제로 있는지 대조해서** `verified` 를 붙인다.
작은 모델을 쓸 수 있는 이유가 이것이다 — 환각이 기계적으로 걸러진다.

다만 정적 파싱과의 역할 분담은 처음 생각보다 미묘하다.
따옴표 안의 `/경로` 를 전부 긁는 정규식은 파라미터 기본값도 잡으므로 **연결 자체는 놓치지 않는다.**
LLM 이 더해주는 것은 **방향**(발행인지 구독인지)과 **문서에만 적힌 흐름**이다.
데이터 흐름을 이해하려면 방향이 있어야 하므로 여전히 필요하지만,
"정적 파싱은 못 보고 LLM 만 본다" 는 과장이다.

### 출력 길이는 문법으로 묶는다

`format:'json'` 은 문법만 강제하고 **길이는 강제하지 못한다.** 채널 10개짜리 파일에
같은 채널을 방향만 바꿔가며 97줄 반복하다 `num_predict` 에 잘려 죽는 일이
40파일 중 1~2건씩 났다. 잘린 JSON 은 파싱에 실패하고 **그 파일의 엣지가 통째로 사라진다.**
하필 채널이 가장 많은 파일에서 터지므로 손실이 가장 큰 곳에서 조용히 진다.

temperature 를 0.4 까지 올려도 재현된다 — 확률로는 못 막는다.
`format` 에 JSON Schema 를 주고 `maxItems` 를 걸면 문법이 배열을 닫도록 강제하므로
이 실패가 원천적으로 사라진다. 최악 비용도 34초에서 8초로 묶인다.
`verified` 가 환각을 문자열 대조로 막는 것과 같은 수법을 길이에 적용한 것이다.

문법이 배열 길이는 묶어도 **같은 채널을 두 번 쓰는 것은 막지 못하므로** 중복은 따로 제거한다.
제거하지 않으면 화면에 같은 선을 겹쳐 그리고, 세는 쪽에서는 개수를 부풀린다.

### 모델을 바꾸면 나아지는가 — qwen3.5:9b 실측

**결론: 안 나아진다.** `qwen2.5-coder:7b` 를 유지한다. (2026-08-16 측정)

`app/eval/edges.mjs` 로 40파일 × 5회를 설정별로 재고 정확 순열검정(252조합 전수)으로 판정했다.

| 설정 | 부가가치 | 커버리지 | 정밀도 | 방향오류율 | ms중앙 |
|---|---|---|---|---|---|
| **qwen2.5-coder:7b** (temp 0.1) | **109.0±5.8** | **82.8%** | 72.7% | **3.00%** | 1977 |
| qwen3.5:9b (temp 1.0 기본) | 86.2±2.2 | 76.1% | **90.0%** | 5.50% | 1774 |
| qwen3.5:9b (temp 0.1 통제) | 83.4±1.7 | 75.6% | 83.6% | 4.08% | 1645 |

부가가치 p=0.008 — 252조합에서 나올 수 있는 최솟값이고 두 집단의 범위가 겹치지 않는다.
속도는 차이 없다(p=0.238~0.365).

**왜 더 큰 모델이 지는가**

- **3.5 는 사고를 켤 수 없다.** 문법을 걸면 첫 토큰부터 JSON 만 허용되어 사고할 자리가 없고
  답이 통째로 `thinking` 필드로 가서 `response` 가 빈 문자열이 된다. 문법을 풀면 사고가
  끝나지 않는다 — 컨텍스트 16384 · 예산 8192 로도 31,540자를 쓰고 287초 뒤 답 없이 잘렸다.
  둘 사이에 안전지대가 없다. `think:false` 는 3.5 를 불리하게 만든 조치가 아니라
  **답이 나오는 유일한 설정**이다.
- **온도 탓이 아니다.** 0.1 로 맞추자 오히려 내려갔다(86.2 → 83.4). 다만 방향오류율은
  5.50% → 4.08% 로 내려가 두 모델이 대등해진다(충돌 p=0.556).
- **애초에 동급이 아니다.** `qwen3.5:9b` 는 9.7B 중 **27블록이 vision tower** 다.
  파이썬 채널 문자열을 읽는 데 한 글자도 안 쓰인다. `qwen2.5-coder:7b` 는 7.6B 전부가
  코드 사전학습이다.
- **`verified` 필터가 정밀도의 값을 깎는다.** 3.5 는 확실할 때만 말한다(정밀도 90% vs 72.7%).
  좋은 성질이지만 여기서는 틀린 주장의 비용이 0이라, 신중함이 커버리지 손실로만 나타난다.

일반 벤치마크에서 3.5 가 앞선다는 것과 모순되지 않는다. 여기서 재는 것은 추론력이 아니라
"ROS 파이썬에서 토픽 문자열과 pub/sub 방향 뽑기" 이고, 3.5 의 두 주무기가
각각 봉쇄되거나 무가치화된다.

**미검증 변수 하나** — 프롬프트는 소형 모델에 맞춰 코드를 먼저 주고 지시를 뒤에 붙인 구조다
(`llm.mjs` 의 `summaryPrompt` 주석). 3.5 에 맞춰 다시 쓰면 결과가 달라질 수 있다.

### 모델 비교 하네스

```bash
node app/eval/edges.mjs <대상저장소> [--files N]        # 기본 20파일
AXMAP_MODEL=<다른모델> node app/eval/edges.mjs <같은저장소>
node app/eval/edges.mjs --compare
```

정답 세트가 없어도 판정이 된다. 서로 독립된 기준이 이미 두 개 있기 때문이다 —
`verified`(문자열 대조)와 `channelsOf`(정적 추출). 재는 것은 "모델이 똑똑한가"가 아니라
**정적 파싱 위에 모델이 무엇을 더 얹는가**다. 대상은 채널이 실제로 배선된 저장소여야 한다.

읽는 순서는 **`형식위반`이 0인지 먼저**다. 0이 아니면 품질이 아니라 배관 문제를 보고 있는 것이다.

그리고 **확률적 모델은 1회 측정이 무의미하다.** 실제로 20파일 × 2회에서는 3.5 가 21%
앞서는 것처럼 보였고, 40파일 × 5회로 늘리자 부호가 반대로 나왔다.

### 터미널로 실제로 되는 것 / 안 되는 것

**된다.** 대상 저장소를 작업 디렉터리로 PowerShell 이 진짜로 돈다. 확인한 것:

```
$ git status --short          진짜 변경 목록 (빨간 D 까지 색으로)
$ python -c "print('한글')"    한글 정상 출력
$ Get-ChildItem ros2_ws/src   실제 디렉터리 목록
$ Get-Location                C:\...\BE_robot
```

ANSI 색은 직접 파싱해 그린다. 진행 막대(`\r`)도 줄을 다시 그리는 방식으로 처리한다.
윈도우 콘솔이 기본 CP949 라 한글이 깨지므로 `[Console]::OutputEncoding` 과
`PYTHONIOENCODING` 을 UTF-8 로 잡아 넣는다.

**안 된다.** `spawn` 이지 pty 가 아니다.

- 대화형 TUI (`vim`, `htop`, `less`) — 화면 제어 시퀀스를 흉내내지 않는다
- 입력이 필요한 명령 (`ssh` 비밀번호, `git rebase -i`) — stdin 이 연결돼 있지 않다
- `Ctrl+C` 로 중단 — 브라우저 탭을 닫으면 프로세스는 죽는다
- 명령 사이에 상태가 남지 않는다 (`cd` 후 다음 명령은 다시 원래 위치)

필요해지면 `node-pty` + `xterm.js` 로 교체하면 되고 화면 구조는 그대로다.

### 그 밖의 한계
- **함수 목록은 정규식이다.** `def`/`class` 를 줄 단위로 찾는다. 데코레이터·중첩·멀티라인
  시그니처에서 틀린다. 화면에 "정규식 추출"이라고 적어 확신을 속이지 않는다.
- **백업 디렉터리를 자동 제외한다.** `backup|snapshot|.bak|-old|archive` 가 경로에 있으면 건너뛴다.
  e101 의 `orin-live-backup/` 처럼 같은 파일이 수십 벌 있으면 그래프가 복제본으로 뒤덮인다.
- **`.gitignore` 가 "선언 밖 수정"으로 잡힌다.** `axmap init` 자신이 고치기 때문이다. 오탐이다.

## 왜 이 스택인가

- **웹 UI** — 그래프도 터미널도 웹 라이브러리가 압도적이다. 네이티브로 가면 둘 다 직접 만들어야 한다.
- **Electron 셸** — 배포는 `desktop/` 이 맡는다 (D16). 이 웹 UI 를 그대로 싣기 때문에
  프로토타입에서 버려지는 것이 없다. 브라우저로 여는 길도 그대로 산다 —
  `node app/server.mjs` 는 죽지 않는다.
- **번들러 없음** — 브라우저 ES 모듈만 쓴다. 빌드 단계가 없어 저장하고 새로고침하면 끝이다.
- **코어 외부 의존성 0** — 힘 기반 그래프도 직접 그린다. 이유는 **폐쇄망에서 npm 이 안 되기
  때문이 아니다.** 앱은 번들되어 나가므로 설치본에는 의존성이 몇 개든 상관없다. 진짜 이유는 둘이다.
  - **감사 표면.** 이 도구는 누가 어떤 코드를 커밋할 수 있는지를 판정하고 git 자격증명을 들고
    실행된다. `src/protocol.mjs` 가 도는 프로세스에 검토 안 된 코드가 같이 올라가면
    도구가 지키려는 성질을 도구 자신이 깬다.
  - **승인 절차.** 폐쇄망 조직은 서드파티 패키지마다 검토·화이트리스트를 요구한다.
    막히는 것은 네트워크가 아니라 결재다.

  여기에 더해, 시각 인코딩이 전부 이 프로젝트 고유라 범용 라이브러리를 써도 대부분을 덮어써야 한다.
  의존성을 쓰는 자리는 `desktop/` 이고, 경계는 **import 방향 하나**로 지킨다 —
  `desktop/` → 코어는 되고 반대는 안 된다.
