# 코퍼스가 왜 필요한가 — 팀에게

한 줄로: **우리 도구가 쓰는 판단 기준을 우리가 눈으로 골랐기 때문이다.**

```
https://i15e101.p.ssafy.io/ssot/      지금 돌아가는 것 (인증 없음)
```

---

## 1. 문제 — 우리 숫자에 근거가 없다

axMap 코드에는 이런 상수들이 박혀 있다.

| 상수 | 뜻 | 근거 |
|---|---|---|
| `splitOver 300` | 300줄 넘으면 큰 파일 | 없음. 눈으로 골랐다 |
| `hubCap 6` | 이웃 6개 넘으면 허브 | 없음 |
| `MIN_SUPPORT 3` | 3번 함께 바뀌면 관계 | 없음 |
| `REL_FLOOR 0.25` | 기능 범위 문턱 | 없음 |

`docs/DECISIONS.md` 의 열린 질문 Q2·Q5·Q6 에 **"눈으로 고른 값"** 이라고
그대로 적혀 있다. 부끄러워서가 아니라, 저장소 하나로는 정할 수가 없어서다.

우리가 화면에서 "이 파일은 큽니다" 라고 말할 때, 그 판단의 근거는
**누군가 300이라고 쳤다** 는 것뿐이다.

## 2. 코퍼스가 하는 일 — 상수를 분포로 바꾼다

수천 개 공개 저장소를 돌면서 "실제로 사람들은 어떻게 쓰나" 를 센다.

```
(X)  이 파일은 430줄입니다. 큽니다.
(O)  커밋 1,500~6,000인 Python 저장소 34개에서 이 위치의 파일은
     중앙값 118줄입니다. 당신 것은 430줄, 상위 8% 입니다.
```

앞은 우리 의견이고 뒤는 관측이다. **차이가 크다.**

## 3. 🔴 그런데 "인기 있는 걸 따라해라" 가 아니다

여기가 가장 오해받는 지점이라 따로 적는다.

별 많은 저장소를 긁어서 "이렇게 하세요" 라고 하면 그건 **생존 편향을 규범으로
만드는 것**이다. 유명한 게 잘 만들어서 유명한 게 아닐 수 있다.

그래서 인기가 아니라 **결과**를 센다 — *"그 파일이 나중에 얼마나 고쳐졌나"*
(커밋 제목에 fix/버그/수정 이 들어간 커밋이 그 파일을 건드린 비율).

그리고 실제로 측정됐다. 저장소 7,107개 기준:

| 별 | 평균 재수정률 |
|---|---|
| 0~2,000 | 0.081 |
| 2,000~6,000 | 0.150 |
| 6,000~20,000 | 0.103 |
| 20,000~ | 0.149 |

**단조 관계가 없다.** 별과 코드 품질은 상관이 없다는 것이,
이제 우리 주장이 아니라 우리 데이터다.

## 4. 이미 나온 것

**파일 길이는 진짜 신호다.** 커밋 수를 고정해도 살아남는다 —
"긴 파일은 원래 자주 고치니까" 라는 반박을 막기 위해 통제한 것이다.

| 커밋 25~60회인 파일 | 0~50줄 | 100~200 | 400~800 | 1600+ |
|---|---|---|---|---|
| 재수정률 | 0.115 | 0.156 | 0.191 | **0.234** |

그리고 **14개 언어 전부** 같은 방향이되 크기가 다르다.

```
swift 1.89배 · typescript 1.71 · rust 1.67 · python 1.65
     …
kotlin 1.33 · php 1.31
```

**결합은 신호가 아니었다.** 커밋 수를 고정하면 사라진다(뒤집힌 U).
우리 제품의 중심 축이라 불편한 결과지만, 그래서 더 알아야 했다.

**사람 수는 신호다.** 여러 명이 만지는 파일이 더 자주 고쳐진다
(1~2명 0.153 → 17명+ 0.198). 이건 조율 비용이고, axMap 이 겨냥하는 자리다.

## 5. 🔴 우리가 어디를 못 보는지도 알게 됐다

이게 코퍼스 없이는 절대 못 얻었을 것이다.

| 잘 봄 | | 거의 못 봄 | |
|---|---|---|---|
| go | 99% | c# | **4%** |
| typescript | 98% | swift | **4%** |
| python | 97% | ruby | **5%** |
| javascript | 97% | kotlin | 7% |
| java | 94% | php·c·c++·rust·scala | 8~12% |

우리 파서가 읽는 언어는 다섯 개뿐이었다.

이걸 안 쟀다면 우리 도구는 C# 팀에게
**"파일당 결합 0.03, 훌륭하게 분리돼 있군요"** 라고 말했을 것이다.
새빨간 거짓말이다. 우리가 `.cs` 를 안 읽을 뿐이다.

이 표 때문에 지금 파서 확장 작업이 진행 중이다. **저장소를 더 모아도
소용이 없고 파서를 늘려야 한다** 는 것도 코퍼스가 알려준 것이다.

## 6. 비용

**추가 비용이 없다.** 지난 프로젝트가 끝나고 놀고 있는 AWS 에서 돈다.
`nice -n 15` 로 낮춰서 젠킨스·게릿을 밀어내지 않는다.
하룻밤(12시간)에 7,107개를 모았고 디스크 1GB, 실패 1건이었다.

공개 저장소의 **통계만** 저장한다. 남의 소스는 재고 나서 즉시 지운다.

## 7. 이게 없으면 못 하는 것

우리 제품이 답하려는 공포가 셋인데, 셋째는 **한 저장소 안에서 답이 안 나온다.**

| | 질문 | 시점 |
|---|---|---|
| F1 | 이해 못 하는 코드가 쌓인다 | 작업 전 |
| F2 | AI 가 뭘 망가뜨렸는지 모른다 | 작업 후 |
| **F3** | **내가 잘 하고 있는지 모른다** | 계속 |

F1·F2 는 *"지금 무슨 일이 일어났나"* 를 묻고, F3 는 **"이게 정상인가"** 를 묻는다.
"정상"은 비교 대상이 있어야 존재한다. 그게 코퍼스다.

## 자주 나오는 반문

**"그냥 린터 규칙 쓰면 되지 않나?"**
린터는 누군가 정한 규칙이다. 그 규칙의 근거를 물으면 대개 관습이다.
우리는 **결과와 이어진** 숫자를 낸다 — "이렇게 하면 나중에 덜 고친다".
그리고 관계가 없으면 **지침을 내지 않는다.**

**"저장소마다 다르지 않나?"**
그래서 `(언어, 규모)` 칸 안에서만 집계한다. 칸을 넘어 합치지 않는다.
커밋 200개짜리와 5만 개짜리를 같은 분포에 넣으면 누구에게도 안 맞는다.

**"표본이 적으면 틀린 말 하는 거 아닌가?"**
저장소 15개·파일 300개 미만이면 **답을 안 한다.** `usable: false` 와 이유를 낸다.
한 번 거짓말한 지침은 그 다음부터 전부 무시당하기 때문이다.

**"상관이지 인과 아닌가?"**
맞다. *"긴 파일이 버그를 만든다"* 가 아니라 *"긴 파일이 더 자주 고쳐졌다"* 다.
그래서 화면에 **구간표 전체**를 함께 낸다. 사람이 직접 보고 판단하게 한다.

## 아직 안 된 것 (숨기지 않는다)

- **떼어놓고 검증(held-out)** 하는 고리가 없다. 기준의 예측이 맞았는지
  채점해본 적이 없다. 이게 있어야 "관찰"이 "검증된 지침"이 된다.

  (그래서 저장소마다 fix 비율을 함께 기록해 걸러낼 수 있게 했다).
- 문서(글) 품질 축은 재료가 없다. 지금은 코드만 본다.
