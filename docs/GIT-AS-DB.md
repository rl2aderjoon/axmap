# git 을 데이터베이스처럼 쓰기 — 무엇이 공짜고 무엇이 아닌가

이 저장소는 이미 **git 안에서 도는 데이터베이스 비슷한 것**을 쓰고 있다.
선점(누가 어느 파일을 잡았나) · 쪽지(에이전트끼리 주고받는 글) · 사람 정보
(어디까지 읽었나) 셋이 전부 git 브랜치에 산다.

이 문서는 그것을 **설계로서 다시 본다.** 지금 구조가 무엇을 잘하고 무엇을 못하는지,
그리고 못하는 것들이 **어제 실제로 어떤 사고로 나타났는지**를 이어 붙인다.

> 🔴 **읽는 사람은 데이터베이스를 안 배운 사람이다.**
> 그래서 "어떤 방식이 좋은가" 보다 **"이 결정을 내리려면 내가 무엇을 알아야 하나"**
> 를 먼저 쓴다. 용어는 처음 나올 때 그 자리에서 푼다. 마지막에 용어표가 있다.

## 1. 먼저 — "데이터베이스" 가 하는 일은 다섯 가지다

DB 를 배운 적 없어도 이 다섯만 알면 이 문서의 모든 결정을 따라올 수 있다.

| # | 하는 일 | 무슨 뜻인가 | git 은? |
|---|---|---|---|
| 1 | **담아두기** | 프로그램을 껐다 켜도 남아 있다 | ✅ 공짜 |
| 2 | **골라내기** (질의) | *"내 앞으로 온 것 중 안 읽은 것만"* 을 물어보면 답이 온다 | ❌ 없음 |
| 3 | **빨리 찾기** (색인) | 10만 건에서 하나를 꺼낼 때 10만 건을 다 안 훑는다 | ❌ 없음 |
| 4 | **동시에 쓰기** | 둘이 같이 써도 한쪽이 다른 쪽을 조용히 지우지 않는다 | ✅ 반쯤 공짜 |
| 5 | **통째로 되거나 안 되거나** (원자성) | 변경이 반쯤 된 상태가 존재하지 않는다 | ✅ 공짜 |

**원자성**(atomicity — 하나의 변경이 통째로 되거나 통째로 안 되거나, 반쯤 된 상태가
없는 것)이 왜 중요한지 예로 보면: 선점 장부에서 "A 가 파일 셋을 잡았다" 를 쓰는
도중에 프로그램이 죽었다고 하자. 파일 둘만 적힌 상태가 남으면 세 번째 파일은
아무도 안 잡은 것으로 보인다. 그 자리에 남이 들어온다. **락이 아니게 된다.**

git 은 커밋 단위로 이것을 준다. 커밋은 만들어지거나 안 만들어지거나 둘 중 하나다.

> 이 문서의 나머지는 전부 **2·3 이 없다는 것**과 **4 가 어디까지 공짜인가**에 대한
> 이야기다.

## 2. 지금 실제로 무엇이 있나 — 실측

**고아 브랜치**(orphan branch — 코드 이력과 아무 관계없이 따로 도는 브랜치. 코드
브랜치와 조상을 하나도 공유하지 않아서, 여기에 커밋을 아무리 쌓아도 코드에는
안 섞인다) 다섯 개가 데이터를 담고 있다.

측정한 곳: 팀 저장소 `S15P21E201`, 2026-09-08 기준.

| 브랜치 | 담는 것 | 지금 파일 수 | 쌓인 커밋 | 디스크 |
|---|---|---|---|---|
| `axmap/claims` | 누가 어느 파일을 잡고 있나 | **4** | **1,256** | 226 KB |
| `axmap/bus` | 쪽지 | **353** | 356 | 87 KB |
| `axmap/users` | 사람별 상태 (어디까지 읽었나) | **6** | 31 | 4.6 KB |
| `axmap/votes` | 합의 표 | **30** | 38 | 7.1 KB |
| `axmap/checkpoints` | 감사용 스냅샷 | **1** | 28 | 6.2 KB |

**세 번째와 네 번째 칸의 차이를 보라.** 선점은 지금 살아 있는 것이 파일 4개인데
그것을 만드느라 커밋 1,256개가 쌓였다. 쪽지는 파일 353개에 커밋 356개 —
거의 1:1 이다.

이 차이가 곧 **성질의 차이**다.

| | 선점 | 쪽지 | 사람 정보 |
|---|---|---|---|
| 수명 | 30~45분 뒤 만료 | 영원 | 사람이 있는 동안 |
| 쓰는 빈도 | 매우 잦다 (하루 281회) | 잦다 (하루 108건) | 잦다 (쪽지 볼 때마다) |
| 같은 자리를 덮어쓰나 | **덮어쓴다** | 절대 안 덮는다 | **덮어쓴다** |
| 지워도 되나 | 지워야 한다 | 안 된다 | 사람이 나가면 |
| 한 건의 임자 | (사람, 창) 하나 | 보낸 사람 하나 | 사람 하나 |

**셋을 한 방식으로 다루면 안 된다는 것이 이 표의 요지다.**

### 실제 파일 이름

```
axmap/claims  claims/janghyojoon@8c0afdd9.json      ← 사람 + 창(세션) 하나에 파일 하나
axmap/bus     messages/20260907T153656Z-janghyojoon-투표-부탁-mr-339-먼저.md
axmap/users   users/rleaderjoon@gmail.com.json      ← 사람 하나에 파일 하나
axmap/votes   votes/back/dev/jaehyeon-31cd6946.json ← 브랜치/사람-커밋
```

선점 파일 하나의 내용:

```json
{
  "agent": "janghyojoon",
  "task": "S15P21E201-735",
  "intent": "앱 행동 이벤트 수용 계약",
  "session": "88981cee-a809-432d-94de-70c3b88ac265",
  "since": "2026-09-07T15:49:27.782Z",
  "ttlMs": 1800000,
  "paths": ["backend/src/.../AuthController.java", "..."]
}
```

사람 정보 파일 하나의 내용 — **이게 전부다.**

```json
{
  "name": "janghyojoon",
  "aliases": [],
  "seen": "20260907T084945Z-yeaseung-lee-결정-요청-메뉴판-번역-..."
}
```

`seen` 한 칸이 *"이 쪽지까지는 읽었다"* 를 뜻한다. 이 한 칸이 어제 사고 두 건의
원인이다 (4.2 · 4.3).

## 3. git 이 공짜로 주는 것

새로 만들 필요가 없는 것들이다. 데이터베이스를 직접 짜면 이게 전부 일이 된다.

### 3.1 통째로 되거나 안 되거나

커밋은 원자적이다. 파일 열 개를 한 커밋에 담으면 열 개가 다 들어가거나 하나도
안 들어간다. **반쯤 쓰인 장부는 존재할 수 없다.**

> ⚠️ 단, **파일 하나를 쓰는 것 자체**는 git 이 아니라 운영체제의 일이라 공짜가 아니다.
> 이 저장소는 그래서 임시 파일에 다 쓴 뒤 이름을 바꾸는 방식을 쓴다
> (`bin/axmap.mjs` 의 `writeFileAtomic`). 같은 폴더 안에서의 이름 바꾸기는
> 원자적이라, 보는 쪽은 옛 파일이나 새 파일만 보고 **반쯤 쓰인 상태는 못 본다.**

### 3.2 이력이 통째로 남는다

*"이 선점은 언제 누가 왜 잡았나"* 를 나중에 물을 수 있다. 보통의 데이터베이스는
값을 덮어쓰면 **옛 값이 사라진다.** 그것을 남기려면 감사 테이블을 따로 만들고
그 테이블이 커지는 것을 또 관리해야 한다. git 은 안 지우는 것이 기본이다.

실측: 선점 브랜치의 커밋 1,256개가 곧 지난 2주 동안 이 팀이 무엇을 언제 잡았다
놓았는지의 완전한 기록이다.

```
751 claim    (잡았다)
481 release  (놓았다)
 23 renew    (시간 연장)
```

### 3.3 누가 썼는지가 위조하기 어렵게 붙는다

커밋에는 **author**(글을 쓴 사람)와 **committer**(그것을 실제로 기록한 사람)가
따로 붙는다. 이 저장소의 합의 장치는 이걸 실제로 쓴다 — 표 파일 안에 적힌
`voter` 를 믿지 않고, **그 파일을 추가한 커밋의 committer** 를 본다
(`governance/gate.mjs`). 파일 내용은 누구나 아무렇게나 적을 수 있지만 커밋의
신원은 git 이 붙인다.

### 3.4 되돌릴 수 있다

잘못 썼으면 이전 커밋으로 되돌리면 끝이다. 이 문서 8절의 "안전하게 옮기는 절차"
가 성립하는 이유가 이것이다 — **되돌릴 수 있으면 위험한 작업을 해볼 수 있다.**

### 3.5 나르는 것·권한이 이미 있다

다른 PC 로 보내는 것(`push`/`fetch`), 누가 쓸 수 있는지(GitLab 권한), 인증
(SSH 키·토큰)이 전부 이미 있다. **새 서버도 새 계정도 필요 없다.**

이것이 실제로 얼마나 큰지: 이 팀은 6명이 각자 다른 PC 에서 일하고, 그중 한
PC 에는 지금 작업 폴더가 14개 열려 있다 (실측 — 본체 1 + 곁폴더 13). 이걸 데이터베이스 서버로 하려면
서버를 세우고 주소를 열고 계정을 나눠주고 방화벽을 뚫어야 한다.

### 3.6 🔴 둘이 동시에 쓰면 한쪽이 거부된다

이게 제일 크다. 5절 전체가 이것이다.

## 4. git 이 안 주는 것 — 어제 터진 여섯 건이 그것이다

여기가 이 문서의 핵심이다. **없는 기능을 나열하는 것이 아니라, 그것이 없어서
어제 실제로 무슨 일이 났는지**를 붙인다.

### 4.0 사고 여섯 건 한눈에

| # | 무슨 일이 났나 | 데이터베이스에서 부르는 이름 |
|---|---|---|
| 1 | 안 읽은 쪽지 수가 25→22→5→16 으로 바뀌었다 | **키를 무엇으로 잡을 것인가** |
| 2 | 목록을 한 번 보면 앞의 것이 전부 읽음이 됐다 | **상태를 한 칸으로 압축했다** |
| 3 | 선점을 잡았는데 검사기가 못 읽었다 | **읽는 쪽과 쓰는 쪽의 규격이 어긋났다** |
| 4 | 다른 폴더에서 잡으면 장부에 안 남았다 | **어디를 봐야 하는지가 갈렸다** |
| 5 | 커밋을 하나 더 올리면 앞의 표가 무효가 됐다 | **의도된 제약** — 결함이 아니다 |
| 6 | `git fetch` 를 안 하면 틀린 답을 냈다 | **언제가 최신인가** |

---

### 4.1 없는 것 · **골라내기** — 조건으로 물어볼 수 없다

보통의 데이터베이스라면 이렇게 묻는다.

```sql
SELECT * FROM messages WHERE to = '나' AND id > (내가 마지막으로 읽은 것)
```

git 에는 이런 물음이 없다. git 이 아는 것은 *"이 커밋의 파일 목록"* 과
*"이 파일의 내용"* 뿐이다. 그래서 **353개 파일을 전부 열어서 앞머리를 읽고,
프로그램이 직접 걸러낸다.**

실제로 그렇게 하고 있다 (`tools/bus.mjs` 의 `readAll` → `list`).

**지금은 이게 문제가 아니다.** 실측: 353건 전문을 다 읽는 데 **0.052초**.
사람이 못 느낀다. 언제부터 문제가 되는지는 7절에서 잰다.

### 4.2 🔴 사고 1 · **같은 값이 두 자리에 서로 다른 이름표로 저장돼 있었다**

*"어디까지 읽었나"* 를 **두 곳**에 적고 있다.

| 자리 | 무엇으로 사람을 가르나 | 예 |
|---|---|---|
| 공유 브랜치 `axmap/users` | **이메일** | `users/rleaderjoon@gmail.com.json` |
| 그 PC 안의 파일 | **지금 뜬 도구 이름** | `{"janghyojoon": "...", "codex": "..."}` |

읽을 때는 **둘 중 더 나아간 쪽**을 쓴다 (`tools/bus.mjs` 의 `readSeen`).

```js
return fromBranch > legacy ? fromBranch : legacy
```

그래서 **"지금 어떤 이름으로 도구가 떴는가" 에 따라 안 읽은 개수가 바뀐다.**
같은 사람, 같은 순간, 같은 쪽지함인데 25 → 22 → 5 → 16 이 됐다.

> 🔴 **결과가 나쁜 쪽으로 났다.** 개수가 줄어드는 방향으로 틀리면 사람은
> "읽을 게 없구나" 하고 넘어간다. 운영 장애 보고 쪽지가 한 번도 "안 읽음" 으로
> 안 뜨고 그대로 묻혔다.

**데이터베이스 용어로는 두 가지가 겹쳤다.**

1. **키**(key — 한 줄을 다른 줄과 구별하는 이름표)를 **불안정한 값**으로 잡았다.
   이메일은 사람이 안 바꾸지만 도구 이름은 창을 열 때마다 바뀐다.
2. **같은 사실을 두 곳에 적었다**(중복 저장). 두 곳에 적으면 **반드시 갈린다.**
   갈렸을 때 어느 쪽이 맞는지 정할 방법이 없기 때문에 "더 나아간 쪽" 같은
   임시방편이 들어가고, 그 임시방편이 곧 버그가 된다.

**얼마나 나쁜지 실측했다.** 팀 저장소 전체 이력에서 — **사람은 6명이다.**

```
서로 다른 이메일    9개   ← 사람 6명 + 봇 1 + 테스트 1 + GitLab 자동 주소 1
서로 다른 이름     13개
선점을 잡은 이름   42개
```

한 사람이 `yeaseung-lee` · `yeaseung lee` · `이예승` 셋으로 커밋한다.
거기에 그 사람이 띄운 AI 도구 이름(`codex-jinmiri` · `jaehyeon-2` · `claude-opus-session`)
까지 붙어서 **6명이 42개의 이름표**를 갖는다.

> **이름은 갈리고 이메일은 거의 안 갈린다.** 표기는 바꿔도 이메일은 안 바꾸기 때문이다.
>
> ⚠️ **"거의" 다.** 한 사람이 GitLab 이 자동으로 붙이는 주소
> (`30831-kojh0124@users.noreply.lab.ssafy.com`)로도 4번 커밋했다. 웹 화면에서
> 편집하면 그 주소가 붙는다. **이메일도 완벽한 키는 아니다** — 다만 이름 42개와
> 이메일 9개(실질 7개)는 차원이 다르다. 완벽한 키가 없으면 **덜 갈리는 것**을 쓰고,
> 갈린 것을 이어주는 자리(`aliases`)를 둔다. 지금 사람 정보 파일에 그 칸이 이미 있다.
> 그리고 이 저장소는 **이미 한쪽에서 옳게 하고 있었다** — 투표권자 명단
> (`governance/policy.json`)은 처음부터 이메일로 사람을 가른다.
> 쪽지함과 선점만 이름을 썼다. **한 저장소가 주소 체계를 두 개 갖고 있었다.**

### 4.3 🔴 사고 2 · **눈금이 "어디까지" 하나뿐이다**

사람 정보 파일에 읽음 표시가 **한 칸**이다.

```json
{ "seen": "20260907T084945Z-yeaseung-lee-결정-요청-..." }
```

*"이 쪽지 id 보다 작으면 전부 읽음"* 이라는 뜻이다. 이런 방식을
**하이 워터 마크**(high-water mark — 물이 가장 높이 올라왔던 자국 하나만 남기는
방식. 그 아래는 전부 지나간 것으로 친다)라고 한다.

쪽지 id 가 시각으로 시작하므로 **글자순 정렬 = 시간순 정렬**이라 이 방식이 성립한다.
값 하나면 되니까 싸다.

**대신 이것을 못 한다.**

- 목록을 한 번 보면 그 안의 **앞의 것이 전부 읽음이 된다.** 다섯 개가 떴는데
  세 번째만 읽고 싶어도 방법이 없다
- **안 읽음으로 되돌리기**(나중에 다시 볼 것으로 표시)가 불가능하다
- 중간 하나를 건너뛰면 그건 영영 안 뜬다

실제로 이 함정을 이미 한 번 밟았다. 화면에 3건만 그리는 알림이 **전체를 읽음으로
찍어서**, 4번째부터는 화면에 뜬 적도 없이 읽음이 됐다. 지금은 *"그린 쪽이,
그린 것만 찍는다"* 라는 규칙(`--no-mark`)으로 막아뒀다 — 규칙으로 막았다는 것은
**구조가 그것을 막아주지 않는다**는 뜻이다.

**이건 설계 선택이지 버그가 아니다.** 다만 지금 선택이 맞는지 다시 볼 값이다 (9절).

### 4.4 없는 것 · **스키마를 한 번에 갈아끼우기**

**스키마**(schema — 데이터가 어떤 모양이어야 하는지의 약속. "선점 파일 이름은
`<이름>.json` 이다" 같은 것)를 바꾸면, 보통의 데이터베이스는 서버 한 대에서
한 번 바꾸면 끝이다. **git 은 그럴 데가 없다.** 모두가 각자 프로그램을 갖고 있다.

### 4.5 🔴 사고 3 · **잡았는데 검사기가 못 읽었다**

선점 파일 이름 규칙이 도중에 바뀌었다.

| | 파일 이름 | 뜻 |
|---|---|---|
| 옛 규칙 | `claims/janghyojoon.json` | 한 사람 = 한 레코드 |
| 새 규칙 | `claims/janghyojoon@8c0afdd9.json` | **(사람, 창) 짝** = 한 레코드 |

바꾼 이유는 옳다 — 같은 사람이 창을 둘 띄우면 서로 다른 작업을 하는데, 이름만으로
가르면 **한쪽의 반납이 다른 쪽이 잡은 것까지 풀어버린다.**

문제는 **읽는 쪽이 옛 규칙을 쓰고 있었다는 것**이다. 커밋 훅(commit hook —
커밋할 때 자동으로 도는 검사 프로그램)이 부르는 axMap 이 다른 자리에 있는
낡은 사본이었다. 실측으로 확인한 것:

```
훅이 1순위로 부르는 것   npm 캐시의 axmap-cli 1.2.0        ← 새 규칙
훅의 되돌아갈 자리       <저장소>/ci/axmap/bin/axmap.mjs   ← 2026-08-26 사본, 옛 규칙
```

> 2026-10-29 에 그 되돌아갈 자리를 훅에서 뺐다 — 8.1 의 3번, [D31](DECISIONS.md).

그리고 **지금 장부에 두 규칙의 파일이 나란히 들어 있다.**

```
claims/janghyojoon.json            ← 옛 규칙으로 쓰인 것
claims/janghyojoon@8c0afdd9.json   ← 새 규칙으로 쓰인 것
```

옛 판은 새 파일을 **읽기는 한다** (파일 내용의 `agent` 칸을 보므로). 하지만
**쓸 때는 옛 이름으로 쓴다.** 그래서 같은 사람이 장부에 두 줄로 존재하고,
옛 판의 반납은 자기가 만든 줄만 지운다. **지운 줄 알았던 것이 남는다.**

> **데이터베이스에서 이 상황을 부르는 말이 있다** — *"읽는 쪽과 쓰는 쪽이 서로
> 다른 스키마를 본다."* 프로그램이 여러 벌 돌아다니는 곳에서는 스키마를 바꿀 때
> **새 판이 옛 것도 읽을 수 있게 만든 뒤, 모두가 새 판이 된 다음에 옛 것을 버린다.**
> 이 저장소는 그 절반(읽기 호환)은 했고 나머지 절반(모두 옮기기)을 안 했다.

### 4.6 🔴 사고 4 · **다른 폴더에서 잡으면 장부에 안 남았다**

**worktree**(같은 저장소의 다른 브랜치를 옆 폴더로 펼쳐 둔 것)에서 선점을 부르면
장부에 안 남았다. 지금 이 PC 에는 코드 worktree 가 **14개** 열려 있다 (실측).

원인은 한 줄이다.

```js
// 옛 판
function ledgerDir(root) { return path.join(root, '.axmap/ledger') }
//                                          ↑ root = 지금 서 있는 worktree 폴더

// 지금 판
function ledgerDir(root) { return path.join(axmapHome(root), '.axmap/ledger') }
//                                          ↑ 메인 폴더를 되짚어서 찾는다
```

장부는 **메인 폴더 한 곳에만** 있다. 옛 판은 "지금 서 있는 폴더" 를 봤으므로,
worktree 에서는 없는 자리를 가리켰다.

**이건 데이터베이스라면 "어느 서버에 접속할 것인가" 에 해당한다.** 보통은 주소가
설정에 적혀 있어서 어디서 실행하든 같은 곳을 본다. git 에는 그런 주소가 없고
*"지금 내가 서 있는 폴더"* 로 추측한다. 추측이 갈리면 **없는 데이터베이스에 조용히
쓰게 된다.**

### 4.7 사고 5 · **표가 무효가 되는 것은 의도다** — 제약과 결함을 가르는 법

브랜치에 커밋을 하나 더 올리면 그 앞에 모인 찬성표가 전부 효력을 잃는다.
어제 한 브랜치에서만 **네 번** 났다.

표 파일 이름이 이렇다.

```
votes/back/dev/jaehyeon-31cd6946.json
                        ^^^^^^^^ 그때의 맨 위 커밋
```

**이건 고칠 결함이 아니라 일부러 그렇게 만든 것이다.** 안 그러면 이렇게 된다:
승인을 받는다 → 그 뒤에 내용을 통째로 갈아끼운다 → 승인은 그대로 남아 있다.
**승인받은 것과 머지되는 것이 다른 물건이 된다.**

> **의도된 제약과 결함을 어떻게 구별하나.** 세 가지를 본다.
>
> | | 의도된 제약 | 결함 |
> |---|---|---|
> | 어디에 적혀 있나 | 문서에 **왜** 가 적혀 있다 (`governance/GOVERNANCE.md` 의 G3) | 아무 데도 없다 |
> | 없앴을 때 | **막으려던 나쁜 일이 가능해진다** | 아무 일도 안 난다 |
> | 실패할 때의 모습 | 막고, **막았다고 말한다** | 조용히 통과하거나 조용히 막는다 |
>
> 여기서는 셋 다 "의도" 쪽이다. 무효가 된 표는 **지워지지 않고 목록에 남는다** —
> `헤드가 바뀐 뒤라 효력 없음 (G3)` 이라고 적힌 채로. *"효력을 잃는다"* 는
> *"사라진다"* 가 아니다.

**다만 이건 사람이 겪는 불편이 진짜다.** 하루 네 번이면 설계가 옳아도 도구가
나쁜 것이다. 고칠 자리는 규칙이 아니라 **순서를 알려주는 것**이다 — 표를 걷기
전에 "지금 커밋을 더 올릴 계획이 있나" 를 묻거나, 커밋을 올린 순간 표를 던진
사람들에게 자동으로 알려주는 것. 규칙은 그대로 두고 **놀라지 않게** 만든다.

### 4.8 🔴 사고 6 · **언제가 최신인가**

합의 판정 프로그램이 표를 읽어올 때 이 순서로 찾는다 (`governance/gate.mjs`).

```
1. --votes-ref 로 직접 지정한 것
2. 원격에서 방금 fetch 한 것              ← 이게 정답
3. refs/heads/axmap/votes      (로컬)     ← 여기로 떨어질 수 있다
4. refs/remotes/origin/axmap/votes
```

`--no-fetch` 를 주거나 fetch 가 실패하면 **3번으로 떨어진다.** 로컬 브랜치는
내 PC 에만 있는 사본이라 남이 던진 표가 없다. 그래서 **표가 모였는데 "미달" 이라고
답한다.**

**이걸 데이터베이스에서는 "일관성"(consistency) 문제라고 한다.** 정확히는
*"내가 지금 보는 값이 최신인가, 아니면 좀 지난 것인가"* 다. 그리고 답은
**데이터마다 다르다.**

| 데이터 | 얼마나 최신이어야 하나 | 왜 |
|---|---|---|
| **선점** | 🔴 **반드시 지금** | 낡은 것을 보면 남이 잡은 파일을 또 잡는다. 락이 아니게 된다 |
| **합의 표** | 🔴 **반드시 지금** | 낡은 것을 보면 통과할 것을 막거나, 막을 것을 통과시킨다 |
| **쪽지** | 좀 늦어도 된다 | 늦으면 새 쪽지가 늦게 뜰 뿐이다 |
| **읽음 눈금** | 늦어도 된다 | 늦으면 읽은 쪽지가 한 번 더 뜰 뿐이다 |

지금 코드가 실제로 이 표대로 되어 있다 — 선점은 fetch 실패하면 **죽고**
(`syncLedger` 의 `die`), 읽음 눈금은 **60초 캐시**를 쓴다. 옳은 판단이다.
문제는 표만 예외적으로 로컬로 떨어질 길이 열려 있었다는 것.

> **왜 이게 어려운가.** git 에는 "지금" 이 없다. 내 PC 의 값과 서버의 값이 다를 수
> 있고, **다르다는 사실조차 물어보기 전엔 모른다.** 그래서 매번 `fetch` 를 해야
> 하는데, `fetch` 는 실측 **1.7초**다. 매번 하면 도구가 느려지고, 안 하면 틀린다.
> **어디에 1.7초를 쓸지가 설계 결정이다.**

### 4.9 없는 것 · **지우기**

데이터베이스라면 `DELETE FROM messages WHERE at < '2026-08-01'` 이면 끝이다.
git 에서 파일을 지우면 **현재 상태에서만 사라지고 이력에는 그대로 남는다.**
진짜로 지우려면 이력을 다시 쓰고 모두가 다시 clone 해야 한다.

실측: 선점 브랜치는 **지금 살아 있는 데이터가 4 KB 인데 226 KB 를 차지한다.**
55배다. 지금 크기로는 아무 문제가 없다. 하지만 **이 비율은 계속 커진다.**

### 4.10 없는 것 · **일부만 잠그기**

데이터베이스는 한 줄만 잠그고 다른 줄은 남이 쓰게 둘 수 있다. git 은 브랜치
전체가 단위다. 그래서 **한 파일에 여러 사람의 데이터를 모아 두면, 서로 관계없는
두 사람의 쓰기가 부딪힌다.**

이 저장소는 이걸 알고 **처음부터 파일을 쪼갰다.** 쪽지 하나에 파일 하나,
사람 하나에 파일 하나. 6절에서 왜 그게 맞았는지 본다.

## 5. 🔴 `git push` 는 이미 데이터베이스의 핵심 장치 하나다

여기가 이 설계의 절반이다.

### 5.1 무슨 일이 일어나나

`git push` 는 이렇게 동작한다.

> **"내가 읽은 뒤로 서버가 안 바뀌었을 때만 쓴다."**
> 그 사이에 남이 먼저 썼으면 **거부한다.**

이걸 **CAS**(Compare-And-Swap — "비교하고 바꾸기". 지금 값이 내가 봤던 그 값일
때만 새 값으로 바꾸고, 아니면 실패한다)라고 한다. 데이터베이스와 운영체제가
동시성을 다루는 가장 기본적인 도구이고, **git 은 이걸 공짜로 준다. 그리고 끌 수 없다.**

```
   A 가 장부를 읽음 (커밋 X)          B 가 장부를 읽음 (커밋 X)
   A 가 자기 줄을 더해서 push  ✅      B 가 자기 줄을 더해서 push  ❌ 거부
                                       "서버는 이제 Y 인데 너는 X 를 봤다"
```

**B 는 A 의 글을 못 덮어쓴다.** 이게 없으면 나중에 쓴 사람이 앞사람 것을 조용히
지운다 — 데이터베이스에서 **잃어버린 갱신**(lost update)이라고 부르는, 여러 명이
같이 쓸 때 나는 가장 흔한 사고다.

### 5.2 거부됐을 때 어떻게 하나

**거부는 "안 된다" 가 아니라 "최신 것 받아서 다시 해라" 다.** 그래서 이렇게 돈다
(`bin/axmap.mjs` 의 `cmdClaim`).

```
반복 (최대 N 회):
  1. 서버에서 최신 장부를 받아 통째로 덮어쓴다   ← 병합하지 않는다. 서버가 진실이다
  2. 지금 장부를 보고 "겹치나" 를 판정한다        ← 여기서 겹치면 그냥 거부. 재시도 안 함
  3. 내 줄을 쓰고 push
  4. 성공 → 끝
     거부 → 조금 기다렸다가 1번으로
  5. push 할 수 없음(서버 장애) → 로컬 것도 되돌리고 죽는다
```

세 가지가 중요하다.

**① 병합하지 않고 통째로 덮어쓴다.** git 은 보통 두 변경을 합치려고 하는데,
장부에서는 그러면 안 된다. **합치면 두 사람이 동시에 소유권을 갖는다** — 6절 「다」
에서 실측으로 확인한 실패다. **서버 것이 진실이고 내 것은 다시 만든다.**

**② 조금 기다렸다가 다시 한다** (`casBackoff`). 안 그러면 경합 중인 프로그램들이
매번 같은 순간에 같이 fetch 하고 같이 push 해서 **같은 쪽이 계속 진다.**
흩어놔야 누군가는 통과한다.

**③ 🔴 push 못 하면 로컬 것도 되돌린다.** 이게 제일 중요하다.

> 서버에 못 올린 선점을 내 PC 에만 남겨두면, **내 화면에는 "내가 잡고 있다" 고
> 나오는데 남은 그걸 볼 수 없다.** 그래서 같은 파일을 잡는다.
> **선점은 서버에 도달했을 때만 성립한다.**

### 5.3 얼마나 자주 부딪히나 — 실측

거부가 얼마나 나는지는 기록이 안 남아서 **직접 측정 못 했다.** 대신 추정할 재료는 있다.

가장 바쁜 날(2026-09-07) 선점 브랜치에 쓴 간격:

```
쓰기 294회
쓰기 사이 간격 중앙값   89초
가장 짧은 간격           4초
10초 안에 붙은 것       294회 중 19회
가장 바쁜 한 시간       40회  (평균 90초에 한 번)
```

한 번의 쓰기가 서버를 잡고 있는 시간은 `fetch` + `push` ≈ **3.4초** (fetch 실측
1.7초). 그러면 **부딪힐 확률은 대략 3.4 ÷ 89 ≈ 4%** — 25번에 한 번.
재시도가 있으니 사람은 거의 못 느낀다.

> ⚠️ 이건 추정이다. 실제 거부 횟수는 **확인 못 함** — 거부는 커밋을 안 남기므로
> 이력에 흔적이 없다. 재보려면 거부를 셀 자리를 만들어야 한다.

**이 숫자가 열 배가 되면 이야기가 달라진다.** 89초에 한 번이 아니라 8.9초에
한 번 쓰게 되면 충돌 확률이 40% 가 된다. 7절에서 그 선을 잡는다.

```
messages/20260907T154130Z-jinmiri-데이터-파이프라인-막힘.md
```

**이름을 잘 지으면 두 사람이 같은 파일을 만들 일이 구조적으로 없다.**
이름에 **시각 + 보낸 사람 + 제목**이 들어간다. 다른 사람끼리는 절대 안 겹치고,
같은 사람이라도 같은 초에 같은 제목으로 두 번 보내야 겹친다.
겹칠 수 없으면 **조율도 필요 없다.**

> ⚠️ 시각은 **초 단위**다 (`20260907T153656Z`). 밀리초가 아니다. 즉 겹칠 확률이
> 0 은 아니다 — 한 프로그램이 같은 제목으로 1초 안에 두 통을 보내면 뒤엣것이
> 앞엣것을 덮는다. **지금 353건 중 그런 사례는 없었다.** 자동으로 쏟아붓는
> 쓰임이 생기면 그때 밀리초를 붙인다.

| 좋은 점 | 나쁜 점 |
|---|---|
| 동시에 써도 절대 안 부딪힌다 | 파일이 계속 늘어난다 (지금 353개) |
| 이름이 곧 정렬 순서다 (시각으로 시작) | 골라내려면 전부 열어봐야 한다 |
| 한 건만 지우면 한 건만 지워진다 | 이름이 곧 키라, 이름 규칙을 바꾸면 4.5 사고가 난다 |

**쪽지에 맞는다.** 계속 쌓이고, 안 고치고, 여럿이 동시에 쓴다.

> ⚠️ **파일 이름은 데이터의 일부다.** 쪽지 id 는 파일 이름 그 자체이고, 읽음
> 눈금이 그 id 를 비교한다. 이름 규칙을 바꾸면 **모든 눈금이 한꺼번에 어긋난다.**

### 나 · 덧붙이기만 하는 기록 + 가끔 접기

```
log/2026-09-07.jsonl        ← 한 줄에 한 사건. 뒤에만 붙인다
log/2026-09-06.jsonl
snapshot/2026-09-06.json    ← 그날까지를 "접어 둔" 결과
```

**접기**(compaction — 지나간 기록을 하나하나 다시 읽지 않아도 되게, 그때까지의
결과만 요약해 두는 것)를 같이 쓴다. 읽는 쪽은 *"마지막 접은 것 + 그 뒤의 줄들"*
만 보면 된다.

이 저장소에 이미 하나 있다 — `axmap/checkpoints` 의 `checkpoints.json`.

```json
{ "ledger": "5139d13e...", "at": "2026-09-07T02:30:46Z", "snapshots": 1015 }
{ "ledger": "9ce30c28...", "at": "2026-09-07T02:43:30Z", "snapshots": 1024 }
```

감사 프로그램이 장부를 매번 처음부터 다시 읽어서 쓸수록 느려졌다. "여기까지는
이미 봤다" 를 적어두는 것으로 고쳤다.

| 좋은 점 | 나쁜 점 |
|---|---|
| 쓰기가 절대 안 부딪힌다 (뒤에만 붙이므로) | 읽을 때 처음부터 훑어야 한다 |
| 무슨 일이 있었는지가 순서대로 다 남는다 | 접는 프로그램을 따로 만들어야 한다 |
| 지금 상태를 언제든 다시 계산할 수 있다 | 접은 것이 틀리면 그 뒤가 전부 틀린다 |

> 🔴 **한 파일에 여럿이 뒤에만 붙이는 것은 git 에서 안 부딪히지 않는다.**
> 텍스트 파일 끝에 두 사람이 각각 줄을 더하면 git 은 **충돌을 낸다.**
> "쓰기가 안 부딪힌다" 는 것은 **쓰는 사람이 하나일 때**의 이야기다.
> `checkpoints.json` 도 쓰는 것은 봇 하나뿐이다.

### 다 · 한 파일에 모아 쓰기

```
claims.json     ← 모두의 선점이 한 파일에
```

**이 저장소가 실제로 이걸 먼저 해봤고, 실패해서 지금 구조가 됐다**
(`docs/EXPERIMENT.md`).

발상은 그럴듯했다 — *"어차피 충돌이 날 거라면, 코드에서 나기 전에 '나 이 파일
건드린다' 는 선언에서 먼저 나게 하자."* 한 파일에 정렬된 목록으로 두면 같은 경로를
요청한 둘이 같은 줄 자리에 쓰게 되고, git 이 알아서 충돌을 낼 것이라고 봤다.

실측 결과가 정반대였다.

| 상황 | 올바른 답 | git 이 낸 답 |
|---|---|---|
| 다른 경로 둘, 장부에 다른 줄 없음 | 통과 | **거부** ✗ |
| 다른 경로 둘, 장부에 제3자 줄 있음 | 통과 | 통과 ✓ |
| 같은 경로 둘 | 거부 | 거부 ✓ |

첫째와 둘째는 **입력이 글자 하나 다르지 않다.** 달라진 것은 아무 관계 없는
제3자가 장부에 남긴 줄 하나뿐이다. 그 줄을 기준으로 둘이 위/아래로 갈라져서
git 이 "다른 자리" 라고 봤다.

> **git 이 답한 질문**: *"둘이 같은 줄 자리에 썼는가"*
> **우리가 묻고 싶었던 질문**: *"둘이 요청한 경로가 겹치는가"*
>
> 두 질문의 답은 **우연히만** 일치하고, 그 우연을 **제3자의 데이터가 결정한다.**

그리고 더 나쁜 것: 장부가 비어 있을수록 틈이 적어서 **경합이 가장 적을 때 잘못된
거부가 가장 많이 났다.** 락 장치로서 정확히 반대로 도는 특성이다.

결정타는 AI 에이전트였다. 충돌 표시를 본 LLM 의 기본 행동은 **"양쪽을 다 살려서
병합"** 인데, 락 장부에서 양쪽을 살리면 **두 에이전트가 동시에 소유권을 갖는다.**
프로토콜이 정반대로 뒤집히는데 겉으로는 "충돌 해결 완료" 로 보인다.

| 좋은 점 | 나쁜 점 |
|---|---|
| 사람이 열어서 전체를 한눈에 본다 | 🔴 **둘이 동시에 쓰면 반드시 부딪힌다** |
| 파일이 안 늘어난다 | 충돌을 사람이나 AI 가 푸는데, **잘못 푸는 방향이 안전하지 않다** |
| | 한 줄만 바꿔도 파일 전체가 새 판이 된다 |

**쓰는 사람이 하나일 때만 쓴다.** `checkpoints.json` 이 그 경우다.

### 라 · 사람마다 자기 자리에만 쓰기

```
users/rleaderjoon@gmail.com.json
users/masdf13@naver.com.json
users/ahwlstjd57@gmail.com.json
```

**자기 파일만 쓰므로 남과 절대 안 부딪힌다.** 가와 비슷하지만 다르다 —
가는 건마다 새 파일이 생기고, 라는 **파일 개수가 사람 수로 고정**되고 내용이 바뀐다.

| 좋은 점 | 나쁜 점 |
|---|---|
| 남과 절대 안 부딪힌다 | 전체를 보려면 전부 열어서 모아야 한다 |
| 파일 수가 사람 수를 안 넘는다 | **파일 이름이 곧 사람의 키다** — 키가 갈리면 4.2 사고 |
| 사람이 나가면 파일 하나 지우면 끝 | 한 사람의 두 창이 동시에 쓰면 이건 부딪힌다 |

**사람 정보에 맞는다.** 그리고 **선점에도 맞는다** — 다만 선점의 임자는 사람이
아니라 **(사람, 창)** 이라, 파일 이름도 그 짝이어야 한다. 그게 4.5 에서 본 변경이다.

### 셋에 무엇이 맞나 — 한 표

| | 선점 | 쪽지 | 사람 정보 |
|---|---|---|---|
| **가** 한 건 = 한 파일 | △ 건이 아니라 임자 단위다 | 🟢 **맞다** | ✗ |
| **나** 덧붙이기 + 접기 | ✗ 지금 상태를 알려고 매번 훑는다 | △ 언젠가 필요 | ✗ |
| **다** 한 파일에 모아 | 🔴 **실패했다** (위) | 🔴 안 된다 | 🔴 안 된다 |
| **라** 사람마다 자기 자리 | 🟢 **맞다** (임자 = 사람+창) | ✗ 남이 보낸 것을 받아야 한다 | 🟢 **맞다** |

**지금 구조가 이미 이 표대로다.** 이 문서의 결론은 "갈아엎어라" 가 아니다.

## 7. 🔴 결정하기 전에 재봐야 하는 것

문외한이 가장 모르는 부분이 여기다. **이걸 모르면 위 넷 중 무엇을 고를지 못 정한다.**
아래는 재는 방법과 **지금 저장소의 실제 값**이다.

### 7.1 읽기가 많나 쓰기가 많나

| | |
|---|---|
| **왜 중요한가** | 읽기가 많으면 **읽기 쉬운 모양**(다 · 모아 쓰기)이 유리하고, 쓰기가 많으면 **안 부딪히는 모양**(가·라)이 유리하다 |
| **어떻게 재나** | 쓰기는 커밋 수로 센다. 읽기는 프로그램이 세어주지 않으면 못 잰다 |
| **지금 값** | 쓰기: 선점 하루 최대 **281회**, 쪽지 하루 최대 **108건**. 읽기: 🔴 **확인 못 함** |

> 읽기를 못 재는 것이 실제로 문제다. 도구를 부를 때마다 쪽지함을 읽으므로 읽기가
> 쓰기보다 훨씬 많을 것이 거의 확실하지만, **"거의 확실" 은 숫자가 아니다.**

### 7.2 몇이 동시에 쓰나

| | |
|---|---|
| **왜 중요한가** | 5.3 의 충돌 확률이 여기서 나온다. 동시에 쓰는 수가 늘면 **다(모아 쓰기)는 즉시 무너지고**, 가·라도 재시도가 늘어난다 |
| **어떻게 재나** | 쓰기 사이 간격을 재서, 한 번의 쓰기가 걸리는 시간과 비교한다 |
| **지금 값** | 사람 **6명**, 이 PC 한 대에 작업 폴더 **14개**. 쓰기 간격 중앙값 **89초**, 최소 4초. 한 번 쓰는 데 약 **3.4초** → 충돌 확률 **약 4%** |

**언제 위험해지나**: 쓰기 간격 중앙값이 **10초 밑**으로 내려가면 충돌이 3분의 1이
된다. 그때는 선점을 더 잘게 쪼개야 한다 (예: 파트별로 브랜치를 나눈다).

### 7.3 얼마나 쌓이나

| | |
|---|---|
| **왜 중요한가** | 가(한 건 한 파일)는 파일 수로, 나(덧붙이기)는 훑는 길이로 한계가 온다 |
| **어떻게 재나** | `git ls-tree -r --name-only origin/<브랜치> \| wc -l` 로 파일 수. 실제로 다 읽는 데 걸리는 시간을 재본다 |
| **지금 값** | 쪽지 **353건 / 12일 = 하루 약 29건**. 전체 836 KB, 평균 2.4 KB. **전부 읽는 데 0.052초** |

**언제 위험해지나**: 전부 읽는 데 **1초**를 넘으면 사람이 느낀다. 지금의 20배 —
**약 6,800건 (353 ÷ 0.052 초), 하루 29건이면 220일 — 7개월 뒤**다.
그때 필요한 것이 접기(나)다.
**지금 만들 이유가 없다.**

### 7.4 옛것을 지워도 되나

| | |
|---|---|
| **왜 중요한가** | 지워도 되면 늘어나는 것이 문제가 안 된다. 못 지우면 **모양을 처음부터 그렇게 잡아야 한다** |
| **어떻게 정하나** | 규칙이 아니라 **사람이 정한다.** 물어봐야 한다 |
| **지금 값** | 선점: 30~45분 뒤 만료 → **지워도 된다.** 쪽지: 🔴 **사람이 정해야 함.** 표: 판정 근거라 **남아야 한다.** 사람 정보: 사람이 나가면 지워도 된다 |

> 🔴 **git 에서는 "지운다" 가 반쯤만 지운다.** 4.9 참고. 현재 상태에서 사라질 뿐
> 이력에는 남는다. 그래서 진짜로 지워야 하는 것(예: 개인정보)이 들어가면
> **git 은 맞는 자리가 아니다.**

### 7.5 조금 옛것을 봐도 되나

| | |
|---|---|
| **왜 중요한가** | 매번 최신을 확인하면 통신이 **1.7초**씩 붙는다. 안 하면 4.8 처럼 틀린 답이 나온다 |
| **어떻게 정하나** | *"낡은 값을 보면 무슨 나쁜 일이 나나"* 를 데이터마다 답한다 |
| **지금 값** | 4.8 의 표대로 이미 갈라 놓았다. 선점·표는 매번 확인, 읽음 눈금은 60초 캐시 |

### 7.6 한 건의 임자가 누구인가

**이걸 안 정하면 아무것도 못 고른다.** 4.2·4.5 두 사고가 전부 여기서 났다.

| 데이터 | 임자는 무엇인가 | 지금 |
|---|---|---|
| 선점 | **(사람, 창)** — 같은 사람의 두 창은 다른 임자 | 이름+창 해시 (이름이 42개) |
| 쪽지 | 보낸 사람 하나. 받는 사람은 여럿 | 이름 (갈린다) |
| 사람 정보 | 사람 하나 | 🟢 이메일 (안 갈린다) |
| 표 | (사람, 브랜치, 커밋) | 이름 + 커밋 8자 |

**세 곳이 이름을 쓰고 한 곳이 이메일을 쓴다. 이게 지금 구조의 단 하나의 진짜 결함이다.**

### 8.3 🔴 읽음 눈금을 안전하게 옮기는 절차

**가장 조심스러운 작업이다.** 자리를 하나로 합치면서 실수하면 **전원이 353건을
한꺼번에 안 읽음으로 보게 된다.** 그렇게 되면 사람은 그것을 배경으로 여기고
**아예 안 읽는다** — 이 도구가 고치려던 바로 그 상태다.

원칙 셋을 먼저 정한다.

> **① 눈금은 절대 뒤로 안 간다.** 어떤 경우에도 이미 읽은 것이 안 읽음이 되지 않는다.
> **② 한 판에 한 가지만 바꾼다.** 자리 합치기와 모양 바꾸기를 같이 하지 않는다.
> **③ 먼저 인쇄만 해본다.** 바꾸기 전에 "바꾸면 각자 몇 건이 되나" 를 사람이 눈으로 본다.

#### 1단계 — 재기만 한다 (아무것도 안 바꾼다)

한 번만 도는 프로그램을 만들어서 **인쇄만** 한다.

```
사람                        지금 안 읽음    합친 뒤 안 읽음    차이
rleaderjoon@gmail.com            16              16            0
masdf13@naver.com                 3               3            0
ahwlstjd57@gmail.com             22              22            0
...
```

**차이 칸이 0 이 아닌 사람이 있으면 거기서 멈춘다.** 왜 다른지 먼저 답해야 한다.

계산 방법: 각 PC 안의 파일에 있는 눈금들을, 그 이름의 임자 이메일로 접어서
(`tools/bus.mjs` 의 `roster()` 가 이미 그 일을 한다) **가장 나아간 것**을 고른다.
그 값이 공유 브랜치의 값보다 나아가 있으면 그것이 새 값이다.

> ⚠️ **이 단계는 각 PC 에서 돌려야 한다.** PC 안의 파일은 그 PC 에만 있다.
> 한 사람이 PC 를 둘 쓰면 둘 다 봐야 한다. **이게 이 작업이 하루 만에 안 끝나는 이유다.**

#### 2단계 — 올리기만 한다 (내리지 않는다)

인쇄한 것을 사람이 확인한 뒤, 공유 브랜치의 값을 **더 나아간 쪽으로만** 갱신한다.
사람마다 파일이 따로라 서로 안 부딪힌다. 되돌리려면 그 커밋 하나만 되돌리면 된다.

**이 시점에도 읽는 규칙은 안 바꾼다.** 여전히 두 자리를 보고 더 나아간 쪽을 쓴다.
그러면 **이 단계에서는 아무 변화도 안 보인다** — 그게 맞다. 성공의 모습이
"아무 일도 안 일어남" 인 것이 안전한 이전이다.

#### 3단계 — 쓰는 곳을 하나로 (읽는 곳은 아직 둘)

새로 쓰는 것은 공유 브랜치에만 쓴다. PC 안 파일은 **읽기만** 한다.
여기서 문제가 나면 되돌리기 쉽다 — PC 안 파일이 그대로 있으므로.

#### 4단계 — 읽는 곳도 하나로

며칠 돌려보고 아무도 이상하다고 안 하면, PC 안 파일 읽기를 뗀다.
**최소 한 주는 둔다.** 사람마다 도구를 켜는 주기가 다르다.

#### 5단계 — 그 다음에야 모양을 바꾼다 (한 칸 → 목록)

**절대 4단계와 같이 하지 않는다.** 옮기는 방법은 옛 값을 버리지 않는 것이다.

```json
// 지금
{ "seen": "20260907T084945Z-..." }

// 나중
{ "seen": "20260907T084945Z-...",     ← 이 아래는 전부 읽음 (그대로 둔다)
  "read": ["20260907T131116Z-...", "20260907T153656Z-..."] }
                                       ← 그 위에서 하나씩 읽은 것
```

옛 칸을 **지우지 않고 그대로 둔다.** 옛 판의 프로그램은 `seen` 만 보므로
계속 돈다. 새 판은 `seen` **또는** `read` 에 있으면 읽음으로 친다.
**한 판에서 두 가지 뜻이 공존할 수 있게 만들어 놓고, 옛 뜻을 나중에 뗀다.**
이게 4.5 사고에서 안 한 절반이다.

목록이 무한정 길어지지 않게: `read` 안의 것이 연속으로 이어지면 `seen` 으로
접는다 (6절의 "접기").

## 9. 🔴 추천 — 셋 각각에 하나씩

### 선점 → **라 (사람마다 자기 자리)** · 지금 그대로 · **키만 이메일로**

**임자 하나에 파일 하나**가 맞다. 이유는 셋이다.

1. 임자는 짧게 살고(30~45분) 자주 바뀐다 — 덧붙이기(나)로 쌓으면 "지금 누가
   잡고 있나" 를 물을 때마다 처음부터 훑어야 한다
2. 여럿이 동시에 쓴다 — 모아 쓰기(다)는 실측으로 실패했다 (6절 다)
3. 다 쓰면 지워야 한다 — 한 파일에 모여 있으면 한 건을 지울 때도 파일 전체가
   새 판이 된다

**바꿀 것은 파일 이름의 앞부분 하나다.**

```
지금    claims/janghyojoon@8c0afdd9.json          ← 이름 (사람 8명에 42개)
바꾼 뒤 claims/rleaderjoon@gmail.com@8c0afdd9.json ← 이메일 (사람 8명에 9개)
```

**지금 구조에서 얼마나 바뀌나: 거의 안 바뀐다.** 파일 이름을 만드는 함수 하나와,
읽을 때 옛 이름도 알아보게 하는 것. 브랜치 구조·CAS·재시도·만료는 전부 그대로다.

> ⚠️ 옮기는 동안 옛 이름과 새 이름이 같이 존재한다. **새 판은 둘 다 읽고,
> 쓸 때만 새 이름을 쓴다.** 선점은 30~45분이면 만료되므로 **하루면 옛 이름이
> 저절로 마른다** — 이 셋 중 가장 옮기기 쉽다. 여기서 먼저 한다.

### 쪽지 → **가 (한 건에 파일 하나)** · 지금 그대로 · **안 바꾼다**

이유는 하나로 충분하다. **353건을 전부 읽는 데 0.052초다.** 고칠 이유가 없다.

- 접기(나)는 **지금 만들지 않는다.** 7.3 에서 잰 대로 필요해지는 것은 약 6,800건,
  이 속도면 7개월 뒤다. **지금 만들면 7개월 동안 쓸모없는 코드를 관리한다**
- 모아 쓰기(다)는 애초에 불가능하다 — 6명이 동시에 보낸다

**단 하나 정해야 할 것**: 쪽지의 **받는 사람**도 이름으로 적혀 있다. 이건 선점을
옮기고 나서 같이 옮긴다. 이미 읽을 때는 이름·이메일을 다 알아보게 되어 있어서
(`addressesOf`) 급하지 않다.

**지금 구조에서 얼마나 바뀌나: 안 바뀐다.**

### 사람 정보 → **라 (사람마다 자기 자리)** · 지금 그대로 · **자리를 하나로, 그 다음 모양을**

이미 이메일을 키로 쓰고 있어서 **가장 옳게 되어 있다.** 문제는 **같은 값을 PC 안에도
적어둔 것**이다 (4.2).

두 가지를 순서대로 한다. **한 번에 하지 않는다.**

1. **PC 안 파일을 없앤다** — 8.3 의 1~4단계. 이걸로 사고 1이 사라진다
2. **눈금을 한 칸에서 목록으로** — 8.3 의 5단계. 이걸로 사고 2가 사라진다

**지금 구조에서 얼마나 바뀌나: 저장 자리는 안 바뀌고(브랜치도 파일 이름도 그대로),
읽고 쓰는 규칙만 바뀐다.** 다만 셋 중 **가장 조심스럽다** — 잘못하면 모두의
쪽지함이 한꺼번에 흔들린다. 그래서 8.3 의 절차가 있다.

### 순서

```
1. 선점의 키를 이메일로        ← 가장 쉽다. 하루면 옛 것이 마른다
2. 낡은 사본 걷어내기          ← 사고 3·4 가 같이 사라진다 (✅ 2026-10-29, D31)
3. 표가 로컬로 떨어지는 길 막기 ← 사고 6
4. 읽음 눈금 자리 합치기        ← 사고 1. 8.3 의 절차대로, 최소 한 주
5. 읽음 눈금 모양 바꾸기        ← 사고 2. 4번이 끝난 뒤에
```

**1·2·3 은 서로 안 겹치므로 같이 해도 된다. 4·5 는 순서를 지킨다.**

## 10. 이 문서가 답하지 못한 것

정직하게 남긴다.

| | |
|---|---|
| **읽기 횟수** | 확인 못 함. 세는 자리가 없다 |
| **push 거부(CAS 실패) 횟수** | 확인 못 함. 거부는 커밋을 안 남긴다. 5.3 의 4% 는 간격으로 낸 **추정**이다 |
| **안 읽음 개수가 25→22→5→16 으로 바뀐 정확한 재현 조건** | 사람이 본 그대로 적었다. **코드에서 확인한 것은 그것이 가능한 경로**(4.2 의 `readSeen`)이지 그 네 숫자 자체가 아니다 |
| **쪽지를 언제 지워도 되나** | 사람이 정해야 한다 |
| **다른 팀·다른 저장소에서도 이 숫자가 비슷한가** | 확인 못 함. 전부 이 저장소 한 곳의 실측이다 |

## 용어표

| 말 | 뜻 |
|---|---|
| **원자성** (atomicity) | 하나의 변경이 통째로 되거나 통째로 안 되거나. 반쯤 된 상태가 없다 |
| **키** (key) | 한 줄을 다른 줄과 구별하는 이름표. 여기서는 대부분 **파일 이름**이 곧 키다 |
| **스키마** (schema) | 데이터가 어떤 모양이어야 하는지의 약속. "선점 파일은 `<이름>.json`" 같은 것 |
| **질의** (query) | 조건을 주고 맞는 것만 골라내라고 물어보는 것 |
| **색인** (index) | 전부 안 훑고 바로 집을 수 있게 미리 만들어 둔 지름길 |
| **CAS** (Compare-And-Swap) | "내가 읽은 뒤로 안 바뀌었을 때만 쓴다". `git push` 가 원래 이렇게 동작한다 |
| **잃어버린 갱신** (lost update) | 둘이 같이 쓸 때 나중 사람이 앞사람 글을 조용히 지우는 것. CAS 가 막는 것 |
| **하이 워터 마크** | 물이 가장 높이 올라왔던 자국 하나만 남기는 방식. 그 아래는 전부 지나간 것으로 친다 |
| **접기** (compaction) | 지나간 기록을 다시 안 읽어도 되게 그때까지의 결과만 요약해 두는 것 |
| **고아 브랜치** (orphan branch) | 코드 이력과 조상을 하나도 공유하지 않고 따로 도는 브랜치 |
| **worktree** | 같은 저장소의 다른 브랜치를 옆 폴더로 펼쳐 둔 것 |
| **훅** (hook) | 커밋 같은 순간에 git 이 자동으로 돌리는 검사 프로그램 |
| **일관성** (consistency) | 지금 내가 보는 값이 최신인가, 좀 지난 것인가의 문제 |
