# 실험: git 의 텍스트 충돌을 선점 감지에 쓸 수 있는가

이 프로젝트의 최초 발상은 이랬다.

> 어차피 충돌이 날 거라면, 코드에서 나기 전에 "나 이 파일 건드린다"는 선언에서 먼저 나게 하자.
> 그러면 git 의 기존 conflict 메커니즘만으로 도구 없이 겹침을 막을 수 있지 않을까.

방향은 맞다. 코드 충돌을 의도 충돌로 앞당기는 것이 이 프로젝트 전체의 전제다.
다만 **그 판정을 git 에게 맡길 수 있는가**는 별개의 질문이고, 이 문서는 그것을 실측한 기록이다.

재현: `bash demo/conflict-vs-parser.sh`

---

## 설계

경로 사전순으로 정렬된 단일 장부 `LOCKS.tsv` 를 공유 브랜치에 두고,
에이전트 A 와 B 가 각각 한 줄씩 추가한 뒤 병합한다.
같은 경로를 요청하면 같은 줄 자리에 삽입되므로 git 이 알아서 충돌을 낼 것이라는 기대다.

```
# path              agent    since   task
src/auth/login.ts   agent-a  T09:00  task-12
src/user/profile.ts agent-b  T09:02  task-13
```

같은 입력을 두 판정기에 넣고 답을 비교했다.

- **판정기 A** — git 의 3-way 병합 (텍스트 충돌 여부)
- **판정기 B** — `src/protocol.mjs` 의 `checkOverlap()` (경로 교집합)

---

## 결과

| | A 가 요청 | B 가 요청 | 장부의 제3자 항목 | 올바른 판정 | git 판정 | 파서 판정 |
|---|---|---|---|---|---|---|
| **Case 1** | `src/auth/login.ts` | `src/user/profile.ts` | 없음 | 통과 | **거부** ✗ | 통과 ✓ |
| **Case 2** | `src/auth/login.ts` | `src/user/profile.ts` | `src/core/config.ts` | 통과 | 통과 ✓ | 통과 ✓ |
| **Case 3** | `src/auth/login.ts` | `src/auth/login.ts` | 없음 | 거부 | 거부 ✓ | 거부 ✓ |

`git push` 의 ref CAS 는 **세 케이스 모두에서** B 의 push 를 거부했다.

---

## 해석

### 1. Case 1 과 Case 2 는 입력이 같은데 답이 갈렸다

두 케이스에서 A 와 B 가 요청한 경로는 글자 하나 다르지 않다.
달라진 것은 **아무 관계 없는 `agent-c` 가 장부에 남긴 줄 하나**뿐이다.

정렬 장부에서 A 와 B 는 그 줄을 기준으로 위/아래로 갈라졌고, git 은 "서로 다른 자리"라고 판단해 통과시켰다.
그 줄이 없는 Case 1 에서는 둘 다 헤더 바로 다음 자리에 삽입되었고, git 은 충돌을 냈다.

> git 이 답한 질문: **"둘이 장부의 같은 줄 자리에 썼는가"**
> 우리가 묻고 싶은 질문: **"둘이 요청한 경로가 겹치는가"**

두 질문의 답은 우연히만 일치한다. 그리고 그 우연은 **제3자의 데이터에 의해 결정된다.**

### 2. 오탐률이 거꾸로 움직인다

충돌은 두 삽입이 같은 틈(gap)에 들어갈 때 발생한다.
장부가 비어 있을수록 틈이 적으므로 서로 다른 경로끼리도 같은 틈에 몰린다.

**즉 경합이 가장 적을 때 오탐이 가장 많다.** 락 시스템으로서는 정확히 반대로 동작하는 특성이다.

### 3. Case 1 과 Case 3 은 출력 형태가 동일하다

```
<<<<<<< HEAD
src/user/profile.ts   agent-b ...      ← Case 1. 올바른 해결: 두 줄 다 남긴다
=======
src/auth/login.ts     agent-a ...
>>>>>>> ccb63e2

<<<<<<< HEAD
src/auth/login.ts     agent-b ...      ← Case 3. 올바른 해결: 한 줄만 남기고 B 는 포기
=======
src/auth/login.ts     agent-a ...
>>>>>>> bf884ed
```

정답이 정반대인데 신호는 같다.
구분하려면 marker 안의 경로를 꺼내 비교해야 하고, **그 비교기가 곧 파서다.**
파서를 어차피 짜야 한다면 git 충돌을 경유할 이유가 없다.

### 4. AI 에이전트에게는 실패 방향이 뒤집힌다

LLM 이 conflict marker 를 보았을 때의 기본 행동은 "양쪽을 모두 살려 병합"이다.
코드에서는 대개 맞는 선택이지만 **락 장부에서 양쪽을 살리면 두 에이전트가 동시에 소유권을 갖는다.**

프로토콜이 정확히 반대로 뒤집히는데, 겉으로는 "충돌 해결 완료"로 보인다.
조용히 실패하는 설계다.

---

## 결론

- 최초 발상의 **목표**(코드 충돌 대신 의도 충돌을 먼저 터뜨린다)는 유지한다.
- 그 목표의 **판정기**만 git 의 줄 단위 diff 에서 직접 짠 파서로 바꾼다.
- `git push` 의 ref CAS 는 선택 대상이 아니다. push 하는 순간 항상 작동하며,
  실패는 거절이 아니라 "최신 장부를 받아 다시 하라"는 순번 신호다.

이것이 [SPEC.md](SPEC.md) 의 **두 관문** 구조가 된 근거다.

| 층 | 질문 | 담당 | 선택 가능? |
|---|---|---|---|
| 관문 1 · 직렬화 | 내가 받아간 뒤 ref 가 움직였나 | `git push` ref CAS | 아니오 (항상 켜짐) |
| 관문 2 · 판정 | 요청 경로가 남의 것과 겹치나 | `checkOverlap()` | 예 |

이 실험의 세 케이스는 `test/protocol.test.mjs` 에 회귀 테스트로 남아 있다.
특히 **"Case 1 과 Case 2 는 반드시 같은 답이어야 한다"** 는 테스트가
무관한 제3자의 데이터가 판정을 바꾸지 못하도록 고정한다.
