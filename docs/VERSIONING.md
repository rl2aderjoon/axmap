# 버전 — 브랜치 단계가 자리를 정한다

`main ➔ func ➔ dev` 3단계. 어느 브랜치에 들어왔는지가 `major.minor.patch` 중
**어느 자리를 올릴지**를 그대로 결정한다.

| 브랜치 | 올리는 자리 | 예 | 언제 |
|---|---|---|---|
| `<파트>/dev` | patch | `1.0.0` → `1.0.1` | 기능 브랜치가 파트 dev 로 머지될 때마다 |
| `<파트>/main` 또는 `<파트>/func` | minor (patch 는 0) | `1.0.3` → `1.1.0` | 하루치 dev 를 파트 중간 단계로 올릴 때 |
| `main` (접두사 없음) | major (아래 전부 0) | `1.2.0` → `2.0.0` | 한 주치를 최상위로 올릴 때 |

🔴 **최상위 `main` 은 접두사가 없는 것뿐이다.** 팀이 실제로 쓰는 파트 브랜치는
`back/main` · `front/main` 인데(옛 저장소의 `be_system/main` 과 같은 컨벤션),
접두사를 통째로 버리면 이것들이 `main` 과 같아져 **파트에 머지할 때마다 major 가
올라간다.** 하루 두 번 머지하면 이틀 만에 5.0.0 이고, 그 숫자는 아무것도 가리키지
않는다. 그래서 **슬래시가 있으면 최상위가 아니다.**

접두사만 다른 것은 같게 본다 — `fe/dev` 도 `back/dev` 도 `dev` 다.
`feat/S15P21E201-144-login` 같은 기능 브랜치는 **단계가 없어서 버전을 올리지 않는다.**
브랜치마다 번호가 갈리면 버전이 무엇도 가리키지 못하기 때문이다.

## 🔴 제품 코드가 없는 파트는 버전을 갖지 않는다

`common` 처럼 **문서·CI·공용 설정만 들어 있는 파트**가 있다. 여기는 버전 축 밖이다.

| | 제품 파트 (`front` · `back` · `bigData`) | 제품이 아닌 파트 (`common`) |
|---|---|---|
| `<파트>/dev` 에 머지 | patch 를 올린다 | **아무것도 안 올린다** |
| 파트 브랜치 (`<파트>/main`) | 있다. minor 를 올린다 | **없다** |
| 최상위 `main` 으로 | 파트 브랜치를 거쳐서 | **`<파트>/dev` 에서 바로** |

### 왜 빼는가

**문서 오타 하나를 고쳤다고 제품 버전이 오르면 그 숫자는 아무것도 가리키지 않는다.**
바로 위에서 날짜 방식을 버린 것과 **똑같은 이유**다 — 아무 일도 안 한 날에 올라가는
숫자와, 제품이 안 바뀌었는데 올라가는 숫자는 같은 종류의 거짓말이다.

그냥 두면 실제로 이렇게 된다. `levelOf` 는 이름의 **마지막 칸만** 보므로
`common/main` 은 파트 브랜치로 읽혀 minor 를, 그 내용이 `main` 에 들어가면 major 를
올린다. 즉 **문서만 고쳐도 제품이 2.0.0 이 된다.**

### 왜 파트 브랜치 단계까지 없애는가

`<파트>/main` 의 뜻은 **"이 파트의 릴리스 후보"** 다. 릴리스할 제품이 없는 파트에는
그 자리가 비어 있다. 비어 있는 칸을 지나가라고 요구하면 사다리가 **막다른 길**이 된다.

2026-08-27 에 실제로 그랬다. 팀 문서가 `common/dev` 까지 올라왔는데 `common/main` 이
원격에 없어서 `main` 으로 갈 길이 사라졌다. **문서는 clone 하면 딸려오는 `main` 에
있어야 뜻이 있는데**, 거기 못 들어갔다. 그래서 `common/dev` 는 최상위로 바로 간다.

> 🔴 **공짜 통과는 아니다.** `main` 으로 가는 MR 은 `governance` 가 정족수를 요구하므로
> 표 없이는 여전히 못 간다. 사다리가 지키려던 것("아래 관문을 지난 것만 위로 간다")은
> 그대로 있고, **없는 칸을 요구하지 않을 뿐이다.**

### 어디에 적혀 있나

`src/version.mjs` 의 `NON_PRODUCT_PARTS` 하나다. **규칙이 아니라 이름 목록이다** —
파트가 제품인지 아닌지는 코드가 알 수 없다. 넣고 빼는 것은 팀의 결정이고,
넣는 순간 그 파트는 버전을 갖지 않고 파트 브랜치 단계도 잃는다.

## 요구한 흐름 그대로

```
1.0.0   첫 작업                    (dev)
1.0.1   다음 작업                  (dev)
1.0.2   그 다음                    (dev)
1.1.0   다음날 — dev 를 func 로     (func)
1.1.1   그날의 작업                (dev)
1.2.0   그 다음날                  (func)
2.0.0   한 주 뒤 — func 를 main 으로 (main)
```

## 🔴 날짜가 아니라 병합으로 올린다

요구는 "하루가 지나면 minor, 한 주가 지나면 major" 였다. 그런데 달력으로 올리면
**아무 일도 안 한 날에도 버전이 올라간다.** 금요일에 `2.0.0` 을 찍었는데 그 주에
머지된 것이 하나도 없으면 그 숫자는 무엇도 가리키지 않는다.

팀의 실제 리듬이 이미 그 주기다 — dev 는 수시로, dev→func 는 하루 한 번,
func→main 은 주 한 번. 그래서 **병합이 일어난 그 순간** 올린다. 결과는 요구한 것과
같고, 다른 점은 그 숫자가 언제나 실제로 들어간 코드를 가리킨다는 것이다.

## 🔴 파일이 아니라 태그에 적는다

`VERSION` 파일이나 `package.json` 의 `version` 을 올리면 **머지마다 텍스트 충돌**이
난다. dev 두 갈래가 각자 `1.0.1` 로 올리면 같은 줄이 부딪히고, 사람이 손으로 푸는
순간 어느 숫자가 맞는지 아무도 모른다.

이 저장소는 같은 문제를 이미 한 번 풀었다 — 장부를 append 로그 하나가 아니라
**파일 하나씩**으로 쪼갠 이유가 그것이다([SPEC.md](SPEC.md) 2절). 태그는 ref 라서
같은 줄을 다투지 않고, git 이 이름 충돌을 CAS 로 막는다. 이미 있는 태그는 두 번
만들 수 없다.

## 손으로 확인하고 싶을 때

```bash
node tools/version.mjs current                 # 지금 버전
node tools/version.mjs next                    # 다음 버전만 계산 (아무것도 안 바꾼다)
node tools/version.mjs next --branch fe/func   # 브랜치를 가정해서 계산
node tools/version.mjs bump --push             # 태그를 만들고 올린다
```

CI 가 `main`/`func`/`dev` 에 push 될 때 `bump --push` 를 대신 부른다
(.gitlab-ci.yml).

## 태그를 올리려면 토큰이 필요하다

CI 기본 토큰(`CI_JOB_TOKEN`)은 저장소에 push 할 수 없다. 프로젝트 Access Token
(Role `Maintainer`, scope `api`)을 만들어 CI/CD 변수 `AXMAP_BOT_TOKEN`
(**Masked + Protected**)에 넣는다.

없으면 `version` 잡은 **조용히 건너뛰지 않고** 다음 버전을 계산해서 알리고 끝난다.
버전이 안 올라간 것을 아무도 모르는 상태가 제일 나쁘다.

## 읽을 수 없는 태그를 만나면

`v1.2` 나 `vNext` 같은 것은 **버전으로 치지 않고 건너뛴다.** `v` 로 시작하는 아무
태그나 붙을 수 있고, 그것 때문에 릴리스 전체를 멈추는 것은 과하다.

다만 "읽었는데 형식이 틀린 것"을 `0.0.0` 으로 떨어뜨리지는 **않는다.** 0 에서 다시
시작하면 이미 나간 번호를 다시 발급하게 되고, 그 순간부터 같은 번호가 서로 다른
코드를 가리킨다. 이 저장소가 락에서 지킨 원칙과 같다 — 애매하면 치환하지 않는다.
