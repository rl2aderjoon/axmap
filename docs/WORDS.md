# 어휘 — 전공자와 비전공자가 같은 화면을 읽게 한다

이 제품의 목표 사용자에는 **프로그래밍을 배운 적 없는 사람**이 들어 있다.
그런데 지금 화면의 말은 전부 전공자 어휘다. 이 문서가 그 간극을 다루는 규칙이다.

🔴 **여기에 단어 대응표를 적지 않는다.** 목록은 `app/web/words.js` 에 산다.
손으로 적은 목록은 화면보다 먼저 낡고, 낡은 목록은 없는 것보다 나쁘다
(CLAUDE.md §0.5). 이 문서에는 **원칙과 판정 규칙만** 둔다.

---

## 🔴 먼저 — 어휘도 재서 정한다

이 저장소는 눈으로 고른 상수를 없애는 데 공을 들였다. γ 도 `coWeight` 도
임계값도 전부 측정으로 정했다. **어휘만 예외일 이유가 없다.**

> **판정 규칙 — 비전공자 벤치에서 그 말 때문에 막힌 기록이 있을 때만 바꾼다.**
> 기록이 없으면 안 바꾼다. "어려워 보인다" 는 근거가 아니다.

근거는 `docs/BENCH.md` 의 회차 보고에 있는 **막힌 지점** 항목이다.
그 프롬프트는 이미 *(a) 무엇을 하려 했나 (b) 화면이 무엇을 했나 (c) 완전히 막혔나*
를 받아 적게 되어 있다. 어휘 판정에 필요한 것이 그대로 들어 있다.

⚠️ 그리고 **말을 바꾸면 회차 비교가 깨진다.** 도구가 좋아져서 나아진 것인지
말이 쉬워져서인지 구분되지 않는다. 그래서 어휘 변경은 회차 사이에 한 번에 몰아서
하고, 무엇을 바꿨는지 그 회차 기록에 적는다.

---

## 원칙 A · 이름이 아니라 문장으로 말한다

```
❌  진입점: main.py
✅  여기서 프로그램이 시작합니다 — main.py
```

용어를 쓰지 말라는 것이 아니다. **용어를 몰라도 문장이 성립하게** 쓰라는 것이다.
전공자는 어차피 어느 쪽이든 읽는다. 잃는 쪽이 없다.

## 원칙 B · 전문 용어는 지우지 말고 괄호로 뒤에 붙인다

```
✅  여기서 프로그램이 시작합니다 (진입점)
```

비전공자는 앞부분만 읽고 넘어가고, 익숙해지면 자연히 뒤를 쓰게 된다.
**어휘를 뺏지 않고 가르친다** — D14 2단계가 정한 *"흐름을 따라가다 보면
어느샌가 이해하게 된다"* 와 같은 방식이다.

지우면 안 되는 이유가 하나 더 있다. 사용자가 그 말을 **AI 에게 옮겨 적는다.**
"진입점" 을 화면에서 지우면 사용자는 AI 에게 물어볼 말을 잃는다.

## 원칙 C · 코드 어휘는 바꾸지 않는다

```
코드   entryCandidates · edges · cochange · membership · resolution
화면   사용자가 읽는 문자열                                  ← 여기만 바꾼다
```

바꾸면 논문·`docs/SPEC.md`·API 응답과의 대응이 끊기고 개발이 느려진다.
그리고 얻는 것이 없다 — **사용자는 코드 이름을 안 본다.**

## 원칙 D · 치환해서 구별을 없애지 않는다

CLAUDE.md 가 락 시스템에 대해 적은 것이 어휘에도 그대로 적용된다.

> **"치환은 서로 다른 두 입력을 같은 것으로 만든다."**

"결합" · "의존" · "참조" 를 전부 "연결" 로 바꾸면 셋의 구별이 사라진다.
쉬운 말을 찾다가 **다른 것을 같게 만들면 그건 개선이 아니라 정보 손실**이다.
그럴 때는 낱말을 바꾸지 말고 **문장을 늘린다**(원칙 A).

## 어디를 고치나

| | |
|---|---|
| `app/web/words.js` | 화면 문자열 전부. **여기만 고친다** |
| `app/web/stage.js` | 그리기. 문자열을 직접 쓰지 않고 `W` 를 참조한다 |
| `docs/BENCH.md` | 막힌 지점 기록 — 어휘 변경의 유일한 근거 |

`words.js` 에서 `🟡` 가 붙은 항목이 **전공자 어휘라 벤치 1순위 후보**다.
표시는 문자열 바로 옆에 둔다. 다른 곳에 목록으로 적으면 그 목록이 먼저 낡는다.

새 문자열을 화면에 내보낼 때는 `words.js` 를 거친다. 여기를 안 거치면 다음 사람이
어휘를 실험할 때 그 문장만 빠지고, **빠진 줄 모른 채** 결과를 읽게 된다.

## 아직 정하지 못한 것

| | 질문 |
|---|---|
| W1 | 비전공자와 전공자가 **같은 화면**을 보나, 모드를 나누나 |
| W2 | 원칙 B 의 괄호가 화면을 얼마나 길게 만드나 — 카드 폭이 같아야 한다는 `stage.js` 규율과 부딪힐 수 있다 |
| W3 | 영어 화면을 만들 때 이 구조가 그대로 가나 (`W` 를 언어별로 나누나) |

W1 이 제일 크다. 모드를 나누면 **두 화면을 다 재야 하고** 벤치 비용이 두 배가 된다.
나누지 않는 쪽을 기본으로 두고, 벤치가 "한 화면으로는 안 된다" 고 말할 때만 나눈다.
