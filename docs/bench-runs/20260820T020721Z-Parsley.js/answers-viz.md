이름상 검증(validator/constraint/field/form) 과 관련돼 보인다. 또 `07-watch.png` 에서 jihun 이 잡고 있는
작업 설명이 정확히 "필드 검증 순서 - 비동기 검증이 순서를 어기던 것"이고 대상 파일이
`parsley/field.js`, `parsley/form.js` 였다 — 이것도 "폼 검증"과 맞닿아 있다는 강한 정황이지만,
화면이 "이 기능 = 폼 검증"이라고 못 박아준 적은 없다.

## 마지막 정리

### 1. 이미지 읽은 횟수 합계 · "못 함" 목록

- **실제 Read 도구 호출**: 4회 (한 번에 1~2장씩 배치로 열었음)
- **열어본 개별 이미지 파일**: 7개 전부 (01~07), 각 1회씩, 재조회 없음
- **질문별 "도구 호출 수"의 합**(중복 참조 포함): 2+2+2+3+2+1+1 = **13**
- **"못 함" 목록**:
  - M4: "폼 검증" 이라는 이름의 기능 점 자체는 화면에 없었음 (파일명 추정만 가능)
  - M5: `05-flow4.png` 가 말한 "건드리면 같이 깨지는 파일 1개"의 실제 이름은 화면에 안 나옴 (src/parsley.js 로 추정만)
  - M6: "선언 밖 수정 1개"의 대상 파일명은 화면에 안 나옴

### 2. 점의 위치·크기·색·연결선 자체가 알려준 것 (글자를 안 읽고도)

이번 7장은 대부분 "사다리"(계층 목록) + 왼쪽 설명 패널이었고, 실제 노드-엣지 그래프 캔버스
("그래프" 뷰)는 캡처에 없었다. 그래도 순수 시각 요소로 알 수 있었던 것들:

- `01-first.png` "무엇으로 이뤄져 있나"의 가로 막대 길이만 봐도 bower_components ≈ src >> test > 나머지,
  즉 숫자를 안 읽어도 이 저장소의 대부분이 (외부 의존성 + 본체 소스) 둘로 쏠려 있고 나머지는 작다는 것을
  막대 길이 비율로 바로 느낄 수 있었다.
- 상단 통계 4칸(둘 다/숨은 결합/안정된 경계/판정 보류)의 색이 파랑·빨강·파랑·회색으로 구분돼 있어,
  숫자를 안 읽어도 "빨강 = 위험/결합" 계열이라는 것과 그 칸이 비어있다(0)는 인상을 색만으로 받았다.
- `07-watch.png` 범례의 모양(꽉 찬 점 vs 테두리만) 차이로 "고치는 중" 과 "잡아만 둠"이 구분된다는 것,
  바깥 테두리(링)가 있으면 "지금 선택된 것"이라는 것은 도형 자체의 규칙이라 글자 없이도 유추 가능했다.
- 실제 파일/기능을 나타내는 점의 크기·위치·연결선(그래프 캔버스)은 이번 캡처들에 없었기 때문에,
  "이 파일이 크다/중심이다"는 시각적으로는 못 봤고 전부 문장으로 읽었다 (아래 3번 참고).

### 3. 글자(왼쪽 패널 문장·숫자)를 읽어서 안 것

- 이 저장소가 `parsleyjs`(폼 검증 라이브러리)라는 것 (README 인용문)
- 진입점이 `src/parsley/main.js` 라는 것 (import 9, "관례적인 파일명" 라벨)
- 저장소 중심(허브) 파일이 `src/parsley.js`이고 그걸 부르는 파일이 81개라는 구체적 수치
- 예제·테스트를 뺀 코드 211개 중 진입점에서 닿는 게 31개(15%)뿐이라는 것, 정적 파싱이 못 보는
  연결(동적 로딩 등)이 있을 수 있다는 경고
- 지금 field.js/form.js 를 jihun 이, ui.js 를 minseo 가 잡고 있고 각각 남은 시간이 29분이라는 것,
  그리고 각자의 작업 의도 문장
- "히스토리 부족 — 커밋 0개"라서 공변경(숨은 결합) 판정 자체가 이번 화면에서는 사실상 비활성 상태였다는 것
- 기능 탭에서 229개 파일 중 201개만 기능으로 묶였고 28개는 예제/테스트/미분류라는 것

### 4. 그림이 아예 없고 왼쪽 글자만 있었어도 똑같이 답할 수 있었을 질문은 몇 개인가?

**7개 중 7개** (사실상 전부). 이 7장의 캡처는 실질적으로 "왼쪽 설명 패널 문장 + 오른쪽 텍스트 목록"
조합이었고, 답을 만든 핵심 근거는 거의 전부 문장(따옴표 인용, 경고 문구, 수치)이었다. 오른쪽의 계층
목록도 결국 파일명·줄 수·"몇 겹"이라는 텍스트였지, 크기/색으로 인코딩된 노드 그래프가 아니었다.
막대 길이(1번 질문 보조 근거)와 claim 범례 도형(6·7번 질문 보조 근거) 정도가 "그림만으로" 거들었을
뿐, 그것들 없이 글자만으로도 M1·M6·M7 은 그대로 답할 수 있었을 것이다. 즉 이번 세트는 시각화라기보다
"글로 잘 정리된 안내문 + 목록"에 가까웠다.

### 5. 화면이 헷갈리게 한 것 · 보고 싶었는데 없었던 것

- **"그래프" 뷰 자체가 없었다.** 상단에 `사다리 | 그래프` 토글이 보였는데 7장 모두 "사다리"(계층
  목록) 상태로만 캡처돼 있어서, 정작 이 벤치마크가 묻는 "점의 위치·크기·색·연결선"을 볼 재료가
  부족했다. 실제 노드-엣지 시각화를 한 번은 보고 싶었다.
- **M3/M4에서 "덩어리"와 "기능"의 정의가 화면마다 달랐다.** 폴더 크기 기준 3덩어리(bower_components/
  src/test)와 기능 탭의 3개 그룹(bower_components/src/(최상위))이 서로 다른 답을 줘서, 어느 쪽이
  "진짜 기능 축"인지 헷갈렸다. "폼 검증" 같은 세부 기능 이름은 이 확대 수준에서는 아예 안 보였고,
  더 안으로 들어가는(예: src 를 펼치는) 화면이 있었다면 M4 를 훨씬 확실하게 답할 수 있었을 것 같다.
- **`05-flow4.png` 가 "위험한 파일이 하나 있다"고 결론만 던지고 이름을 안 보여준 것**이 가장 아쉬웠다.
  바로 다음 화면에 그 파일 하나를 강조한 그래프나 카드가 있었다면 M5 를 추정이 아니라 확답으로
  줄 수 있었다.
- **"선언 밖 수정 1개 / 파일 0" 표기가 모순처럼 보였다.** 상단 요약 숫자(1개)와 괄호 안 "파일 0"이
  같이 붙어 있어서 이게 카운트 오류인지, 아니면 "0개 파일에 대한 것"이라는 다른 의미인지 텍스트만
  으로는 확정할 수 없었다.
