# blastmap 시각 화면만 보고 답하기 — alluxio 저장소

신입 개발자 관점. PNG 7장만 봤고, API·소스코드·blastmap 코드는 보지 않았다.

---

## M1. 이 저장소는 무엇을 하는 물건인가

**답:** Alluxio Open Source (예전 이름 Tachyon). 대규모 데이터를 위한 분산 캐싱 플랫폼이다.
연산 프레임워크(computation frameworks)와 저장 시스템(storage systems) 사이의 간극을 이어주며,
연산 애플리케이션이 여러 저장 시스템에 공통 인터페이스로 접속할 수 있게 한다.

**근거:** `02-흐름1-무엇을하는물건.png` (=`01-first.png`와 동일 화면), 좌측 "① 이 저장소는 무엇을 하는 물건인가" 카드 안
`alluxio-parent` README 발췌문: "Alluxio Open Source (formerly known as Tachyon) is a Distributed
Caching Platform for large-scale data. It bridges the gap between computation frameworks and
storage systems, enabling computation applications to connect to numerous storage systems through
a common interface."

- 도구 호출 수: 1

## M2. 실행은 어디서 시작하나 — 파일 하나

**답:** `integration/kubernetes/operator/alluxio/cmd/controller/main.go`

**근거:** 모든 화면 상단 "0겹 진입점 — 여기서 읽기 시작합니다 (8개)" 목록의 맨 첫 줄. 143줄짜리
`main.go`이고, `03-흐름2-진입점.png` 좌측 패널에 "func main() (package main) · 관례적인 파일명 ·
아무도 import 하지 않는데 남을 import 한다 · Go 관례: cmd/<이름>/main.go" 로 이 파일을 콕 집어
설명한다. 단, 진입점은 이거 하나가 아니라 총 8개다 (Go main.go 2개, Java `main()` 1개
`RpcUtilsBench.java`, Python `if __name__ == '__main__'` 스크립트 4개 등). "실행이 어디서
시작하나"의 대표값으로 이 파일을 골랐다.

- 도구 호출 수: 2 (01, 03)

**답:** `core` (1,747개 파일), `tests` (254개), `integration` (221개) — 파일 수 기준 상위 3개.

**근거:** `01-first.png` / `02-흐름1-무엇을하는물건.png` 좌측 "무엇으로 이뤄져 있나" 막대그래프.

docs 113 > table 105 > stress 90 순.

보였는데, 이건 "덩어리 셋"이라기보다 core 내부의 하위 기능들이라 M3 답에는 포함하지 않았다.)

- 도구 호출 수: 1

## M4. "저장소(스토리지) 연결" 기능을 고치려면 어느 파일

**답 (부분적):** 정확히 파일 하나를 못 짚었다. 방향은 잡힌다 — `underFs` 카테고리
(134개 파일) 아래, 각 저장 시스템별 커넥터 디렉터리들이다: `underfs/s3a/...`,
`underfs/swift/...`, `underfs/hdf(s)/...`, `underfs/tos/...` 등. README 문구 자체가 "여러
저장 시스템에 공통 인터페이스로 연결"이라고 하니 이 UnderFileSystem 계열이 그 기능이 맞을
것이다. 다만 화면에 뜬 파일명이 전부 말줄임표(`…`)로 잘려 있어서 ("underfs/s3a/src/main…" 처럼)
열어야 할 **정확한 파일명 전체**는 못 읽었다.

**근거:** `01-first.png`/`02-...png` 좌측 구성 목록의 `underFs 134`; `05-흐름4-활발하고위험한곳.png`
"가장 자주 바뀌는 곳" 표의 `underfs/s3a/src/main…` (221회), `underfs/swift/src/ma…` (199회),
`underfs/hdf/src/mai…` (193회) 행들.

- 도구 호출 수: 2 (01, 05)

## M7. 내가 지금 어떤 파일을 고치면 누구와 부딪히나

**답:** 못 함. M6과 같은 이유 — 원격 장부(claim 기록)를 이 화면이 아예 못 읽는 상태라서,
특정 파일을 고쳤을 때 누구와 충돌하는지 판단할 근거 자체가 없다.

**근거:** `07-감시-누가무엇을.png` 동일 안내문. 범례에는 "선점됨/작업 중/선점 밖 수정"
세 가지 상태와 색이 정의돼 있어서 *만약* 장부가 있었다면 이 화면에서 답을 찾을 수
있었을 것 같다는 것은 알 수 있다. 하지만 지금 이 스크린샷에서는 그 장부 자체가 없다.

- 도구 호출 수: 1

## 마무리

**1. 이미지 읽은 횟수 합계:** 7 (7장 각각 1회씩 읽음, 재조회 없음)

**2. "못 함"으로 남긴 질문과 이유:**
- **M6, M7** — `07-감시-누가무엇을.png` 화면이 "원격 장부를 못 봤다 / 이 0은 실제 상태가
  아니라 못 읽었다는 뜻"이라고 명시적으로 경고하고 있어서, 지금 다른 사람이 무엇을 잡고
  있는지 그리고 내가 뭘 고치면 누구와 부딪히는지를 이 화면만으로는 판정할 근거가 없다.
- **M4는 절반만 답함** — 방향(underFs 계열 저장소 커넥터)은 잡았지만, 화면의 파일명이
  전부 말줄임표로 잘려 있어 열어야 할 정확한 전체 경로는 못 읽었다.

**3. 막혔던 자리:**
사이드바에 있는 단계 아이콘 ①~⑥ 중 ⑤, ⑥ 은 어느 스크린샷에서도 펼쳐진 내용이 안 보인다
(①~④만 `02~05.png`로 펼쳐진 걸 확인했다). 5번·6번 단계가 뭘 보여주는 화면인지 궁금했는데
그 내용이 화면에 없었다. 또 `04-흐름3-계층.png` 아래쪽 "main.go 에서 무엇이 불리나" 표에서
호출 대상 파일명들(`integration/kubernetes/operator/alluxio/cmd/con…` 등)이 잘려서 정확한
전체 경로를 못 봤다 — 이런 잘림이 M4·M5 답의 정밀도를 계속 깎아먹었다.

**4. 도움이 된 순간 / 방해가 된 순간:**
- 도움: `04-흐름3-계층.png`의 "중심은 추측이 아니라 관측입니다 — PropertyKey.java 를 부르는
  파일이 742개로 가장 많습니다" 문장. 숫자 근거가 바로 옆에 붙어 있어서 "왜 이 파일이
  중요한지"를 다시 찾아볼 필요 없이 그 자리에서 확신을 가지고 답할 수 있었다.
- 방해: 파일 경로가 목록 전반에서 `…`로 잘려 나오는 것 (예: `core/server/master/…`,
  `underfs/s3a/src/main…`). 어느 카테고리인지는 알겠는데 정확히 어떤 파일을 열어야 하는지
  끝내 못 알아내는 경우가 여러 번 있었다 (M4, M5의 보조 후보들).

**5. 글자 없이 그림만으로 알 수 있었던 것이 있었나:**
일부는 있었다. `01-first.png`/`02-...png`의 "무엇으로 이뤄져 있나" 막대그래프는 숫자를 안
읽어도 막대 길이만 보고 core가 압도적으로 크고 그다음이 tests, integration 순이라는
**상대적 크기 순서**는 그림만으로 파악할 수 있었다 (M3에 활용). `05-흐름4-활발하고위험한곳.png`의
빨간 배지들도 색(빨강=위험/변동 큼)이 줄줄이 붙어 있다는 사실 자체가 "이 구역 전체가
위험군"이라는 인상을 글자를 읽기 전에 먼저 줬다. 다만 이 둘을 빼면, **나머지 답(M1, M2, M4,
M5, M6, M7)은 거의 다 옆에 적힌 글자(README 인용문, "742개"라는 숫자, "장부를 못 봤다"는
경고 문장)를 읽어서 알았다** — 그래프·구조 자체보다는 문장이 결정적이었던 경우가 더 많았다.
