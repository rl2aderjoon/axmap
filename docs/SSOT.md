# 기준 (SSOT) — 코퍼스가 정하는 단일 진실

기본 주소는 `http://127.0.0.1:7902/baseline`이다. 로컬 기준 서버는 [COLLECT.md](COLLECT.md)의 절차로 실행하고, 다른 서버는 `AXMAP_SSOT_URL`로 지정한다. 기준을 받지 못하면 캐시나 기본값으로 돌아가며 그 이유를 표시한다.

---

## 무엇을 푸는가

우리 임계값은 전부 사람이 눈으로 고른 상수였다.

```
MIN_SUPPORT 3 · hubCap 6 · splitOver 300 · GO_PKG_CAP 12 · REL_FLOOR 0.25
```

`docs/DECISIONS.md` 의 Q2·Q5·Q6 이 **"눈으로 고른 값"** 이라고 적혀 있다.
저장소 하나로는 정할 수가 없기 때문이다. 코퍼스가 그 상수를 **분포**로 바꾼다.

---

## 🔴 넘지 않기로 한 선 넷

### 1. 인기 ≠ 좋음. 결과로 판정한다

별 많은 저장소를 긁어 "이렇게 하세요" 라고 하면 **생존 편향을 규범으로 만드는 것**이다.
그래서 예측 변수의 구간마다 **재수정률**을 따로 센다.

> 재수정률 = 그 파일을 건드린 커밋 중 고침·버그 커밋의 비율

`clips/pattern` 한 저장소만으로도 이미 신호가 보인다.

| 파일 길이 | 재수정률 |
|---|---|
| 10~20줄 | 0.125 |
| 100~150줄 | 0.108 |
| 300~400줄 | 0.167 |
| 800~1200줄 | **0.220** |

⚠️ 완벽하지 않다. `fix` 관습이 없는 저장소에서는 0에 몰린다. 그래서 저장소마다
`fixCommitRatio` 를 함께 기록해 관습 없는 저장소를 걸러낼 수 있게 했다.

**추세가 없으면(`flat`) 지침을 내지 않는다.** "남들은 이만큼 쓴다" 와
"그래서 나중에 더 고치게 된다" 는 다른 말이고, 뒤쪽만 지침이 될 수 있다.

### 2. 지침에는 적용 조건이 붙는다

```
❌  함수는 20줄을 넘기지 마세요
✅  커밋 1,500~6,000 · Python 저장소 34개 · 파일 12,400개에서 관찰
    (스냅샷 v418, 2026-08-19)
```

**적용 조건 없는 지침은 점성술이다.** 모든 집계는 `(언어, 규모)` 칸 안에서만 한다.
칸을 넘어 합치지 않는다 — 커밋 200개짜리 장난감과 커밋 5만 개짜리 커널을 같은
분포에 넣으면 그 분포는 누구에게도 맞지 않는다.

| 칸 | |
|---|---|
| `small` | 커밋 400~1,500 |
| `mid` | 커밋 1,500~6,000 |
| `large` | 커밋 6,000 이상 |

### 3. 표본이 모자라면 답하지 않는다

```
MIN_REPOS 15 · MIN_FILES 300
```

저장소 3개로 만든 분위수를 "업계 기준" 처럼 보여주면 그건 거짓말이고,
**한 번 거짓말한 지침은 그 다음부터 전부 무시당한다.**
못 쓰는 칸도 숨기지 않고 `usable: false` 와 이유를 함께 낸다.

### 4. 우리 자신의 커버리지를 함께 낸다

저장소 하나면 파서 구멍이 "엣지 몇 개 잃음" 으로 끝난다.
**코퍼스에서는 분포를 왜곡한다** — 우리가 잘 못 읽는 언어일수록 결합도가 낮게
나오고, 그러면 기준이 그 언어 팀에게 "당신들은 건강합니다" 라고 말한다.

실측으로 겪었다: syft(Go) 정적 엣지 1개, baritone(Java) 0개,
clips/pattern 내부 import 304개 중 48개(16%).

그래서 칸마다 `parseCoverage` 를 함께 싣는다.

## 구조

```
개발 PC 는 꺼져도 됨.  전부 AWS 에서 돈다.

  run-worker.sh (감시자)      죽으면 10초 뒤 되살린다. 22:00 UTC 에 멈춘다
    └ corpus/worker.mjs       고르기 → 클론 → 계측 → 기록 → 삭제 → 스냅샷
         ↓ 파일로만 오간다
      data/repos.jsonl        저장소별 레코드 (덧붙이기 전용)
      data/seen.txt           이미 본 것
      data/baseline.json      최신 스냅샷 (원자적 쓰기)
         ↑
  corpus/serve.mjs :7902  ──nginx /ssot/──▶  공개
```

- **학습 도중에도 답한다.** 저장소 하나를 잴 때마다 스냅샷을 다시 쓴다.
- **죽어도 이어서 한다.** 상태가 전부 파일에 있어 메모리에 없다.
- **원자적 쓰기.** 임시 파일에 쓰고 rename — 반쯤 쓰인 JSON 이 나가지 않는다.
- **클론은 재고 나서 즉시 지운다.** 안 지우면 디스크가 먼저 죽는다.
- `nice -n 15` — 이 서버에는 젠킨스와 게릿이 같이 산다. 남의 일을 밀어내지 않는다.

## 집계가 히스토그램인 이유

파일마다 값을 다 들고 있으면 메모리가 저장소 수에 비례해 늘고, 중간에 죽으면 다 잃는다.
고정 구간 히스토그램은 메모리가 O(1) 이고 **합치는 것이 덧셈**이라 부분 결과를
언제든 합쳐 스냅샷을 낼 수 있다.

⚠️ 대신 분위수가 근사값이다. 응답에 `approx: true` 를 붙여 숨기지 않는다.
열린 구간(마지막 칸)에서는 **바깥으로 외삽하지 않는다** — "10,000줄 이상" 을
12,345줄이라고 지어내지 않기 위해서다.

## 쓰는 법

```
GET /ssot/                 사람이 보는 화면
GET /ssot/status           지금까지 몇 개를 봤나, 어느 칸이 쓸 만한가
GET /ssot/baseline         스냅샷 전체 (기계용)
GET /ssot/ask?lang=python&commits=3000&lines=430&fanout=12
```

`ask` 의 답에는 **언제나** 이것이 함께 나간다.

| | |
|---|---|
| `n` | 몇 개 저장소·파일에서 나온 값인가 |
| `appliesTo` | 어느 언어·규모 칸인가 |
| `version` | 어느 스냅샷인가 |
| `parseCoverage` | 그 칸에서 우리 파서가 얼마나 보고 있나 |
| `outcome` | 이 축이 재수정률과 실제로 관계가 있는가 (`up`/`down`/`flat`) |

## 아직 안 한 것

- **문서(글) 축이 없다.** 지금은 코드만 본다. `datanodes.mjs` 가 `.md` 를 노드로
  올리므로 "문서가 코드와 함께 안 바뀌면 낡은 것" 은 지금 재료로 낼 수 있다 (D3 의 확장).
- **떼어놓고 검증(held-out)** 하지 않았다. 기준의 예측이 맞았는지 채점하는 고리가 없다.
  이것이 있어야 기준이 "관찰" 에서 "검증된 지침" 이 된다.
- 커밋 관습(`fix` 를 쓰는가)으로 저장소를 거르는 것을 **기록만 하고 아직 적용하지 않았다.**
- 재수정률 말고 다른 결과 신호(revert 비율, 도입 후 재작성량)를 아직 안 센다.

## 파서를 늘리면 코퍼스가 그것을 알아야 한다

`PARSER_VERSION` 이 레코드마다 찍힌다(`corpus/measure.mjs`). 집계는 **같은
도장끼리만** 커버리지를 평균 낸다(`corpus/stats.mjs` `coverageOf`).

그렇게 안 하면 새 파서가 헛일이 된다 — `parseCoverage` 는 레코드 수만 개의
평균이라 새 것 몇백 개로는 안 움직이고, 결합 판정 게이트가 영원히 안 열린다.
옛 기록은 *"그때 우리가 파서가 없었다"* 를 말하는데 화면은 그것을
*"이 언어는 결합을 볼 수 없다"* 로 읽는다.

지금 파서로 잰 저장소가 칸마다 15개를 넘기 전까지는 응답이 그렇게 말한다:

```json
"coverage": { "from": "mixed", "repos": 4, "needs": 15, "parser": "c,cpp,go,..." }
```

**파서를 늘린 날에는 코퍼스를 다시 재야 한다.** 안 그러면 저장소에만 있고
통계에는 없다.
