# axMap 선점 프로토콜 규격 v0

여러 AI 에이전트가 한 저장소에서 병렬로 작업할 때,
**작업을 시작하기 전에** 겹침을 확정적으로 감지하기 위한 프로토콜.

이름의 뜻. **axMap 은 AI Experience(ax) 의 지도다** — 에이전트가 코드베이스에서
길을 찾고 서로를 피해 가는 경험을 만든다. 동시에 개발 환경의 AI Transformation,
즉 사람 혼자 쓰던 저장소를 여러 에이전트가 함께 쓰는 곳으로 바꾸는 일을 함의한다.

> 산문에서는 `axMap`, 식별자·명령·경로에서는 `axmap` 을 쓴다.

설계 근거는 [EXPERIMENT.md](EXPERIMENT.md) 에 있다.

## 1. 두 관문

```
  에이전트가 작업을 시작하려 한다
             │
             ▼
  ┌──────────────────────────────────────────────┐
  │ 관문 1 · 직렬화                               │
  │   git push 의 ref CAS                        │
  │   "내가 받아간 뒤 ref 가 움직였나?"            │
  │   → 거부되면 실패가 아니라 재시도 신호         │
  │   → 끌 수 없다. push 하면 항상 작동한다        │
  └──────────────────────────────────────────────┘
             │
             ▼
  ┌──────────────────────────────────────────────┐
  │ 관문 2 · 판정                                 │
  │   checkOverlap()                             │
  │   "요청 경로가 남이 잡은 경로와 겹치나?"        │
  │   → 거부되면 진짜 거절. 이유를 함께 준다        │
  └──────────────────────────────────────────────┘
```

두 관문은 대안이 아니라 서로 다른 층이다.
관문 1 은 "누가 먼저 썼는가"를, 관문 2 는 "그래서 겹치는가"를 답한다.

## 2. 저장 위치

| 항목 | 값 |
|---|---|
| 장부 브랜치 | `axmap/claims` (부모 없는 고아 브랜치) |
| 로컬 worktree | `<메인 체크아웃>/.axmap/ledger` — **저장소에 하나뿐** (바로 아래) |
| claim 파일 | `<worktree>/claims/<agent>.json` — 에이전트당 정확히 하나 |
| 쪽지함 브랜치 | `axmap/bus` (부모 없는 고아 브랜치) |
| 쪽지함 worktree | `<repo>/.axmap/bus` |
| 쪽지 파일 | `<worktree>/messages/<시각>-<보낸이>-<제목slug>.md` — 하나당 파일 하나 |
| 읽음 표시 | `<repo>/.axmap-bus-seen.json` — **장부가 아니다.** 아래 참고 |

### 장부는 메인 체크아웃에 하나뿐이다 — 링크된 worktree 도 그것을 본다

**링크된 worktree** — `git worktree add` 로 만든, 같은 저장소의 다른 브랜치를 옆 폴더로
펼쳐 둔 것. HEAD 와 인덱스는 폴더마다 따로지만, 오브젝트·refs·**훅**은 저장소에 하나뿐이다
(그 하나가 있는 곳이 **공통 디렉터리** — `git rev-parse --git-common-dir`).

그래서 장부를 찾을 때는 `git rev-parse --show-toplevel`(지금 서 있는 worktree)이 아니라
**공통 디렉터리의 부모**(메인 체크아웃)에서 `.axmap/ledger` 를 본다.

🔴 2026-08-28 실측. 이 규칙이 없던 동안 링크된 worktree 안에서 `git commit` 이
**전부** 막혔다. 훅은 공통이라 그대로 도는데 `.axmap/ledger` 는 메인 체크아웃에만 있어
`장부가 없습니다` 로 종료 코드 1 이 났다 — 선점과 아무 상관 없는 커밋까지.
그때 사람이 쓴 우회는 그 worktree 안에 장부 worktree 를 하나 더 만드는 것이었다.
돌아가긴 하지만 **장부가 worktree 수만큼 늘고**, 하나가 뒤처지면 같은 저장소에 진실이
둘이 된다. 락 시스템에서 진실이 둘이면 락이 아니다.

**1.3.0부터 장부가 없으면 자동으로 준비한다.** 기존 원격 장부를 재사용하고 원격에 없다고 확인된 경우에만 새 고아 브랜치를 만든다. 원격 접근 실패와 원격 선택 모호성은 오류다. 원격이 없는 repo는 경고와 함께 로컬 모드로 동작한다. 자동 준비 후에도 staged 파일이 선점 범위 밖이면 커밋을 거부한다.

초기화는 Git 공통 디렉터리의 `axmap-init.lock`으로 직렬화하고 잠금 안에서 장부 존재를 다시 검사한다. 정상·오류 종료 시 잠금을 반납하며 강제 종료로 남은 잠금은 자동으로 빼앗지 않는다. 준비 로그는 stderr, `status --json` 결과는 stdout으로 분리한다. `.git/info/exclude`에 `.axmap/`을 등록하므로 코드 브랜치의 파일은 수정하지 않는다.

MCP 타겟은 `AXMAP_REPO` → 도구의 절대 경로 `cwd` → 클라이언트 roots → 시작 repo 순이다. 전역 앱 타겟으로 다른 세션을 전환하지 않는다. roots 변경을 받으면 갱신을 기다린 뒤 전환하며 이전 repo의 해당 세션 claim만 반납한다. roots를 읽지 못하거나 여러 repo 중 하나로 고를 수 없으면 요청을 중단한다. 상세 근거는 [D22](DECISIONS.md#d22--작업-repo를-세션별로-따라가고-장부를-자동-준비한다).

공통 디렉터리의 이름이 `.git` 이 아닌 배치(bare 저장소의 worktree, `--git-dir` 을 손으로
준 경우)에서는 부모를 짚지 않고 `--show-toplevel` 을 그대로 쓴다. 그 부모는 저장소 바깥이다.

**1.3.2부터 쪽지함(`.axmap/bus`)과 사용자 정보(`.axmap/users`)도 같은 메인 체크아웃에서 공유한다.** repo별 Git 이메일은 실제 실행 worktree에서 읽으며, 이전 worktree의 로컬 읽음 파일은 호환용으로 함께 읽는다.

### 쪽지 표시 이름과 참여 프로필 (1.3.2)

`setup`은 대화형 이름 입력 또는 `--name`으로 `{version:1,name,updatedAt}`을 `~/.axmap/profile.json`에 저장한다. 수정 시각은 이름을 설정한 시점이며, 이전 PC가 나중에 활동했다는 이유로 더 최근의 이름 수정을 되돌리지 않는다. 비대화형 실행은 기존 프로필·Git·OS 이름을 사용한다. 이메일은 저장하지 않으며 실제 repo의 Git 이메일(명시적 `AXMAP_AGENT_EMAIL` 우선)을 사용한다. 이 이름은 선점 주체 이름을 바꾸지 않는다.

해당 repo에서 첫 협업 명령을 성공적으로 사용하거나 쪽지 명령을 사용하면 `axmap/users`의 `users/<email>.json`에 프로필을 자동 commit·push한다. 기존 `seen`과 별칭은 유지한다. `setup`만으로 임의의 repo에 공유하지 않는다. 공유 실패는 경고하며 협업 명령은 계속하고, 다음 사용 때 재시도한다. 변경 없는 성공 프로필의 원격 확인과 사용자 목록 동기화는 최대 60초 간격이다. 원격이 없으면 로컬 상태임을 알린다.

`axmap bus contacts`는 알려진 표시 이름·이메일을 나열한다. 같은 이름에 여러 이메일이 있으면 전송 시 명시적 이메일을 요구한다. 알려진 이름은 쪽지의 `to`에 이메일로 저장하고 `from`은 표시 이름, `fromEmail`은 이메일을 저장한다. 답장은 `fromEmail`을 우선한다. MCP 개인 쪽지·알림은 이름 하나 대신 `--mine`의 이메일·별칭 집합으로 조회한다. 투표권자 명단·승인 정책에는 영향이 없다.

사용자 브랜치는 `axmap-users.lock`으로 직렬화한다. fetch 후 fast-forward 또는 사용자 JSON 병합으로 미게시 프로필·읽음 정보를 보존한다. 동시 push 거부는 최신 브랜치 위에서 재시도한다. JSON 병합은 별칭을 합치고, 더 나아간 읽음 시각과 최신 프로필 이름을 유지한다.

### 읽음 표시 — 목록에 뜬 순간 읽은 것으로 친다

```
.axmap-bus-seen.json     { "<agent>": "<가장 최근에 보여준 쪽지 id>" }
안 읽음 판정              id > seen[me]
```

id 가 시각으로 시작하므로 문자열 비교가 곧 시간 비교다. 고수위 하나면 되고,
읽은 id 목록을 들고 있을 필요가 없다.

🔴 **표시를 찍는 시점은 "목록을 보여준 순간"이다.** 본문(`read`)까지 열어야
읽음으로 치면, 알림은 **모든 쪽지를 열 때까지 계속 뜬다.** 알림의 일은 제목을
한 번 보여주는 것이고 본문은 `read` 가 한다 — 둘을 한 판정에 묶으면 알림이
잔소리가 되고, 잔소리가 된 알림은 읽히지 않는다.

⚠️ 대가를 적어 둔다 — **제목만 보고 넘기면 그 쪽지는 다시 안 뜬다.** 파일은
그대로 있으므로 `list --all` 로 언제든 다시 본다. 안 뜨는 것과 사라지는 것은 다르다.

#### 🔴 그린 쪽이, 그린 것만 찍는다

"보여준 순간" 은 **목록을 만든 순간이 아니라 화면에 나간 순간**이다. 둘이 갈리는
자리가 하나 있다 — **목록을 잘라서 보여주는 쪽**이다. MCP 알림 배너는 받은 줄 중
앞의 3건만 그리고 나머지는 `… 그 밖에 N건` 으로 접는다. 접힌 것까지 읽음으로 찍으면
그 쪽지들은 **화면에 뜬 적도 없이** 다시 안 뜬다. 오류도 로그도 없이 사라진다.

그래서 찍는 일을 목록에서 떼어냈다.

| 부르는 쪽 | 무엇을 쓰나 |
|---|---|
| 목록을 **그대로 다 내보내는** 쪽 (사람이 부른 `list`, `ax_inbox`) | `list --unread` — 낸 것 전부가 읽음이 된다 |
| 목록을 **잘라서 보여주는** 쪽 (MCP 배너) | `list --unread --no-mark` 로 읽기만 하고, 그린 id 만 `seen <id>…` 에 넘긴다 |

```
bus list --to <나> --unread --no-mark     안 읽은 것만 낸다. 찍지 않는다
bus seen <아이디> [<아이디>…]              이것들만 읽음으로 찍는다 (가장 큰 것이 고수위)
```

`seen` 은 `pull()` 을 하지 않는다. 로컬 파일 하나를 쓸 뿐이라 원격을 물을 이유가
없고, 알림을 그릴 때마다 fetch 가 돌면 배너가 도구를 느리게 만든다.

⚠️ **`--all` 로 낸 목록으로는 찍지 않는다.** 남에게 간 쪽지가 섞여 있어서 그중 가장
큰 id 로 찍으면 나에게 온 안 읽은 쪽지가 그 아래에 묻힌다.

이 규칙이 성립하는 전제는 **목록이 id 오름차순**이라는 것이다(`readAll` 이 정렬한다).
앞에서부터 자르므로 접힌 것은 언제나 그린 것보다 id 가 크고, 따라서 고수위에
걸리지 않는다. 정렬이 사라지면 이 규칙도 같이 깨진다.

🔴 **읽음은 장부에 넣지 않는다.** 내가 읽었는지는 **나만의 상태**라 남과 합의할
필요가 없고, 장부에 쓰면 쪽지를 볼 때마다 push 경합이 생긴다. 그래서 이 파일은
고아 브랜치가 아니라 작업 트리 루트에 있고 `.gitignore` 에 올라가 있다.

⚠️ 쓰기는 **조용히 실패한다.** 못 찍으면 다음에 같은 쪽지가 한 번 더 뜰 뿐이고,
그건 손해가 아니다. 반대로 여기서 죽으면 쪽지를 보려다 명령이 통째로 죽는다.

### 쪽지함 — 장부와 같은 자리, 반대의 실패 규칙

쪽지는 원래 `docs/bus/` 에 있었다. 그건 작업 트리라서 상대에게 가려면
커밋 → MR → 머지 → 상대가 pull 을 거쳤고, 기본 브랜치가 보호돼 있으면
**쪽지 한 통이 MR 한 사이클**이다. 게다가 보내려면 `docs/bus` 를 claim 해야 해서
한 사람이 잡고 있는 동안 나머지는 쪽지를 못 보냈다 — 통로가 자물쇠였다.
고아 브랜치로 옮기면 셋 다 사라진다.

🔴 **그러나 push 실패의 뜻이 장부와 정반대다.** claim 은 push 가 실패하면
멈춰야 한다 — 로컬에만 남은 락은 나만 보이고 남은 같은 파일을 잡으므로
실패를 삼키는 것이 곧 fail-open 이다(§6). 쪽지는 반대다. 안 간 쪽지는
**아직 안 간 것**일 뿐 아무 판정에도 쓰이지 않는다. 그래서 쪽지함의 fetch·push
실패는 경고에 그치고 사람의 작업을 막지 않는다.

한 가지만 fail-closed 다 — **쪽지함이 준비되지 않았으면 쓰지 않고 거부한다.**
준비 전에 쓰면 `.axmap/bus/messages` 가 worktree 아닌 맨 폴더로 생기고, 그러면
나중에 `init` 이 "정상적인 쪽지함이 아닙니다, 지우세요" 라고 안내한다 —
**안 간 쪽지를 지우라고 시키는 것**이 된다.

옛 쪽지함 `docs/bus/` 는 **읽기만** 한다. 옮기지 않는다 — 옮기면 같은 내용이
두 브랜치에 남고 어느 쪽이 진짜인지 아무도 모른다. 새것은 전부 고아 브랜치로
가므로 옛것은 자연히 마른다.

⚠️ **고아 브랜치는 저장소 루트의 `.gitattributes` 가 닿지 않는다.** 그래서 그
브랜치 안에 따로 하나 둔다. 없으면 Windows 에서 CRLF 로 체크아웃되고, 쪽지
머리말 파서가 `\r` 에 걸려 **쪽지가 목록에서 조용히 사라진다.** 2026-08-26 에
실제로 그랬다. 파서도 줄바꿈에 무관하게 고쳤다 — 데이터 포맷이 체크아웃 설정에
의존하면 그 설정이 안 닿는 자리마다 같은 사고가 난다.

### 어느 원격에 두는가 — 이름을 가정하지 않는다

장부를 주고받을 원격의 **이름**은 아래 순서로 정한다. 위에서부터 먼저 맞는 것을 쓴다.

| | 출처 | 범위 |
|---|---|---|
| 1 | `--remote <이름>` | 그 명령에서만 |
| 2 | `AXMAP_REMOTE` | 셸 단위 |
| 3 | `git config axmap.remote` | 저장소에 박힌 값 — `init` 이 여기에 적는다 |
| 4 | 원격이 **정확히 하나**면 그것 | 이름이 무엇이든 |
| 5 | `origin` 이 있으면 `origin` | 옛 동작과의 호환 |
| 6 | 그 밖 | **고르지 않는다.** `init` 이 후보를 나열하고 종료 코드 1 |

**6에서 하나를 골라 주지 않는다.** §3 "입력 검증"의 원칙 그대로다 — 치환은 서로 다른
두 입력을 같은 것으로 만들고, 락에서 그것은 곧 소유권 충돌이다. 잘못 고르면 장부가
엉뚱한 저장소로 가는데, **그 실패에는 증상이 없다.** push 는 성공하고 팀은 서로의
claim 을 영영 못 본다.

**추론한 결과는 `init` 이 `git config axmap.remote` 에 못 박는다.** 이후 명령이 매번
다시 추론하면 원격이 추가되거나 이름이 바뀔 때 판정이 조용히 달라진다 — 어제는 팀
저장소로 가던 장부가 오늘은 개인 저장소로 간다. 정하는 것은 한 번이다.

지정한 이름이 실제로 없으면 **거부한다(코드 1).** 오타를 조용히 넘기면 그 순간부터
무보호 상태이고, 그것을 알려주는 신호가 하나도 없다.

**원격이 없으면 거부하지 않고 경고한다.** 혼자 쓰는 사용자가 실제로 있기 때문이다.
다만 `init` 때 한 번이 아니라 **claim 마다**(프로세스당 한 번) stderr 로 낸다.
경고가 한 번뿐이면 그 뒤 수백 번의 claim 이 전부 조용히 성공하고, 사람은 보호받고
있다고 믿는다. 관문 1이 없는 상태에서 claim 성공은 "겹치지 않는다"가 아니라
**"남을 볼 수 없다"** 는 뜻이다.

**고아 브랜치인 이유.** 장부는 코드와 수명이 완전히 다르다.
초 단위로 갱신되며 코드 이력에 남을 이유가 없고, 코드를 push 하지 않고도 장부만 push 할 수 있어야 한다.

**worktree 인 이유.** 브랜치를 오가지 않고 장부를 읽고 쓰기 위해서다.
에이전트는 작업 브랜치에 그대로 머문 채 `.axmap/ledger` 를 통해 장부를 다룬다.

**에이전트당 파일 하나인 이유.** 두 에이전트가 같은 줄을 쓸 일 자체를 없앤다.
텍스트 충돌은 구조적으로 발생하지 않으며, 겹침은 오직 관문 2 가 판정한다.

**레코드를 원자적으로 쓰는 이유.** 관문 1 이 CAS 인 이상 원자성은 선택이 아니다.
레코드는 임시 파일에 다 쓴 뒤 같은 디렉터리에서 `rename` 한다.

`writeFileSync` 는 호출 하나로 보이지만 커널이 여러 번에 나눠 쓸 수 있다.
그 사이 다른 에이전트의 `git add -A` 가 worktree 를 통째로 스테이징하면
**반쯤 쓰인 레코드가 그대로 커밋된다.** 그리고 파싱 실패는 건너뛰지 않고 전체를
중단하므로(§6 fail-closed), 그 순간 팀 전원의 장부가 함께 멈춘다.
창은 좁지만 터지면 범위가 전부다.

같은 디렉터리 안의 `rename` 은 같은 파일시스템이라 원자적이다.
보는 쪽은 옛 파일이나 새 파일만 보고, 반쯤 쓰인 상태는 존재할 수 없다.

임시 이름은 `<agent>.json.tmp-<pid>` 로 **`.json` 으로 끝나지 않는다.**
레코드를 읽을 때 `.json` 만 보므로, rename 직전에 누가 임시 파일을 집어가도
최악이 "깨진 레코드"가 아니라 "무해한 쓰레기 파일"이 된다.
막지 못하는 창에서는 실패의 크기라도 낮춘다.

worktree 에 `.gitignore`(`*.tmp-*`)를 함께 두어 임시 파일이 아예 스테이징되지
않게 한다. 프로세스가 강제 종료되어 임시 파일이 남는 경우까지 이것으로 덮인다.

`.axmap/` 은 `axmap init` 이 `.gitignore` 에 자동으로 추가한다.

`claims/.gitkeep` 을 함께 만든다. git 은 빈 디렉터리를 추적하지 않으므로,
모두가 반납해 claim 파일이 0개가 되면 `reset --hard` 가 `claims/` 자체를 지운다.
그러면 "정상적으로 다 반납한 상태"가 "장부가 없음"으로 오진된다.
같은 이유로 장부의 존재 여부는 `claims/` 가 아니라 **worktree 자체**로 판정한다.

## 3. claim 레코드

```json
{
  "agent":  "agent-a",
  "task":   "task-12",
  "intent": "토큰 검증 로직 리팩토링",
  "since":  "2026-08-15T09:00:00.000Z",
  "ttlMs":  1800000,
  "paths":  ["src/auth/login.ts", "src/auth/token.ts"]
}
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `agent` | ✓ | 고유 식별자. 파일명이 여기서 나온다 |
| `task` | | 티켓/작업 ID. 거부 메시지에 표시된다 |
| `intent` | | 사람이 읽는 한 줄 설명. `status` 에 표시된다 |
| `since` | ✓ | ISO 8601 UTC. `claim`/`renew` 시각 |
| `ttlMs` | ✓ | 유효 기간(ms). `since + ttlMs` 가 만료 시각 |
| `paths` | ✓ | 정규화된 경로 배열. 파일과 디렉터리 모두 가능 |

### `actor` — 누가 잡았나 (선택)

레코드에 `actor` 를 실을 수 있다. 화면에서 색을 나누는 데만 쓰이고 **판정에는 관여하지 않는다.**

| 값 | 뜻 |
|---|---|
| `human` | 사람 |
| `agent` | 대화형 AI |
| `background` | 백그라운드 에이전트 |
| `team` | 다른 팀원 |

`--actor <값>` 또는 환경변수 `AXMAP_ACTOR` 로 준다. 없으면 `null` 이다.

**목록에 없는 값은 거부한다(코드 1).** 색만 정하는 필드이므로 조용히 폴백하고 싶은
유혹이 있지만, 치환은 서로 다른 두 입력을 같은 것으로 만든다 — 이 문서가 아래
"입력 검증"에서 정한 원칙에 예외를 두지 않는다.

### 입력 검증

애매한 입력은 **조용히 정규화하지 않고 거부한다.**
정규화는 서로 다른 두 입력을 같은 것으로 만들 수 있고, 락 시스템에서 그것은 곧 소유권 충돌이다.

| 대상 | 규칙 | 거부하는 이유 |
|---|---|---|
| `agent` | `^[A-Za-z0-9][A-Za-z0-9._-]*$`, 64자 이하 | 이름이 그대로 파일명이 된다. `agent/a` 와 `agent_a` 를 둘 다 `agent_a.json` 으로 치환하면 서로의 claim 을 덮어쓴다 |
| `paths` | 절대 경로 금지 (`/…`, `C:…`) | 저장소 밖은 이 프로토콜의 관할이 아니다 |
| `paths` | `..` 세그먼트 금지 | 같은 위 |
| `paths` | 루트(`.`, `/`) 금지 | 저장소 전체를 잠그면 프로토콜의 의미가 없다 |

존재하지 않는 경로는 **경고만 하고 통과시킨다.** 아직 만들지 않은 파일을 미리 잡는 것은 정당하다.
다만 오타로 엉뚱한 경로를 잡으면 실제 수정이 pre-commit 에 막혀 혼란스러우므로 알린다.

### 에이전트 이름을 정하는 순서 — 기본값은 없다

CLI(`bin/axmap.mjs`)와 MCP 서버(`mcp/server.mjs`)가 **같은 순서**로 정한다.

| 순위 | 출처 |
|---|---|
| 1 | `--agent` (CLI 만) |
| 2 | `AXMAP_AGENT` |
| 3 | `git config user.name` |
| 4 | 전부 없으면 **die** |

🔴 **안전한 기본 이름을 두지 않는다.** 이것이 이 절의 전부다.

예전 `.mcp.json` 은 이름이 없으면 모두에게 `claude` 를 줬다.
그 값이 저장소에 커밋되어 있으므로 clone 한 팀원 다섯 명이 **장부에서 한 명**이 된다.
`checkOverlap()` 은 자기 claim 을 겹침으로 보지 않으므로(관문 2 의 `c.agent === me` 분기),
다섯 명이 서로의 영역을 **아무 경고 없이** 덮어쓴다.

이것은 위 "입력 검증"이 금지한 바로 그 실패다 — *치환은 서로 다른 두 입력을 같은 것으로
만들고, 락 시스템에서 그것은 곧 소유권 충돌이다.* 이름이 없으면 조용히 채우지 않고 거부한다.
잘못 막으면 사람이 변수를 설정하면 그만이지만, 못 막으면 아무도 에러를 보지 못한다.

**옛 이름을 받아주는 자리는 어디에도 없다.** 한때 환경변수에만 한시적 호환을 두었지만
걷어냈다. 두 이름이 공존하면 같은 사람이 상황에 따라 다른 이름으로 장부에 남고,
그것이야말로 상호배제를 통째로 무너뜨린다. 호환을 오래 두면 그것이 규격이 된다.

### 세션 id — 이름이 같아도 주체가 다르면 갈라야 한다

**이름은 "누구인가" 이고 세션은 "어느 작업 주체인가" 다.** 한 사람이 동시에 두 주체일 수
있다 — 같은 PC 에서 AI 도구 세션을 두 개 띄우는 것이 정확히 그것이다.

🔴 2026-08-28 에 **두 번** 재현됐다. 세션 두 개가 같은 저장소를 만졌고, 둘 다
`git config user.name` 이 `janghyojoon` 이라 장부에서 **한 사람**이었다.
`checkOverlap()` 은 자기 claim 을 겹침으로 보지 않으므로 뒤에 온 claim 이 그냥 통과했고,
레코드는 이름당 파일 하나라 앞 세션의 작업·의도·시작 시각이 그대로 덮였다.
`status` 에는 claim 이 1건만 남았다. 두 세션이 같은 파일을 동시에 밀었고 **장부는 아무
경고도 안 냈다.** 이름을 정하는 순서(위)가 막으려던 실패가, 이름이 진짜로 같을 때
그대로 되살아난 것이다.

| 순위 | 출처 |
|---|---|
| 1 | `--session <id>` (CLI 만) |
| 2 | `AXMAP_SESSION` — MCP 서버가 자식에게 이 이름으로 심는다 |
| 3 | `CLAUDE_CODE_SESSION_ID` — 도구가 세션마다 다르게 준다 |
| 4 | 없으면 `null` = **확인할 수 없음** (CLI). MCP 서버만 `mcp-<pid>` 로 떨어진다 |

claim 레코드에 `session` 필드로 남고, **레코드를 가르는 키의 절반이다**
(`actor` 와 다른 점이다). 즉 레코드의 임자는 이름 하나가 아니라 **(이름, 세션) 짝**이고,
장부 파일도 짝마다 하나다.

> 🔴 **처음 낸 처방은 거부였다. 1.0.4 에서 걷어냈다.**
>
> 세션이 다르면 `claim` 도 `release` 도 종료 코드 2 로 막았다. 증상은 멎었지만
> 뿌리는 그대로였다 — 뿌리는 **레코드가 이름당 하나라 통째로 갈아끼워진다는 것**이고,
> 거부는 그 위에 덮은 뚜껑이었다. 그 뚜껑은 같은 사람이 창 두 개로 **겹치지도 않는
> 다른 일**을 하는 것까지 막았고, 막힌 사람은 이름을 바꿔 달거나 도구 밖으로 나갔다.
>
> 지금은 **자리를 나눈다.** 세션마다 레코드가 따로 적히므로 덮을 자리가 아예 없다.

세션을 모르는 실행들(세션 개념이 없는 셸, 옛 레코드)은 `null` 이라는 **한 자리를 함께
쓴다.** 실행마다 다른 값을 지어내면 자기가 잡은 것을 자기가 못 늘리고 못 반납한다.

🔴 **없다고 프로세스마다 다른 값을 지어내지 않는다.** pid 나 난수를 채우면 `axmap` 을
부를 때마다 다른 세션이 되고, 자기가 잡은 것을 자기가 못 늘리고 못 반납한다.
모를 때는 모른다고 말하는 것이 유일하게 안전한 값이다.

| 명령 | 같은 이름의 다른 세션에 대해 |
|---|---|
| `claim` | **막지 않는다.** 자기 줄을 새로 만든다. 앞 세션의 `task`·`intent`·`since` 는 그대로 남는다. 다만 그런 줄이 있다는 것과, 경로가 겹치면 겹친다는 것을 **찍어준다** |
| `release` | **이 세션이 잡은 것만 푼다.** 다른 세션의 줄은 손대지 않는다. 그것까지 풀려면 `--all-sessions` |
| `renew` | **이 세션의 것만 늘린다.** 다른 세션 줄은 못 찾은 것으로 끝내고(종료 코드 1), 그런 줄이 있다고 알려준다 — 모르고 늘리면 아무도 안 쓰는 경로가 계속 막힌다 |

`release --all-sessions` 가 **유일한 문이다.** 문을 안 두면 사람은 시스템 밖으로 나가고,
그때 하는 일은 장부 파일을 손으로 지우는 것이라 아무 기록도 안 남는다.

**겹침 검사는 agent와 session을 함께 비교한다.** 같은 이름이어도 세션이 다르면 다른 주체로 판정해 겹치는 선점을 거절한다. 관리형 터미널 연결은 세션마다 고유한 식별자를 자식 프로세스에 전달한다.

## 4. 경로 규칙

### 정규화

1. `\` → `/`
2. 연속 `/` 를 하나로
3. 앞의 `./` 제거
4. 뒤의 `/` 제거

저장소 루트 기준 상대 경로를 쓴다.

### 겹침 정의

```
overlap(a, b)  ⇔  a == b  ∨  a.startsWith(b + "/")  ∨  b.startsWith(a + "/")
```

반드시 `/` 경계로 판정한다. 단순 문자열 prefix 로 판정하면 `src/auth` 가 `src/authz` 를 잡아먹는다.

| a | b | 겹침 | 이유 |
|---|---|---|---|
| `src/auth` | `src/auth/login.ts` | ✓ | 디렉터리가 하위 파일을 덮는다 |
| `src/auth/login.ts` | `src/auth` | ✓ | 방향 무관 |
| `src/auth` | `src/authz` | ✗ | `/` 경계가 아니다 |
| `src/auth/login.ts` | `src/auth/token.ts` | ✗ | 형제 파일 |

## 5. 상태 전이

```
      ┌─────────┐
      │ 미점유  │
      └────┬────┘
           │ claim  (관문 1 통과 ∧ 관문 2 통과)
           ▼
      ┌─────────┐  renew (since 갱신)
      │  점유   │ ⟲
      └────┬────┘
           │
    ┌──────┴───────┐
    │              │
 release      since+ttlMs 경과
    │              │
    ▼              ▼
┌─────────┐  ┌──────────┐
│ 미점유  │  │  만료됨   │  레코드는 남지만 아무것도 막지 못한다
└─────────┘  └────┬─────┘
                  │ 다음 claim/release 때 정리
                  ▼
             ┌─────────┐
             │ 미점유  │
             └─────────┘
```

**TTL 이 필요한 이유.** 에이전트는 죽는다. 컨텍스트가 끊기고, 프로세스가 종료되고, 사람이 창을 닫는다.
`release` 를 보장할 수 없으므로 락은 스스로 풀려야 한다.
살아 있는 에이전트는 `renew` 로 연장하고, 죽은 에이전트의 락은 만료된다.

기본 TTL 은 30분이다.

### 만료의 정확한 의미

> **만료는 레코드가 사라지는 것이 아니라, 레코드는 남고 효력만 잃는 것이다.**

이 구분을 놓치면 락이 조용히 두 명에게 발급된다. 실제로 밟은 함정이다.

1. `agent-a` 가 `src/foo` 를 잡았다가 TTL 이 만료됐다 (레코드는 장부에 남아 있다)
2. `agent-b` 가 정당하게 `src/foo` 를 가져갔다
3. `agent-a` 가 이제 `src/bar` 를 claim 한다
4. 관문 2 는 **요청한 `src/bar` 만** 검사한다
5. 기존 claim 과 합집합을 만들 때 죽어 있던 `src/foo` 가 딸려 들어오고 `since` 가 갱신된다
6. → `src/foo` 를 `agent-a` 와 `agent-b` 가 동시에 소유한다

따라서 다음 두 규칙을 지킨다.

- **합집합 병합의 대상은 "내 레코드"가 아니라 "효력이 남은 내 레코드"다.**
  만료됐으면 새 claim 으로 시작한다 (`myActiveClaim()`).
- **만료된 claim 은 `renew` 할 수 없다.** 그 사이 남이 가져갔을 수 있으므로
  관문 2 를 다시 통과해야 한다. `renew` 는 관문 2 를 거치지 않는다.

## 6. 취득 알고리즘

```
acquire(paths):
  for attempt in 1..5:
      ── 관문 1 준비 ──────────────────────────────
      git fetch origin axmap/claims       (장부 worktree 안에서)
      git reset --hard FETCH_HEAD            (원격이 항상 진실. 병합하지 않는다)

      ── 관문 2 ──────────────────────────────────
      claims  := 장부의 모든 레코드
                 (레코드 하나라도 읽을 수 없으면 즉시 중단 - fail-closed)
      verdict := checkOverlap(paths, claims, me, now)
      if not verdict.ok:
          거부 사유를 출력하고 exit 2          ← 재시도하지 않는다

      prev := myActiveClaim(claims, me, now)   ← 만료된 내 레코드는 제외
      내 claim 파일 := prev.paths ∪ paths
      git commit

      ── 관문 1 ──────────────────────────────────
      if git push origin HEAD:axmap/claims 성공:
          return 성공
      # 거부 = 그 사이 누가 장부를 바꿨다. 다시 읽고 관문 2 부터 재판정.
      백오프(attempt)                        ← 즉시 다시 몰아치지 않는다

  exit 1  (경합 과다)
```

### 두 종류의 경합 — 백오프는 둘 다에 붙는다

| | 무엇이 부딪히나 | 어떻게 보이나 |
|---|---|---|
| 관문 1 (CAS) | 원격 ref | `git push` 거부 |
| 로컬 인덱스 락 | 같은 worktree 의 `.git/…/index.lock` | `add`·`commit`·`reset` 이 "File exists" 로 실패 |

**둘은 층이 다르므로 위 재시도 루프가 아래를 덮지 않는다.** 실제로 아래는 오랫동안
재시도가 아예 없어서 `index.lock` 하나에 즉시 exit 1 이었다. 한 저장소에서 여러
프로세스가 장부를 커밋하면(앱이 세션을 여럿 굴리는 것이 바로 그것이다) 매번 밟는다.

둘 다 **지수 백오프로 재시도**한다(50 → 1600ms). 지터는 난수가 아니라 **pid** 로 만든다 —
프로세스를 흩어놓는 목적은 pid 로도 달성되고, 난수와 달리 같은 입력에서 같은 타이밍이
재현되므로 재시도가 실제로 도는지를 테스트가 확인할 수 있다.

끝내 락이 안 풀리면 **원인을 말하며** exit 1 한다. "git 실패" 로 뭉개면 사람이 고칠
방법이 없다. 그리고 죽기 전에 **로컬 레코드를 되돌린다** — 커밋도 push 도 되지 않은
claim 이 worktree 에 남으면 그 저장소만 "내가 쥐고 있다" 고 말하는 fail-open 이 된다.
아직 한 번도 add 되지 않은 레코드는 추적되지 않으므로 `reset --hard` 로는 지워지지
않는다는 점에 주의한다.

**재시도 때 관문 2 를 다시 통과해야 하는 이유.**
push 가 거부된 원인이 "그 사이 누군가 내가 원하는 경로를 가져갔기 때문"일 수 있다.
관문 2 를 건너뛰고 push 만 재시도하면 겹친 claim 이 그대로 들어간다.

`fetch` 는 반드시 **장부 worktree 안에서** 실행한다.
`FETCH_HEAD` 는 worktree 별로 따로 보관되므로, 메인 worktree 에서 fetch 하면 장부 worktree 에서 보이지 않는다.

### fail-closed 원칙

락 시스템에서 최악의 실패는 **거부해야 할 것을 조용히 통과시키는 것**이다.
막아야 할 때 못 막으면 두 에이전트가 같은 코드를 고치고, 아무도 에러를 보지 못한다.
반대로 통과시켜야 할 때 막으면 에이전트가 메시지를 읽고 다른 작업으로 돌면 그만이다.

**판단이 서지 않으면 거부한다.**

| 상황 | 하지 않는 것 | 하는 것 |
|---|---|---|
| 장부 레코드를 파싱할 수 없다 | 건너뛰고 계속 | 전체 중단 |
| 레코드에 필수 필드가 없다 | 기본값으로 채움 | 전체 중단 |
| 에이전트 이름에 이상한 문자가 있다 | 안전한 문자로 치환 | 거부 |
| 내 이전 claim 이 만료됐다 | 그대로 이어씀 | 새 claim 으로 시작 |

레코드를 하나 건너뛰면 그 에이전트가 아무것도 잡고 있지 않은 것처럼 보이고,
남의 락 위에 내 claim 이 발급된다. 그래서 건너뛰지 않는다.

## 7. pre-commit 계약

```
staged := git diff --cached --name-only   (.axmap/ 제외)
mine   := 내 claim 의 paths  (만료되었으면 빈 배열)

∀ f ∈ staged : ∃ p ∈ mine : f == p ∨ f.startsWith(p + "/")
```

위반 시 커밋을 거부한다.

이것이 없으면 프로토콜은 순수 권고 사항이 된다.
claim 을 건너뛰고 바로 코드를 고치는 에이전트를 막을 방법이 있어야 한다.

훅 안에서 git 을 호출할 때는 `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`,
`GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_PREFIX`
를 제거해야 한다. 이 변수들은 `cwd` 보다 우선하므로 장부 worktree 조작을 깨뜨린다.

예외로 staged 목록을 읽을 때만 `GIT_INDEX_FILE` 을 남긴다.
`git commit --only <경로>` 는 임시 인덱스를 만들어 이 변수로 알려주며,
제거하면 실제로 커밋될 내용이 아닌 다른 인덱스를 검사하게 된다.

### 장부 커밋은 사용자 훅을 거치지 않는다

**연결된 worktree 는 훅 디렉터리를 공유한다.** `.git/hooks` 는 `git-common-dir` 아래에 하나뿐이다.
따라서 사용자가 `pre-commit` 훅을 설치하면 **장부 worktree 에 대한 커밋에도 그 훅이 발동한다.**

그대로 두면 이렇게 죽는다.

1. 장부 커밋 → `pre-commit` 발동 → `axmap verify` 실행
2. 이번에는 장부 worktree 안에서 실행되므로 저장소 루트가 `.axmap/ledger` 다
3. 그 안에 또 장부가 있을 리 없으므로 실패
4. → **훅을 설치하는 순간 `claim` 이 통째로 죽는다**

장부는 사용자 코드가 아니라 내부 기록이므로 사용자 훅의 대상이 아니다.
장부 커밋은 항상 `--no-verify` 로 한다.
`verify` 자신도 장부 worktree 안에서 호출되면 즉시 통과시킨다 (두 번째 그물).

이 함정은 순서를 사람이 정한 데모에서는 드러나지 않았고, `demo/chaos.sh` 의 무작위 순서가 찾아냈다.

## 7-2. `audit` — 장부가 스스로 깨졌는지 검사한다

```
axmap audit [--json] [--fetch] [--code <구간>] [--checkpoint]
```

장부 브랜치의 **모든 스냅샷을 시간순으로 재생**하며 불변식을 확인한다.
지금 상태만 보는 것이 아니라 과거의 모든 시점을 본다.

| 검사 | 무엇 |
|---|---|
| I1 상호배제 | 어느 시점에도 두 에이전트가 같은 경로를 잡고 있지 않았나 |
| I2 무손실 | 성공한 claim 의 경로가 레코드에서 빠지지 않았나 |
| I6 비부활 | 만료된 레코드가 되살아나지 않았나 |

`src/invariants.mjs` 를 쓴다. 모델 검증기(`test/model.test.mjs`)와 **같은 검사기**다.

**종료 코드는 0 또는 4다.** 위반을 찾으면 4 — 다른 거부(2·3)와 구분되어야 한다.
2·3 은 "당신이 규칙을 어겼다"이고, **4 는 "장부 자체가 깨졌다"**로 성격이 다르다.

> 이 명령이 존재할 수 있는 이유는 판정이 순수 함수이기 때문이다.
> LLM 이 겹침을 판정했다면 과거를 재생해도 같은 답이 나온다는 보장이 없고,
> 그러면 이 검사 자체가 성립하지 않는다 (DECISIONS.md D4).

### 체크포인트 — 이력은 그대로 두고 **다시 안 본다**

장부는 하루 100건씩 늘기만 하므로, 매번 처음부터 재생하면 이 검사는 쓸수록
느려진다. 팀 저장소에서 파이프라인 평균이 42초에서 332초로 갔고, 같은 파이프라인의
다른 잡은 5~10초 그대로였다 (실측 2026-09-04, 표본 각 15건).

**최근 N개만 본다·오래된 것을 지운다 로는 못 고친다.** 이 검사가 보장하는 문장이
*"어느 시점에도 두 사람이 같은 파일을 동시에 잡은 적이 없다"* 이므로, 최근만 보면
사흘 전 겹침이 영원히 안 보인다.

그래서 버리는 대신 **이미 본 구간을 다시 안 본다.** 체크포인트 하나는 이런 문장이다 —
*"장부를 뿌리부터 이 커밋까지 재생했고, 그 구간의 모든 스냅샷에서 I1 이 성립했다."*
장부는 뒤에 붙기만 하는 git 이력이라 한 번 증명한 앞구간은 계속 참이고, 거기에
이어서 재생한 결과를 붙이면 **전체를 본 것과 같다.**

| | |
|---|---|
| 어디 사는가 | 고아 브랜치 `axmap/checkpoints` 의 `checkpoints.json` 하나 |
| 무엇이 적히나 | **장부 커밋 sha 와 그 시점** — 상태의 사본이 아니라 주소다 |
| 누가 적나 | `axmap audit --checkpoint` 가 **감사가 통과했을 때만** |
| worktree | 없다. 읽기·쓰기 모두 git 배관이라 신선한 clone(=CI)에서도 그대로 돈다 |

🔴 **어디서부터 재생하는가가 이 설계의 전부다.** 시작 지점은 "가장 최근
체크포인트" 가 **아니라** "이번 코드 구간에서 가장 오래된 커밋보다 앞선
체크포인트" 다. 최근 것부터 보면 승격 MR 이 나르는 며칠 전 커밋은 대조할 장부
스냅샷이 없어 **조용히 통과**한다 — 락에서 최악인 fail-open 이다.

- 기능 브랜치는 오늘 만든 커밋 몇 개뿐이라 오늘치만 읽는다
- 승격 MR 은 며칠치를 한 번에 나르므로 그만큼 거슬러 올라간다

**드물게 무거운 것이 자주 무거운 것보다 낫다.** 고치기 전은 정반대였다.

🔴 **판정할 수 없으면 통과시키지 않는다.** 체크포인트가 가리키는 커밋이 지금
장부의 조상이 아니거나(이력이 다시 쓰였다) 파일이 깨져 있으면 **판정 불가**로
0 이 아닌 종료 코드를 낸다. 성능을 위해 보장을 무르게 만들지 않는다.

**첫 체크포인트보다 앞선 코드 커밋은 면제한다** — 이미 만들어진 커밋이라 지금 와서
다시 만들 수 없다. 장부가 생기기 전 커밋을 봐주던 자리를 한 번 더 쓰는 것이고,
면제한 것은 **몇 건을 무엇을** 봐줬는지 결과에 그대로 찍힌다.

체크포인트를 남기는 자리는 감사를 이미 돌리는 곳이 가장 좋다 — 팀 CI 의 감사 잡에
`--checkpoint` 를 붙이면 통과할 때마다 하나씩 쌓인다. **그 잡에 push 권한이 없어도
감사 결과는 달라지지 않는다.** 못 남긴 체크포인트의 대가는 다음 감사가 느린 것이지
판정이 헐거워지는 것이 아니다 (장부 push 실패와 정반대다).

## 7-3. 병합 합의 — 게이트는 거부권, 표는 판단

> Phase 2. **판정 로직만 있고 CLI·git 연결은 아직 없다.**
> `checkMerge()` 는 `src/protocol.mjs` 에 있고 `test/protocol.test.mjs` 가 검사한다.

작업 노드가 사라져도 저장소가 스스로 굴러가려면, **"이 변경을 넣어도 되는가"를
사람이 그 자리에 없어도 답할 수 있어야** 한다. 그 판정을 여기서 정의한다.

MR/PR 을 이 문서에서는 **제안(proposal)** 이라고 부른다. 플랫폼마다 이름이 다르고
(GitLab MR · GitHub PR), 폐쇄망에는 둘 다 없다. 제안과 표는 git 안에 산다.

### 두 층 — 섞지 않는다

```
  제안 하나
     │
     ▼
  ┌──────────────────────────────────────────────┐
  │ 층 1 · 게이트 (기계, 결정론적)                 │
  │   test / demo / demo:compare /               │
  │   demo:chaos         │
  │   하나라도 빨강 → 끝. 표를 세지 않는다          │ ← I8
  └──────────────────────────────────────────────┘
     │ 전부 초록
     ▼
  ┌──────────────────────────────────────────────┐
  │ 층 2 · 표 (판단, 비동기 누적)                  │
  │   votes/<제안ID>/<투표자>.json                │
  │   위험 등급별 정족수                            │
  └──────────────────────────────────────────────┘
```

**게이트를 표 중 하나로 넣지 않는 이유.** 넣는 순간 2 대 1 로 빨간 테스트를
통과시킬 수 있게 된다. 이 저장소는 "판정은 언제나 종료 코드"라고 정해 두었고
(CLAUDE.md), 종료 코드는 협상 대상이 아니다.

빨간 게이트를 만나면 **표를 세지 않고 즉시 나간다.** 세기 시작하면
"5 대 0 인데 왜 안 되나"라는 질문이 생기고, 그 질문이 생기면 언젠가 통과한다.

### 🔴 표는 실시간이 아니다

정족수를 **동시 접속 조건**으로 걸면 시스템이 노드 가용성에 의존하게 된다.
에이전트가 2대면 아무것도 못 하고, 0대면 정지한다.
그건 이 프로토콜이 TTL 로 피하려던 실패(I4)를 병합 층에서 다시 만드는 것이다.

| 붙어 있는 에이전트 | 실시간 정족수 | 이 규격 |
|---|---|---|
| 3 | 병합 | 병합 |
| 2 | ✗ 아무것도 못 함 | 표 2개 쌓인 채 대기 |
| 0 | ✗ 시스템 정지 | 저장소는 멀쩡. 그냥 조용함 |
| 3주 뒤 세 번째 표 | ✗ 처음부터 다시 | 그 순간 병합 |

표는 파일로 쌓인다. 3초 간격으로 오든 3주 간격으로 오든 조건은 같다.
`docs/bus/` 가 이미 같은 거래를 했다 — 실시간을 포기하고 "다른 컴퓨터에 있어도 된다"를 얻었다.

### 표 레코드

```json
{
  "voter":   "agent-b",
  "head":    "9f3c1a2",
  "verdict": "approve",
  "lens":    "spec",
  "reason":  "SPEC 7-3 과 어긋나는 곳 없음"
}
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `voter` | ✓ | 투표자. 그대로 파일명이 되므로 `agent` 와 **같은 규칙**으로 검증한다 |
| `head` | ✓ | 이 표가 본 커밋. 제안의 head 가 움직이면 표는 **자동으로 무효** |
| `verdict` | ✓ | `approve` \| `reject` |
| `lens` | | 어떤 관점으로 봤나. 아래. **판정에는 관여하지 않는다** |
| `reason` | | 사람이 읽는 한 줄 |

**표에 TTL 이 없는 이유.** claim 은 시간이 지나면 의미를 잃지만, 표는 **코드가
바뀌어야** 의미를 잃는다. 그래서 무효화 기준이 시계가 아니라 `head` 다.
제안자가 지적을 고쳐 새 커밋을 올리면 모든 표가 한 번에 리셋되는데,
이건 부작용이 아니라 의도다 — **고친 코드는 다시 봐야 한다.**

**투표자당 파일 하나인 이유**는 claim 과 같다. 두 명이 같은 줄을 쓸 일을 없앤다.
같은 제안·같은 투표자의 표가 둘 이상 읽히면 **건너뛰지 말고 전체를 중단**한다(§6).

### 반대표 하나가 정족수를 이긴다

`reject` 가 하나라도 있으면 찬성표가 몇이든 막힌다.

다수결로 덮지 않는 이유: **발견은 다수결의 대상이 아니다.** 2 대 1 로 통과시키면
"한 명이 찾아낸 진짜 문제"와 "한 명이 틀린 것"을 구별하지 않고 똑같이 버린다.

교착이 아니다. 막혔을 때 나가는 길은 논쟁이 아니라 **고치는 것**이고,
고치면 head 가 바뀌어 반대표가 스스로 사라진다.

### 자기 표는 세지 않는다

`voter == proposal.agent` 인 표는 정족수에서 제외한다.
시빌 공격의 가장 싼 형태이고, 막는 비용이 한 줄이다.

> ⚠️ **반출 후에는 이것으로 부족하다.** GitHub 공개 시점에는 한 사람이 이름 셋으로
> 표 셋을 쓸 수 있다. 정답은 git 기본 기능인 **서명 커밋**이라 새 의존성이 없다.
> 지금 만들지 않는다 — 지금은 참여자를 전부 알기 때문이다.
> **반출 시점에 반드시 다시 판단한다.** 신원은 나중에 끼워 넣기가 가장 어려운 축이다.

### 정족수는 위험 등급별이다

고정 3표는 두 방향으로 틀린다. 오탈자 하나에 에이전트 3대를 깨워야 하고,
프로토콜 심장부를 고치는 데 1표면 충분해진다.

| 등급 | 경로 | 필요한 찬성표 |
|---|---|---|
| 심장부 | `src/protocol.mjs` · `src/invariants.mjs` · `bin/axmap.mjs` · `docs/SPEC.md` · `docs/INVARIANTS.md` | **3** |
| 보통 | 그 외 전부 | 1 |
| 문서 | `docs/` (위 두 파일 제외) | 0 — 게이트만 |

제안이 여러 등급에 걸치면 **가장 높은 쪽**을 따른다.
어느 등급에도 안 걸리는 새 파일은 0 이 아니라 **기본값 1** 로 떨어진다 —
등급을 모르는 것은 "위험하지 않다"가 아니다.

경로 판정은 claim 과 같은 `coversPath()` 를 쓴다. 판정 규칙을 두 벌 두지 않는다.

### 렌즈 — 같은 모델 3개는 투표자 3명이 아니다

🔴 **아직 재지 않았다.** 같은 프롬프트로 같은 모델을 3번 부르면 유효 투표자 수는
1이고 나머지는 비용이다. 하드웨어 고장은 대체로 독립이지만 **소프트웨어 결함은
체계적이고 상관되어 있다.** 같은 배치에서 나온 디스크 3개는 중복 저장이 아니다.

그래서 표에 `lens` 를 적는다. 서로 **다르게 틀리게** 하기 위한 것이다.

| `lens` | 무엇을 보나 |
|---|---|
| `spec` | SPEC·INVARIANTS 와 어긋나는가 |
| `refute` | 이 변경으로 **통과가 늘어나는가** (CLAUDE.md 가 이미 요구하는 질문) |
| `product` | 비전공자가 쓸 수 있는가 (D1 · D14) |

**`lens` 는 판정에 관여하지 않는다.** `actor` 와 같은 위치의 표시용 필드다.
렌즈별 정족수를 강제하려면 먼저 **불일치율을 재야 한다** — 렌즈가 실제로 다른
답을 내는지 모르는 채로 강제하면 비용만 3배가 된다. 검증 없이 렌즈별 정족수를 강제하지 않는다.

### 판정

```
checkMerge({ proposal, votes, gates, policy }) -> {ok, need, approvals, blocks}
```

순수 함수다. git 도 시계도 없다 — `checkOverlap` 과 같은 이유로,
과거를 재생해 사후 감사를 할 수 있어야 하기 때문이다(§7-2).

```
merge(p) ⇔  모든 필수 게이트가 존재하고 초록
          ∧ head 가 일치하는 reject 표가 없음
          ∧ head 가 일치하고 voter ≠ 제안자인 approve 표 ≥ need(p.paths)
```

**게이트가 없는 것도 빨강으로 친다.** 안 돌린 검증과 통과한 검증을 같게 보면
게이트가 아예 없는 것과 같다(§6 fail-closed).

## 8. 종료 코드

| 코드 | 의미 | 에이전트가 할 일 |
|---|---|---|
| 0 | 성공 | 작업 진행 |
| 1 | 사용법/환경 오류, 경합 과다 | 메시지를 읽고 수정 |
| 2 | 관문 2 거부 — 경로 겹침, **또는 같은 이름·다른 세션** | **다른 작업으로 전환**. 재시도해도 결과는 같다 |
| 3 | pre-commit 거부 (claim 없는 파일) | 해당 경로를 claim 하거나 스테이징에서 제외 |
| 4 | `audit` 이 불변식 위반을 찾음 | 장부가 깨졌다. 사람이 봐야 한다 |
| 5 | `release` 가 **아무것도 반납하지 못함** | 내 이름이 잡을 때와 다르다. 확인하고 다시 |

2 와 3 을 구분하는 이유는 에이전트가 자동으로 다르게 대응해야 하기 때문이다.
2 는 계획을 바꾸라는 뜻이고, 3 은 절차를 빠뜨렸다는 뜻이다.

**세션 충돌에 코드를 새로 만들지 않은 이유**는 부르는 쪽이 할 일이 같아서다 —
재시도하지 말고 방향을 바꾼다. 무엇이 막았는지는 메시지가 말한다(겹침이면 점유자,
세션이면 어느 세션이 무엇을 잡고 있는지와 `--all-sessions`). 종료 코드는 *무엇을 해야 하는가*를 나누는 것이지
*무슨 일이 있었는가*를 나누는 것이 아니다. 그걸 섞으면 코드가 계속 늘고, 늘어난 코드는
아무도 안 본다.

🔴 다만 `release` 가 세션 때문에 막힐 때는 **5 가 아니라 2** 다. 5 는 "내 이름이 잡을
때와 다르다" 는 뜻이고 처방이 "이름을 맞춰라" 인데, 세션 충돌의 처방은 정반대로
"이름을 갈라라" 다. 같은 코드로 내면 부르는 쪽이 엉뚱한 처방으로 간다.

### 왜 5 가 따로 있나

**반납을 시켰는데 아무것도 반납 안 된 것은 성공이 아니다.**

실제로 두 대로 협업하다 물렸다. `AXMAP_AGENT=X` 로 claim 한 뒤, 그 변수가
없는 셸에서 `release` 를 불렀다. 이름이 `git config user.name` 으로 떨어졌고,
그 이름으로는 잡은 것이 없으니 *"…이(가) 잡고 있는 경로가 없습니다"* 를
찍고 **종료 코드 0** 을 냈다.

반납했다고 믿었지만 락은 그대로였고, 다른 에이전트를 30분 더 막았다.
출력을 `>/dev/null` 로 보낸 상태였으므로 아무 신호도 없었다.

0 을 주면 스크립트와 에이전트는 그것을 성공으로 읽는다. 락 시스템에서
**조용히 통과시키는 것이 가장 나쁜 실패**라는 원칙이 여기에도 그대로 적용된다.

메시지에는 **이름이 어디서 왔는지**(`--agent` / `AXMAP_AGENT` /
`git config`)를 함께 적는다. 원인이 거의 항상 그것이기 때문이다.

## 9. 확장 지점 — blast radius (Phase 2, 미구현)

파일 단위 락으로는 잡을 수 없는 겹침이 있다.

> A 는 `src/auth.ts` 를, B 는 `src/checkout.ts` 를 잡았다. 경로는 겹치지 않는다.
> 그런데 A 가 `verifyToken()` 의 시그니처를 바꿨고, `checkout.ts` 가 그것을 쓴다.

이 경우 claim 은 통과하지만 작업은 충돌한다.
**파일 단위 락이 의존 관계를 보지 못하는 것은, git 의 줄 단위 판정이 경로를 보지 못하는 것과 같은 종류의 미스매치다.**

해결 방향은 claim 의 정의를 넓히는 것이다.

```
claim = write-lock(paths)  +  notify(dependents(paths))
```

`checkOverlap()` 이 붙는 자리에 그래프 조회를 한 번 더 붙인다.
`paths` 는 지금처럼 거부하고, `dependents` 는 거부 대신 경고와 통지로 처리한다.
(강한 락으로 만들면 중심 모듈 하나가 저장소 전체를 잠근다.)

이 프로젝트가 그래프를 그리는 이유가 여기 있다.
그래프는 사람을 위한 그림이 아니라 **관문 2 의 판정 재료**다.
`axMap` 의 `map` 은 그 판정 재료를 가리킨다 — 보기 좋은 그림이 아니라, 에이전트가
"내가 건드리면 무엇이 같이 흔들리는가"를 묻는 자리다.

## 10. 비목표 (v0)

- **심볼 단위 락** — `src/auth.ts#verifyToken`. 같은 파일에 서로 다른 함수를 추가하는
  두 에이전트를 헛되이 막는 오탐이 남아 있다. Phase 3.
- **협상/대기열** — 거부는 즉시 거부다. 대기하거나 순번을 예약하지 않는다.
- **부분 잠금 승격** — 읽기 락과 쓰기 락을 구분하지 않는다.
- **네트워크 분단 처리** — origin 이 없으면 관문 1 이 작동하지 않는다.
  단일 작업자 환경에서만 안전하며 CLI 가 경고한다.
- **한 클론을 여러 에이전트가 공유** — 에이전트마다 자기 클론이나 worktree 를 가져야 한다.
  장부 worktree 를 공유하면 git 인덱스 락에서 경합한다.

### 장부 압축을 만들지 않은 이유

장부 브랜치는 claim 마다 커밋이 쌓인다. 실측했다.

```
7 커밋 → 42 objects, 3.86 KiB   (커밋당 약 550 바이트)
```

에이전트 6명이 30분마다 갱신하며 하루 8시간 작업하면 하루 약 150 커밋, **약 80 KB** 다.
1년을 쌓아도 30 MB 미만이고 `git gc` 가 더 줄인다.

압축을 하려면 force-push 가 필요한데, 그것은 다른 에이전트의 관문 1(CAS)을 무력화한다.
**얻는 것보다 잃는 것이 크므로 만들지 않는다.**

## 11. MCP 도구 표면

`mcp/server.mjs` 가 내놓는 도구 목록이다. **여기에 새 판정은 없다** —
전부 `bin/axmap.mjs` 를 그대로 부르고 종료 코드를 그대로 옮긴다.
두 경로가 갈라지면 장부를 믿을 수 없게 되므로 이 성질을 깨지 않는다.

| 도구 | 부르는 명령 | 비고 |
|---|---|---|
| `ax_brief` | (없음) | 문서를 읽어 만든다. 아래 "무엇을 읽는가" 참고 |
| `ax_init` | `axmap init` | 이미 있으면 아무것도 바꾸지 않는다 |
| `ax_claim` | `axmap claim … --ttl --actor` | exit 2 는 "다른 작업으로 옮겨라" |
| `ax_check` | `axmap status --json` | 장부를 바꾸지 않는다 |
| `ax_status` | `axmap status` | |
| `ax_release` | `axmap release [경로…]` | exit 5 를 삼키지 않는다 |
| `ax_renew` | `axmap renew --ttl` | |
| `ax_inbox` / `ax_send` | `tools/bus.mjs` | 쪽지함. 실시간이 아니다 |

### `SELF` 와 `REPO` — 프로그램과 데이터를 가른다

MCP 서버는 **자기 저장소(`SELF`)와 작업 대상(`REPO`)이 다를 수 있다.**
`AXMAP_REPO` 를 남의 저장소로 두고 붙이는 것이 정상 사용이다.
그때 무엇을 어느 쪽에서 잡느냐가 이 서버에서 가장 자주 틀리는 곳이다.

| | 기준 | 왜 |
|---|---|---|
| `bin/axmap.mjs`, `tools/bus.mjs` | **`SELF`** | 실행할 **프로그램**이다. 대상 저장소에는 없다 |
| 장부(`.axmap/`), 쪽지함(`docs/bus/`) | **`REPO`** | 그 팀의 **데이터**다. 그 팀의 저장소에 남아야 한다 |
| 브리핑이 읽는 문서 | **`REPO`** | 대상을 설명해야 한다 |
| 코드 지도(`MAP`) | `SELF`, 그리고 `REPO === SELF` 일 때만 | axMap 자신의 지도라서 |

쪽지함 위치는 `AXMAP_BUS_DIR` 로 넘긴다. 기본값은 `tools/bus.mjs` 가 있는
저장소이며, MCP 서버는 언제나 `<REPO>/docs/bus` 를 명시적으로 준다.

### 🔴 `ax_init` 이 도구 목록에 있어야 하는 이유

장부 없는 저장소에서 첫 `ax_claim` 은 exit 1 과 함께 *"먼저 실행하세요:
axmap init"* 을 낸다. 지시는 정확하지만 **에이전트에게는 셸이 없다.**
`init` 이 도구가 아니면 그 지시를 읽고도 실행할 수 없고, 사람이 끼어들어야만
풀린다 — 붙이자마자 만나는 벽이 정확히 여기다.

이 저장소 안에서만 시험하면 장부가 이미 있으므로 한 번도 안 밟는다.
`test/mcp.test.mjs` 가 `REPO ≠ SELF` 이고 장부가 없는 조합을 고정한다.

### 브리핑이 무엇을 읽는가

`REPO === SELF` 이면 axMap 자신의 문서와 코드 지도를 낸다.
`REPO ≠ SELF` 이면 **대상 저장소의** `CLAUDE.md` · `README.md` · `docs/` 만 읽고,
없으면 없다고 말한다. **axMap 의 문서로 대신 채우지 않는다.**

낡은 지도는 없는 지도보다 나쁘고, **남의 지도를 자기 지도인 양 주는 것은
그보다 한 단계 더 나쁘다** — 낡은 지도는 언젠가 맞았기라도 하다.
같은 이유로 대상 저장소의 코드 지도는 만들지 않는다. 지어낸 지도가 곧 그 실패다.
