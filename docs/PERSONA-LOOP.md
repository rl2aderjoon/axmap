# 3인 페르소나 루프 — 시각화가 실제로 일하는가

같은 저장소·같은 질문지에 **보는 것만 다른** 신입 셋을 붙인다.

```
A  시각화만   스크린샷만. API 도 소스도 못 본다
B  텍스트만   API 만. 화면을 못 본다              ← 기준선
C  둘 다
```

`node tools/persona-bench.mjs --draw` 로 새 저장소를 뽑아 판을 연다.
🔴 **성공한 저장소는 두 번 쓰지 않는다.** 이미 그 저장소에 맞춰 고쳤기 때문에
같은 것으로 또 재는 것은 아무것도 재지 않는 것이다.

## 1회차 — alluxio (Java · 커밋 26,314 · 파일 4,127 · 2026-08-20)

노드 3,124 · 엣지 15,676. 모델은 셋 다 Sonnet.

| | 도구 호출 | 7문항 | 실제로 틀린 답 |
|---|---|---|---|
| A 시각화만 | 10 | M6·M7 "못 함", M4 부분 실패 | 0 |
| B 텍스트만 | 13 | 전부 답함 | 🔴 **2 (M6·M7)** |
| C 둘 다 | 20 | M7 "못 함" | 0 |

### 🔴 이 판의 결론은 예상과 달랐다

**시각화가 이긴 유일한 자리는 "공간" 이 아니라 "정직" 이었다.**

C 가 정확히 이렇게 적었다 —

> API 만으로 정말 불가능한 것은 없었다. JSON 이 언제나 스크린샷보다 원본
> 정보가 많았다. **다만 화면의 평범한 문장 경고가 `claims: []` 같은 원시
> 숫자를 "아무도 없다" 로 오독하는 것을 막아줬다.**

그리고 B 가 실제로 그 오독을 했다. `/api/watch` 가 `ledgerAvailable: false` 를
보내면서 **동시에** `claims: []` 와 `summary.agents: 0` 을 보냈고, B 는 그 0 을
읽고 *"아무도 안 잡고 있어 부딪힐 대상 없음"* 이라고 **확신 있게 틀린 답**을 냈다.

같은 것을 그림으로 본 A 는 맞게 "못 함" 이라고 했다. 화면이 경고를 크게
그렸기 때문이다.

**화면이 API 보다 정직했다.**

### 그래서 무엇이 달라지나

그 정직함은 **그림의 성질이 아니라 글의 성질**이다. 숫자 옆에 단서를 붙이는 것.
그러니 API 에도 넣을 수 있고, 넣었다 —

    claims: []           → null      (없다 ≠ 모른다)
    summary.agents: 0    → null + why

🔴 **그 순간 지금 시각화의 측정된 값은 0 에 가까워진다.**

A 가 마지막 질문에 정직하게 답한 것이 이것을 뒷받침한다 —

> 막대그래프의 크기 순서와 빨간 배지 색은 글자 없이도 인상을 줬지만,
> **나머지 답 대부분은 옆에 적힌 문장을 읽어서 알아냈다.**

지금 화면에서 그림이 실제로 정보를 나르는 것은 **막대와 색 두 가지뿐**이다.
힘-지향 그래프는 거기 없다.

### 부수적으로 드러난 것

| | |
|---|---|
| 🔴 첫 화면이 60초 안에 안 뜬다 | 스크린샷 7장 중 2장이 시간초과. 둘 다 첫 무거운 계산 |
| 화면의 파일 경로가 말줄임표로 잘린다 | A 가 M4 에서 정확한 경로를 못 읽었다 |
| `/api/graph` 5MB · `/api/overlay` 7.2MB | B: "요약 없는 원본 덤프라 사람이 읽기엔 부적합" |
| 화면과 API 의 숫자가 다르다 | PropertyKey 참조 수 — 화면 742 vs API `deg` 769. 확인 필요 |
| A·C 가 사이드바 ⑤⑥ 걸음을 못 봤다 | 스크린샷에 그 상태가 안 담겼다 |

## 2회차 — Parsley.js (JS · 폼 검증 · 2026-08-20)

1회차의 설계 결함(스크린샷에 사이드바 문장이 들어 있었다)을 고치고 조건을 넷으로.
그리고 이번엔 **장부에 실제 claim 을 심었다** — 1회차는 비어 있어 협업 축을 못 쟀다.

| | 본 것 | 도구 호출 | 결과 |
|---|---|---|---|
| **A′ 그림만** | 그래프 3장 | 3 | 🔴 **M2 완전 실패**, M3·M6·M7 부분 실패 |
| A 화면 | 화면 7장 | 4 | 7/7 (M4 못 함) |
| B 텍스트 | API | 11 | 7/7, **못 읽은 것을 정확히 구분** |
| C 둘 다 | 화면+API | 26 | 7/7 (M4 미해결) |

### 🔴 결론 — 그림은 답을 만들지 못했다

A′ 가 순수 기하학(점의 크기·위치·선)만으로 알아낸 것은 **셋뿐**이었다.

> expect.js 노드의 압도적 크기 · bower_components 의 완전 고립 · src 와 한 점의 단일 연결

그리고 그 셋 중 **어느 것도 질문에 답하지 못했다.** A′ 가 답한 것들은
전부 상단 표시줄과 범례의 **글자**를 읽은 결과였고, 스스로 이렇게 적었다 —

> 그림 없이 텍스트 표만 있었어도 답이 같았을 질문: **4개 (M1·M4·M6·M7)**.
> 이들은 실질적으로 상단 텍스트 패널을 읽은 것이지 그래프 시각 정보를 쓴 게 아니었다.

A 는 더 강하게 말했다 —

> 캡처 7장에 그래프 캔버스가 **전혀 없었고** 전부 사다리(계층 목록) + 텍스트였다.
> "그림 없이 글자만 있었어도 답할 수 있었을 질문" 이 **7개 중 7개.**

즉 기본 화면은 이미 텍스트다. 그리고 그 텍스트만으로 4회 호출에 7문항을 답했다.
**API(11회)보다 빠르다** — 요약이 되어 있기 때문이다.

### 🔴 A′ 가 짚은 결정적 한 줄

> 그래프의 작은 점에 **파일명 라벨이 없어** claim 된 파일(field.js·form.js·ui.js)을
> 그래프 노드와 매칭할 수 없었다.

확인해보니 라벨 문제가 아니었다. **그 점들이 아예 그려지지 않았다.**
"핵심만"(밀집 완화)이 229개를 28개로 줄이면서 셋 다 떨어뜨렸다 —
핵심 집합 28개에 세 파일 모두 없었다.

사람이 여러 번 요청한 **"어느 노드가 작업 중인지 그래프에서 보여달라"** 가
못 landed 한 진짜 이유가 이것이다. 밀집 완화는 "덜 중요한 것을 접는다" 는
장치인데, **지금 사람이 손대고 있는 파일보다 덜 중요한 것은 이 화면에 없다.**
판단의 전제가 뒤집혀 있었다.

→ 고쳤다. 감시 중인 파일은 밀집 완화에서 절대 빠지지 않고, 라벨도 양보하지 않는다.

### 🔴 C 가 찾은 내부 불일치

> flow·graph 화면은 "커밋 0개, 히스토리 부족" 이라 하는데
> feature 화면과 watch 패널은 실제 커밋을 보여준다.

원인을 따라가니 `readCommitSets` 가 `fatal: unable to read <sha>` 로 죽고
**null 을 조용히 돌려주고** 있었다. 화면은 그걸 "히스토리 부족" 이라 번역했다.
히스토리는 있었다. **못 읽은 것을 없는 것으로 말한 것**이다 — 오늘만 네 번째다.

→ 실패 이유를 `stats.gitError` 로 함께 낸다.

⚠️ 그리고 그 실패는 **우리 벤치 준비가 만든 것**이었다. 장부를 남의 GitHub 에
push 하지 않으려고 평가 클론의 `origin` 을 로컬 베어 저장소로 바꿔 달았는데,
그때 `extensions.partialclone` 설정이 통째로 지워져 blobless 판정이 깨졌다.
blobless 클론에서 rename 탐지가 켜지면 없는 blob 을 읽으려다 죽는다.

**다음 판부터는 평가 대상을 `--filter=blob:none` 없이 통째로 클론한다.**
느리지만 이 함정이 사라진다.

### B 가 1회차의 오답을 반복하지 않았다

1회차에서 B 는 `claims: []` 를 "아무도 없다" 로 읽고 확신 있게 틀렸다.
그 사이 `/api/watch` 를 고쳤고(못 읽었으면 null), 2회차 B 는 이렇게 적었다 —

> git 기반 위험 신호는 `null`/`noGit:true` 였다. **없는 게 아니라 못 읽은 것**이다.

수정이 실제로 오답을 막았다. 벤치가 회귀 테스트 노릇을 했다.

## 3회차 — ziti (Go · 커밋 6,113 · 파일 1,926 · 2026-08-20)

1·2회차와 **묻는 것이 다르다.** 앞의 둘은 "그림이 값을 하는가" 를 물었고 답은
"아니오" 였다. 3회차는 **"그러면 어떤 형식이 나은가"** 를 묻는다.
사람이 형식 넷을 고르라고 했다.

조건 다섯. 저장소·질문지·장부가 전부 같고 **보는 화면만** 다르다.

| | 화면 | 호출 | M4 | 틀린 답 | 그림 없이 글자만으로 답이 같았을 질문 |
|---|---|---:|---|---:|---|
| **B 텍스트** (기준선) | API 만 | **28** | 우회로 답함 | 0 | **7 / 7** |
| **사다리** | `?view=ladder` | **32** | 못 함 | 0 | **7 / 7** |
| **그래프** | `?view=graph` | **32** | 못 함 | 0 | **7 / 7** |
| **감시** | `?watch=1` | **34** | 못 함 | 0 | **7 / 7** |
| **펼치기** | `?view=reveal` (기본) | **46** | 못 함 | 🔴 **1 (M2)** | **7 / 7** |

### 🔴 결론 ① — 형식을 바꿔도 그림은 여전히 답을 못 만든다

네 조건이 **서로 모르는 채로 같은 숫자를 냈다: 7/7.**
힘-지향 그래프든, 계층 목록이든, 점진 공개든, 활동 지도든 마찬가지였다.

각자 "그림만으로 알아낸 것" 을 적었는데 전부 같은 모양이다 —
막대 길이, 색 띠, 들여쓰기, 점의 크기. 그리고 **넷 다 바로 옆에 같은 내용이
숫자나 문장으로 다시 적혀 있었다.**

> 답을 실제로 만든 것은 다섯 개의 **문장**이었다:
> 「137개가 부른다」「폴더를 잡으면 아래 파일까지 물든다」「29% 뿐이다」
> 「아직 말할 수 없습니다」「출처: README.md」   — 사다리 조건

> M7 의 핵심 발견은 **그림에 전혀 없었고** `lift 8.1 · n=5` 라는 목록 한 줄에서 나왔다.
> — 그래프 조건

세 회차가 같은 답을 냈다. **이제 이것은 인상이 아니라 관측이다.**

### 🔴 결론 ② — 그림이 아니라 **목록이냐 확정이냐**가 갈랐다

유일한 오답이 나온 자리가 이것을 정확히 보여준다.

도구는 진입점 1위로 `ziti/db-explorer/cmd/ziti-db-explorer/main.go` 를 올린다.
**곁다리 유틸리티다.** 제품 CLI 는 `ziti/main.go` 이고 2위에 있었다.

| 조건 | M2 답 | 왜 |
|---|---|---|
| 텍스트 | `ziti/main.go` ✅ | 목록에서 `rank:2` 를 보고 **스스로 뒤집었다** |
| 사다리 | `ziti/main.go` ✅ | 진입점 8개를 나열해줘서 고를 수 있었다 |
| 그래프 | `ziti/main.go` ✅ | 같은 목록을 봤다 |
| 감시 | 두 답이 충돌 ⚠️ | 안내 ②는 db-explorer, 경로 찾기는 `ziti/main.go` |
| **펼치기** | `db-explorer/…` ❌ | ★로 **하나에 못 박아서** 그대로 따라갔다 |

**목록을 보여주는 형식은 도구의 오답을 사람이 고칠 수 있고,
하나로 확정하는 형식은 오답을 그대로 전파한다.**

그리고 그 오답이 화면 전체를 망가뜨렸다. 펼치기가 이렇게 말했다 —

> "main.go 에서 import 로 닿는 것은 8개가 전부입니다 — 코드 1,631개 중 **0%**."
> "**12단계 안에서는 어느 방향으로도 이어지지 않습니다.**"

신입은 이것을 "이 저장소는 끊겨 있다" 로 읽는다. 사실은 **우리가 잘못된 문에서
출발시킨 것**이다. 진짜 진입점을 넣으면 3단계로 중심까지 이어진다:
`ziti/main.go → ziti/cmd/cli.go → ziti/util/identities.go → controller/env/appenv.go`.

호출 수가 펼치기만 46회로 튄 것(나머지 28~34)도 여기서 온다.
막다른 길을 확인하고 되돌아 나오는 데 다 썼다.

### 🔴 결론 ③ — 감시 화면의 색 링은 **한 번도 안 그려졌다**

이 판에서 가장 아픈 것. 활동 지도는 3회차 후보 중 하나였고,
사람이 여러 번 요청한 "어느 노드가 작업 중인지 보여달라" 가 이것이다.

> 범례(「색 = 누가 잡았나」, 「바깥 흰 링 = 지금 고른 것」)는 완벽히 이해했지만
> **그 문법이 적용된 노드를 하나도 못 봤다.**
> 잡힌 파일을 지도에 올리려 여섯 가지를 시도했으나 지도는 끝까지 db-explorer 6개만 그렸다.

원인은 결론 ②와 같다. 지도가 **진입점에서 import 로 닿는 것만** 그리는데,
그 진입점이 틀려서 곁다리 6개에 갇혔다. claim 된 36개 파일은 영영 안 올라온다.

2회차에서 똑같은 증상을 한 번 고쳤다(밀집 완화가 claim 된 파일을 떨어뜨리던 것).
**증상이 같고 원인이 다르다.** 그때는 필터가 떨어뜨렸고, 이번엔 도달성이 막았다.

M6·M7 을 감시 조건이 제일 잘 답한 것은 사실이다 — 셋 전부와의 충돌을 찾았고
`.gitignore` 가 claim 없이 고쳐지는 것까지 봤다. **그런데 그것도 전부 글이었다.**

### 다섯 조건이 독립적으로 겹쳐 짚은 결함

| | 결함 | 짚은 조건 |
|---|---|---|
| **D-1** | 진입점 1위가 곁다리 유틸리티다 | 텍스트 · 펼치기 · 감시 |
| **D-2** | M4(등록 지점)를 **아무도 못 했다** | 5 / 5 |
| **D-3** | 경로 찾기가 **자기 화면 본문과 다른 답**을 준다 | 사다리 · 감시 |
| **D-4** | 「선언 밖 수정 1」의 **파일명이 어디에도 없다** | 그래프 · 텍스트 |
| **D-5** | 위험 목록 파일명이 잘리고 펼 수단이 없다 (`title` 없음) | 사다리 · 펼치기 |
| **D-6** | churn 상위를 `go.mod`·`CHANGELOG.md` 가 먹는다 (`deg:0` 비-코드) | 텍스트 |
| **D-7** | `/api/overlay` 의 `edges` 에 **스키마 두 종류가 섞여 있다** | 텍스트 |

D-7 이 제일 위험하다. import 엣지는 `kind` 를, co-change 엣지는 `origin`/`lift` 를
쓴다. 기준선이 "co-change 없음" 이라 오판했다가 **우연히** 되찾았다.
못 찾았으면 M7 의 숨은 충돌 둘이 통째로 없는 답이 됐을 것이다.

### 판 설계에서 잡힌 것

판을 열다 **이 판을 무효로 만들 뻔한 버그**를 잡았다. `#pathbar` 와
`#ladder`·`#reveal` 이 같은 픽셀에 그려져 첫 안내 문단이 읽을 수 없었다.
그래프 뷰만 멀쩡했다 — 즉 **비교 대상 넷 중 둘만 깨진 채로** 잴 뻔했다.
에이전트 둘을 이미 띄운 뒤였고, 멈추고 고치고 다시 시작했다.
(1회차도 비슷한 준비 결함으로 한 번 날렸다.)

⚠️ **이 판의 한계** — 브라우저 환경이 조건마다 고르지 않았다.
펼치기 조건은 호출 18~23 에서 배율이 175% 로 고정돼 사실상 **그림 없는 조건**이
됐고, 감시 조건은 호출 6부터 스크린샷이 뷰포트보다 좁았다. 46회라는 숫자에는
그 손실이 섞여 있다. **다만 7/7 은 다섯 조건이 전부 같으므로 이 잡음에 흔들리지 않는다.**

### 4회차에서 할 것

세 회차가 같은 답을 냈으므로 "그림이 값을 하는가" 는 더 안 묻는다.
다음은 **글을 더 잘 쓰는 쪽**이다.

1. **D-1 을 먼저 고친다.** 진입점 순위가 틀리면 그 뒤 화면이 전부 틀린다.
   곁다리 바이너리(`db-explorer`·`eventdoc`·`*-test`)를 뒤로 미루는 근거가 필요하다.
2. **확정 대신 목록.** 펼치기가 ★ 하나로 시작하는 것을 바꾼다 —
   결론 ②가 그 값을 직접 쟀다.
3. **D-2 를 정면으로.** 네 조건이 전부 M4 에서 멈췄다. 도구가 정직하게
   "못 한다" 고 말한 것은 맞지만, 세 판 연속 같은 자리에서 멈췄다.
