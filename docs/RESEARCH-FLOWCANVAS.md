## 0. 한 줄 결론 — 먼저 읽는다

> **Zapier 를 베껴야 할 곳은 그림이 아니라 그림 옆의 글이다.
> 그리고 배치를 "계산"하지 않고 "저장"한다는 결정이다.**

우리 벤치 3회차는 다섯 조건 전부에서 **7/7** 이 나왔다 —
"그림 없이 글자만 있었어도 답은 같았다". 이 조사는 그 결과를 뒤집지 못했다.
Zapier 를 실제로 열어봤더니 **Zapier 자신도 같은 구조**였다:
Canvas 의 Copilot 프레임(`Canvas_iterate` so_8)에서 화면 왼쪽 30% 는
`"Analyze Lead Quality - Score leads 1-10 based on contact completeness…"` 같은
**산문 설명**이 차지하고, 오른쪽 70% 의 그림은 카드 세 장과 화살표 하나였다.
**설명은 글이 하고, 그림은 확인만 한다.** 우리 벤치가 관측한 것과 정확히 같은 분업이다.

그러므로 이 문서의 권고는 "Zapier 처럼 예쁜 캔버스를 만들자"가 **아니다**.
아래 3장의 첫 증분은 **새 시각화를 만들지 않는다.** 이미 이긴 텍스트(`ladder`)를
Zapier 의 *조판 규율*로 다시 그리는 것이다.

## 1. Zapier 의 시각 언어 — 실제로 본 것

### 🔴 먼저: Zapier 에는 시각 언어가 **두 개** 있다. 섞어 보면 안 된다

이 구분을 안 하고 "Zapier 처럼"이라고 말하면 논의가 매번 어긋난다.

| | **Zap 편집기** (홈페이지 `AI Workflows`) | **Canvas** (zapier.com/canvas) |
|---|---|---|
| 배치 | **자동 · 강제.** 세로 한 줄, 사용자가 위치를 못 정한다 | **수동.** 사용자가 카드를 아무 데나 놓는다 |
| 노드 | 균일 폭 한 줄짜리 카드 | 가변 높이 카드 + 미니 썸네일 |
| 연결선 | 세로 직선 하나. **화살촉 없음** | 직교 꺾은선 + 얇은 열린 화살촉 |
| 무엇인가 | 실행되는 진짜 워크플로 | 그리는 **다이어그램** (초안·문서) |
| 우리에게 맞는 쪽 | **이쪽이다** | 이쪽이 아니다 (아래 2장) |

우리가 그려야 하는 것은 사용자가 배치할 수 없는 **주어진 사실**(import 그래프)이다.
그러므로 참고 대상은 **Zap 편집기**이고, Canvas 에서는 딱 두 가지만 훔친다
(그룹 프레임, 그리고 "배치를 저장한다"는 결정).

### 1.1 Zap 편집기 — 정밀 기술

출처: `res.cloudinary.com/.../v1745864783/aiworkflowshomepage.mp4` 의
프레임 so_11(전체 화면)과 so_5(확대). 화면 안 배율 표시는 **70%**.

**색 — 픽셀 샘플링으로 얻은 실제 값**

| 요소 | 값 | 우리 `shell.css` 대응 |
|---|---|---|
| 캔버스 바탕 | `#f9f8f4` | `--side: #f5f3ef` — **거의 같은 색이다** |
| 카드 채움 | `#fffefa` (따뜻한 흰색, 순백 아님) | `--bg: #ffffff` 보다 살짝 따뜻 |
| 상단 크롬 | `#403635` (따뜻한 짙은 회갈색) | `--ink: #26241f` 계열 |
| **연결선** | **`#7166a2`** (채도 낮은 인디고) | 없음 — 새로 정해야 함 |
| 카드 테두리 | `#ecebe7` 근처의 1px | `--line: #e8e5df` — **거의 같다** |

🔴 **연결선 색이 결정적인 관찰이다.** `#7166a2` 는 브랜드 보라(`#6B5CE0` 류)가
**아니다.** 채도를 죽인 인디고이고, `#f9f8f4` 바탕 대비가 4.4:1 정도밖에 안 된다.
**연결선은 일부러 조용하다.** 주인공은 카드의 글자이고 선은 배경 구조물이다.
우리가 지금 `graph.js` 에서 쓰는 `hsla(h, 62%, 62%)` 채도 62% 는 이 규율의 반대편이다.

**노드 카드 — 두 줄, 그게 전부**

```
┌──────────────────────────────────────┐
│ (✓)  [🔗 Webhooks by Zapier]     ⋮   │  ← 줄 1: 상태 · 출처 칩 · 메뉴
│ 1. Catch Hook                    ⌄   │  ← 줄 2: 번호 + 제목 (+ 펼침)
└──────────────────────────────────────┘
```

- 줄 1: **초록 체크 원**(검증 통과) + **앱 칩**(옅은 살구색 채움, 1px 주황 테두리,
  radius ≈ 5px, 안에 진짜 브랜드 로고 + 앱 이름) + 우측 `⋮` 케밥
- 줄 2: **`숫자.` + 제목**. `1. Catch Hook` · `2. Find Person` · `3. Split into paths`
- **번호가 붙어 있다는 것이 핵심이다.** 그림을 안 봐도 `3 → 7 → 8` 이라고
  말할 수 있다. 그림이 곧 **읽을 수 있는 목차**가 된다.
- 카드는 전부 **같은 폭**. 높이도 접힌 상태에서는 전부 같다.

**간격 — 비율로 적는다** (절대 픽셀은 영상 캡처 배율을 모르므로 신뢰하지 않는다)

so_11 프레임에서 잰 값:

| 관계 | 측정 | 비율 |
|---|---|---|
| 카드 폭 : 카드 높이(접힘) | 212 : 50 | **4.2 : 1** |
| 카드 사이 세로 여백 : 카드 높이 | 62 : 50 | **1.24 : 1** |
| 행 피치(카드 위 → 다음 카드 위) : 카드 높이 | 112 : 50 | **2.24 : 1** |
| 분기 열 피치 : 카드 폭 | 267 : 212 | **1.26 : 1** (홈통 26%) |

🔴 **세로 여백이 카드 높이보다 크다**(1.24배). 이것이 이 화면이 빽빽하지 않게
느껴지는 이유다. 우리 `shell.css` 의 방향("여백")과 같은 판단이다.

**연결선과 `+`**

- 부모 카드 아래 중앙 → 자식 카드 위 중앙, **세로 직선 한 줄**. 굵기 ≈ 2px.
- **화살촉이 없다.** 방향은 위에서 아래로 읽는다는 규약이 대신한다.
- **선의 정확한 중점에 `+` 가 있다.** 누르면 거기에 단계를 끼워 넣는다.
  이것이 이 화면이 *저작 도구*라는 사실이 드러나는 자리다 (5장에서 다시 다룬다).

**분기 — "쪼개진 화살표"가 아니라 "하나의 버스"**

```
        3. Split into paths
                │
                +
                │
   ┌────────────┼────────────┐        ← 가로 버스 한 줄, 직각, 모서리 안 둥글다
   │            │            │
(Lead nurture) (High prio.) (Mentions "help")   ← 알약형 조건 칩
   │            │            │
4. Path cond.  7. Path cond. 10. Path cond.
```

- 부모에서 **짧은 세로 스텁** → **가로 버스 한 줄** → 각 자식으로 **세로 낙하**.
- 모서리는 **직각이고 둥글지 않다** (Zap 편집기). Canvas 쪽은 둥글다 — 아래 1.2.
- 각 가지 머리에 **알약형 조건 칩**: 흰 채움, 1px 인디고 테두리, radius 999px,
  인디고 글자, 드롭다운 `⌄` 와 케밥. 라벨이 곧 **조건문**이다:
  `Lead nurture` · `High priority account` · `Mentions "help" or "support"` · `Path C`.

🔴 **분기가 "하나의 결정"으로 읽히는 이유는 버스를 공유하기 때문이다.**
자식마다 부모에서 각각 선을 뽑았다면 세 개의 독립된 관계로 보인다.
한 줄기에서 갈라지면 "여기서 한 번 갈린다"로 읽힌다. **이건 공짜로 옮겨올 수 있다.**

**규모 대응**

- Zap 편집기의 유일한 전략은 **"모든 단계를 한 줄로 접는다"** 이다.
  단계가 30개면 그냥 30줄이 되고 스크롤한다. 축소·군집·요약이 없다.
- 배율 표시(`70% ⌄`)가 있고 사용자가 줄일 수 있다.
- 🔴 **Zapier 는 100단계짜리 워크플로를 감당하도록 설계되지 않았다.**
  이것이 유추의 가장 약한 고리다 — 우리 ziti 실측은 **파일 2,019개 · 엣지 16,613개**다.

**모션**

- 케밥 메뉴가 **페이드 + 미세 스케일**로 뜨고, 그 뒤 캔버스에 **딤 스크림**이 깔린다
  (so_5 에서 뒤쪽 카드들이 흐려져 있다).
- 호버 시 카드 왼쪽에 **6점 드래그 그립**이 나타난다.
- **노드가 스스로 움직이는 애니메이션은 없다.** 물리도 없고 재배치 트랜지션도 없다.
  🔴 우리 온보딩 실험 4회차가 보고한 *"찍고 누르는 사이에 노드가 이동해 빗나갔다"*
  는 이 화면에서는 **구조적으로 발생할 수 없다.**

**빈 화면**

Zap 편집기의 빈 상태는 트리거 카드 한 장(`1. ...`)이 놓인 상태다 — 완전한 백지가 아니다.
Canvas 의 빈 상태(`Canvas_diagram` so_3)는 **정말 아무것도 없는 따뜻한 점격자**이고,
유일한 단서는 하단 중앙의 도구 팔레트다. 캔버스 위에 "여기서 시작하세요" 안내가 없다.
진입은 캔버스가 아니라 **목록 화면의 AI 프롬프트**가 맡는다:
`"Get a system recommendation [✳AI] / Describe what you're building…"` (`Canvas_hero` so_2).

### 1.2 Canvas — 다른 언어

출처: `canvas-cta_raj6kh.png` (2400×1358, 화면 안 배율 45%) 및
`Canvas_diagram` / `Canvas_visualize` / `Canvas_iterate` 프레임.

**색 — 히스토그램으로 뽑은 실제 값**

| 요소 | 값 |
|---|---|
| 캔버스 바탕 | `#f7f6f1` + 미세 **점격자** |
| 그룹 프레임 (초록) | `#dffacb` |
| 그룹 프레임 (하늘) | `#d3f8f8` |
| 그룹 프레임 (중립) | `#f9f7f3` |
| 카드 몸통 · Zap | `#fff8f1` |
| 카드 몸통 · Table | `#f0eef5` |
| 카드 몸통 · Agent | `#fefdf8` |
| **바닥띠 · Zap** | **`#ffc06e`** (주황) |
| **바닥띠 · Table** | **`#2b2258`** (남색) |
| **바닥띠 · Agent** | **`#3f3634`** (숯) |

**카드 해부 — 세 층**

```
        [✎ Draft]  ← 배지. 카드 위 테두리에 걸쳐 반쯤 밖으로 나온다
┌─────────────────────────┐
│ ┌─────────────────────┐ │  ← ① 미리보기: 그 물건의 축소 모형
│ │ [Show steps ↕]      │ │     (Table 이면 미니 표, Zap 이면 미니 단계들)
│ │   ▭▭▭▭▭             │ │     또는 제목 + 3줄로 잘린 설명
│ │      │              │ │
│ │   ▭ ⊕ ▭       [⤢]  │ │  ← 인디고 펼침 버튼, 미리보기 우하단
│ └─────────────────────┘ │
│ Store Employee Information │  ← ② 이름. 몸통 배경 위에 왼쪽 정렬
├─────────────────────────┤
│ ▪ Table  ↗              │  ← ③ 바닥띠: 종류색 + 종류 아이콘 + 종류 이름
└─────────────────────────┘
```

🔴 **종류를 색으로 말하는 자리가 "바닥띠"라는 것이 중요하다.**
카드 전체를 물들이지 않는다. 몸통은 그 색의 **아주 옅은 틴트**(`#fff8f1` 대 `#ffc06e`)로만
공명하고, 진한 색은 아래 한 줄에 가둔다. 그래서 카드가 20장 있어도 화면이 알록달록해지지 않는다.
D7 의 "색상은 끝까지" 와 열린 질문 Q1("파일 1000개에서 화면 1/3이 물들어 색이 정보를 잃는다")
사이의 실무적 타협안이 정확히 이것이다.

**선택 · 앵커**

선택된 카드는 **2px 인디고 테두리** + **가장자리 중점 4곳의 검은 원형 핸들**.
이 핸들이 곧 연결 앵커다(끌면 연결선이 나온다). 선택 시 카드 **위쪽에** 짙은 숯색
플로팅 툴바가 뜬다: `Explain` · 상태 원 · `Change app` · 링크 · 문서 · 사람 · `⋯`.

**배지 · 상태**

- `✎ Draft` — 흰 알약, 카드 우상단 테두리에 걸침
- `● Status: On` — 옅은 초록 알약 + 초록 점, 같은 자리
- `📅 +2 ⚙` — 카드 좌상단 **안쪽**의 작은 아이콘 칩 줄.
  🔴 **"아이콘 2~3개 보여주고 나머지는 `+N`"** 이 Zapier 의 다중 부착물 축약 패턴이다.

**연결선**

- **직교 꺾은선**, 모서리는 **작게 둥글다**(Zap 편집기와 다른 점).
- 끝에 **작고 열린 V 자 화살촉**(채워진 삼각형 아님).
- 두 노드가 같은 높이면 **꺾이지 않고 그냥 수평 직선**이 된다 (`Canvas_iterate` so_8).
  → 라우터는 "직교이되 정렬되면 직선으로 퇴화"한다.
- 분기는 Zap 편집기와 같은 **버스 공유** 방식이다 (`canvas-cta` 확대에서 확인).

**그룹 프레임**

- 평평한 파스텔 채움, radius ≈ 4px, **테두리 거의 없음**, 넉넉한 안쪽 여백.
- 라벨 칩이 프레임 **왼쪽 위 모서리 바깥에** 붙는다: 흰 알약, 1px 옅은 테두리,
  프레임 글리프 + 이름 11px semibold — `Onboarding Flow` · `Document Delivery` ·
  `Feedback System` · `Zap`.
- 프레임 **안쪽**에는 큰 제목(`New Hire Workflow`, `Feedback`)을 따로 둘 수 있다.

**규모 대응 — Canvas 쪽의 세 장치**

| 장치 | 하는 일 |
|---|---|
| `Show steps` 토글 | Zap 하나를 **썸네일 한 장으로 접는다** (내부 단계를 숨긴다) |
| 그룹 프레임 | 공간적으로 묶고 이름을 붙인다 |
| `+N` 아이콘 칩 | 부착물 목록을 3개 + 나머지로 자른다 |
| `Auto layout` 버튼 | 🔴 아래 참조 |

**🔴 `Auto layout` — 이 조사에서 가장 값진 한 줄**

Zapier 공식 가이드(zapier.com/blog/zapier-canvas-guide)는 이렇게 적는다:

> `Auto layout` 버튼이 "연결선을 곧게 펴고 단계를 정렬"한다.

즉 **Canvas 의 배치는 계산된 것이 아니라 저장된 것이다.**
사용자가 놓은 자리가 그대로 유지되고, 재배치는 **사람이 명시적으로 누를 때 한 번만** 일어난다.

> **Zapier 의 배치가 안정적인 이유는 좋은 알고리즘 때문이 아니라
> 알고리즘을 매번 돌리지 않기 때문이다.**

우리 제약("사용자가 같은 저장소를 매일 다시 연다 · 색과 위치가 튀면 안 된다")에
대한 답이 여기 통째로 들어 있다. 3장에서 그대로 채택한다.

## 2. 옮길 것과 옮기지 못할 것

### 2.1 그대로 옮긴다

| 요소 | 왜 우리 제약을 통과하나 |
|---|---|
| **강제 세로 척추 + 단계 번호** | `ladder.mjs` 가 이미 BFS 로 겹을 계산한다. 번호를 붙이면 그림이 **읽을 수 있는 목차**가 된다. 벤치 변형 ①(호출 사슬)이 M3 도달을 31→9~10 호출로 줄인 이유가 정확히 "그림이 아니라 **읽을 수 있는 순서**를 줬기 때문"이다 (`ladder.mjs` 머리주석) |
| **버스 공유 분기** | 한 파일이 5개를 여는 것이 "5개의 관계"가 아니라 "여기서 갈린다"로 읽힌다. 순수 기하이고 의존성 0 |
| **가지 머리의 조건 칩** | 우리 판에서는 조건이 아니라 **그룹 이름**이 들어간다. `corpus/terms.mjs` 의 `labelBlocks()` 가 이미 이름을 만든다 (D17) |
| **바닥띠로 종류를 말하기** | D13 의 `origin`(static / static-stable / both / cochange)을 카드 전체가 아니라 **한 줄**에만 칠한다. Q1(색 확장성)의 실무적 완화 |
| **`+N` 축약 칩** | D9 의 허브 배지(`estop 구독자`)와 같은 문제·같은 답 |
| **조용한 연결선** (`#7166a2`, 대비 4.4:1) | 선이 주인공이 아니라는 선언. `graph.js` 의 채도 62% 는 반대 방향 |
| **세로 여백 > 카드 높이** (1.24 : 1) | `shell.css` 의 "여백" 방향과 같다 |
| **`Auto layout` — 배치는 저장하고, 재계산은 사람이 누를 때만** | 🔴 "매일 다시 여는데 튀면 안 된다" 제약에 대한 **직접적인 답** |
| **물리 없음 · 자발 이동 없음** | 온보딩 실험 4회차의 "클릭 빗나감" 이 구조적으로 사라진다. D16 의 요구 시 렌더링(정지 시 0회/초)과도 같은 방향 |

### 2.2 옮기지 않는다 — 이유와 함께

| 요소 | 왜 안 되나 |
|---|---|
| **사용자 자유 배치 (Canvas 본체)** | Canvas 는 사람이 *그리는* 도구다. 우리 그래프는 **주어진 사실**이라 사람이 옮길 자리가 없다. 옮기게 하면 "위치가 무엇을 뜻하는지 모르겠다"(온보딩 실험 원문)가 그대로 재발한다 |
| **점격자 배경** | Zapier 는 자유 배치의 **스냅 격자**라서 필요하다. 우리는 격자에 스냅할 일이 없으므로 순수한 잉크 낭비다. `shell.css` 의 방향(여백)에 어긋난다 |
| **앱 브랜드 로고 아이콘** | Zapier 의 아이콘은 **9,000개 앱의 실제 로고**이고, 사용자가 이미 아는 상표다. 파일에는 대응물이 없다. 언어 아이콘(`.go`·`.ts`)으로 바꾸면 **정보량이 0에 가깝다** — 저장소 하나는 대개 한 언어다 |
| **가장자리 4개의 연결 앵커 핸들** | 저작 도구의 어포던스다. 읽기 전용 화면에서는 "끌면 뭔가 되나?" 하는 **거짓 어포던스**가 된다 |
| **연결선 중점의 `+`** | 같은 이유. 우리 화면에서 사용자가 만들 수 있는 엣지는 없다 |
| **`✓` 초록 체크 (검증 통과)** | Zapier 는 각 단계를 **실행해 본 결과**를 안다. 우리가 아는 것은 `origin` 뿐이고, 초록 체크로 그리면 **확신 있게 틀린 답**이 된다 — D5 가 가장 해롭다고 못박은 실패 방식이다 |
| **화살촉 없애기 (Zap 편집기 방식)** | Zapier 는 단계가 **선형 시간 순서**라서 위→아래가 곧 방향이다. import 그래프는 사이클이 있고, `ladder.mjs` 는 `directed === false` 인 엣지를 양방향으로 넣는다. **방향을 모르는 엣지가 있다는 사실 자체가 정보**이므로 지우면 안 된다 |
| **Canvas 의 자유 형태 텍스트/이미지 요소** | 우리 산출물은 재현 가능해야 한다 (`axmap audit`). 사람이 캔버스에 낙서를 남기면 그 캔버스는 더 이상 저장소의 함수가 아니다 |
| **`Explain` 을 노드 툴바에 넣기** | D4·D7 이 정한 예산(요약은 3단계까지, 상세는 클릭할 때)을 UI 가 우회하게 만든다. 툴바에 있으면 사용자가 30번 누른다 |

### 2.3 🔴 유추가 약한 지점 — 정직하게 적는다

**Zapier 사용자는 자기가 방금 만든 20단계짜리 워크플로를 본다.
우리 사용자는 남이 만든 2,019개짜리 저장소를 처음 본다.**

이 차이가 만드는 것:

| | Zapier | 우리 |
|---|---|---|
| 노드 수 | 3~30 | ziti 실측 **2,019** (엣지 16,613) |
| 노드의 의미 | 사용자가 직접 고른 것 | 사용자가 처음 보는 것 |
| 위치의 의미 | 사용자가 정한 것 | 도구가 정한 것 |
| 그림의 역할 | 내가 지은 것의 **확인** | 모르는 것의 **발견** |

Deutsch limit — *"화면에 시각 요소를 50개 넘게 둘 수 없다"* — 은 Zapier 에게는
제약이 아니다. 워크플로가 원래 30단계 미만이니까. **우리에게는 40배 초과다.**

이 조사에서 얻은 대응은 하나뿐이다: **화면에 카드를 60장 넘게 그리지 않는다.**
그 이상은 그룹 카드로 접는다(Canvas 의 `Show steps` 와 같은 장치).
"전부 보여주고 사용자가 줄이게 한다"는 D14 가 이미 버린 대안이다.

## 3. 구현 계획

### 3.1 렌더러 — **DOM + SVG**. Canvas 2D 도 WebGL 도 아니다

현 상태: `app/web/graph.js:145` 가 `canvas.getContext('2d')` 다. 2D 캔버스다
(`ladder.mjs` 주석의 "3D 힘 그래프"는 그 이전 세대를 가리킨다).

**권고: 카드는 DOM(`<div>`), 연결선만 SVG 오버레이 한 장.**

```
#stage (position: relative)
├─ <svg class="wires">      ← position:absolute; inset:0; pointer-events:none
│    <defs><marker id="tip">…</marker></defs>
│    <path class="w tree"  d="…"/>   ← BFS 트리 간선
│    <path class="w cross" d="…"/>   ← 트리 밖 간선 (옅게)
└─ <div class="card" style="--r:2; --slot:5">…</div>   ← 카드들. 문서 순서 = 읽기 순서
```

**왜 DOM 인가 — 벤치가 낸 근거로만 고른다**

| 근거 | 출처 |
|---|---|
| **답의 내용물이 글자다.** 캔버스에는 선택 가능한 텍스트도, 줄바꿈도, 말줄임도, Ctrl+F 도 없다 | 벤치 3회차 전 조건 7/7 |
| **잘린 라벨 문제.** ladder 조건은 `zoom`(호출 29)을 썼다가 *"잘린 글자는 픽셀을 키운다고 되살아나지 않는다"* 고 적었고, **`title` 속성 하나면 막힌 지점이 없었을 것**이라고 스스로 진단했다. DOM 에서는 공짜다 | `answers-ladder.md` |
| **클릭 빗나감.** DOM 요소는 히트 영역이 정확하다. 손으로 히트테스트를 짜지 않는다 | BENCH.md 측정 항목 |
| **요구 시 렌더링이 저절로 된다.** DOM 은 안 바뀐 것을 다시 그리지 않는다. D16 의 자체 점검(정지 후 25회/초 초과 시 실패)이 **rAF 를 아예 안 걸고** 통과한다 | D16 |
| **평가 하네스가 `read_page` 로 읽는다.** 벤치 에이전트는 접근성 트리를 읽는다. 캔버스는 이 도구에 **완전히 불투명**하다 | bench-runs 전체 |

**왜 WebGL 이 아닌가.** `ladder.mjs` 가 이미 죽인 것이다. 그리고 글자를 더 나쁘게 만든다.
**왜 순수 SVG 가 아닌가.** `<foreignObject>` 없이 SVG 안에서 텍스트 줄바꿈·말줄임을 하려면
직접 조판해야 한다. 카드를 DOM 으로 두면 CSS 가 공짜로 해준다.
**왜 선만 SVG 인가.** 경로는 SVG 가 잘하는 유일한 것이다. CSS 로 직교 꺾은선을 그리면
`div` 를 3개씩 쌓게 된다.

**성능.** 카드 60장 · path 80개 = DOM 노드 200개 미만. 브라우저에게 아무것도 아니다.
"60장을 넘지 않는다"는 위 2.3 의 결론이므로 성능 논의는 여기서 닫힌다.

**의존성.** **0개.** 라이브러리를 쓰지 않는다 (3.5 참조).

### 3.2 배치 알고리즘 — 계층형(Sugiyama-lite). 새 알고리즘을 만들지 않는다

🔴 **`app/lib/ladder.mjs` 가 이미 필요한 것을 전부 계산한다.**

```js
const depth  = new Map()   // 노드 → 진입점에서 몇 겹 (= rank)
const parent = new Map()   // 노드 → BFS 트리 부모  ← 이것이 열쇠다
const opensOf = (id) => …  // 이 가지가 여는 파일 수 (= 정렬 근거)
```

`parent` 맵이 있으면 **임의의 그래프에서 트리 하나가 뽑힌다.**
그 트리를 Zapier 의 척추로 그리고, 트리에 없는 엣지는 옅은 곡선으로 따로 그린다.
**이것이 트리가 아닌 그래프에서 Zapier 처럼 생긴 그림을 얻는 유일한 정직한 방법이다.**

| 단계 | 방법 | 이미 있나 |
|---|---|---|
| ① 겹(rank) 정하기 | `entry.mjs` 시드에서 BFS. `ladder.mjs` 의 `depth` | ✅ 있다 |
| ② 겹 안 순서 | **결정적 정렬**: `(그룹명, opens 내림차순, 경로 오름차순)` | 부분적 (`opens` 있음) |
| ③ 트리 간선 | `parent` 맵 | ✅ 있다 |
| ④ 나머지 간선 | 트리에 없는 엣지 = 교차 링크 | 파생 가능 |
| ⑤ 교차 줄이기 | **초기에는 하지 않는다** (아래) | — |

**⑤ 교차 줄이기를 초기에 하지 않는 이유.** 배리센터 반복은 결과가 입력 순서에 민감하고,
그것이 정확히 "작은 변화에 결과가 통째로 뒤집힌다"(D17 이 spectral 을 버린 세 번째 이유)다.
**교차가 몇 개 보이는 것보다 어제와 다른 그림이 뜨는 것이 나쁘다.**
필요해지면 나중에 넣되, 반드시 결정적 타이브레이커(경로 문자열)를 끝에 붙인다.

**군집(그룹) — D17 준수. 🔴 이미 만들어지는 중이다**

조사 중 작업 트리에서 확인했다 (2026-08-21 기준 아직 커밋 전, `??`):
`corpus/cluster.mjs` · `corpus/clusterscore.mjs` · `test/cluster.test.mjs` ·
`tools/cluster-sweep.mjs`. **D17 의 숙제를 누군가 이미 실행하고 있다.**

이 화면 작업은 **군집을 새로 만들지 않는다.** 아래를 그대로 소비한다.

| 이미 있는 것 | 무엇 |
|---|---|
| `cluster(name, g, opts)` | `louvain` · `leiden` · `labelPropagation` 공통 진입. 출력은 항상 `membership: Int32Array` |
| `buildGraph(ids, edges, …)` | `origin` 이 `static`·`cochange`·`both` 인 엣지로 가중 그래프를 만든다 (D12·D13) |
| `quality(…, {objective})` | `modularity` 와 `cpm` 둘. CPM 은 해상도 한계가 없고 γ 에 읽을 수 있는 뜻이 있다 |
| `rng(seed)` | mulberry32. **`Math.random()` 이 없다** — 씨앗이 인자다 |
| `agreement(runs)` → `{mean, min}` | 씨앗을 바꿔 여러 번 나눈 결과의 **ARI 평균과 최솟값**. 주석이 명시한다: *"이 숫자가 낮으면 씨앗 하나 바꿨을 뿐인데 화면 색이 전부 바뀐다는 뜻"* |
| `LIMITS` | `minStability: 0.6` · `maxBlocks: 40` · `maxDirAgreement: 0.9` |
| `rank(candidates)` | 가중합을 만들지 않는다. **제약을 먼저 통과시키고 통과한 것 중에서 고른다.** 아무도 통과 못 하면 후보를 지어내지 않는다 |

🔴 **`LIMITS.maxBlocks = 40` 과 `LIMITS.minStability = 0.6` 은 이 문서의 3.3·2.3 과
같은 문제를 이미 풀고 있다.** 화면 쪽에서 상한을 새로 정하지 말고 이 상수를 읽는다.
(주석도 열린 질문 Q1 을 명시적으로 가리킨다 — *"화면에 색으로 구별해 그릴 수 있는 상한"*.)

- spectral 은 후보에서 제외 (D17).
- 이름: `corpus/terms.mjs` 의 `labelBlocks()`. 입력이 "파일 → 블록 번호"뿐이라
  **군집 알고리즘을 나중에 Infomap/SBM 으로 바꿔도 그대로 붙는다** (D17).
- 🔴 **그리고 3.3 의 결론이 여기서 결정적이 된다** — 색을 **블록 번호**에 붙이면
  알고리즘이 블록을 재번호할 때마다 색이 뒤집힌다. `labelBlocks()` 가 낸
  **이름에 붙이면** 재번호를 견딘다. `agreement()` 가 재는 ARI 는 "같은 파일들이
  같이 묶였는가"이지 "번호가 같은가"가 아니므로, ARI 가 높아도 **번호는 얼마든지 바뀐다.**
  **이름 키잉이 없으면 ARI 0.9 짜리 안정적인 군집에서도 색이 튄다.**

### 3.3 🔴 커밋이 바뀌어도 흔들리지 않게 하는 법

**먼저 — 지금 코드에 흔들림의 원인이 두 군데 있다. 이건 조사 중에 발견한 것이다.**

> ⚠ 조사 시점(2026-08-21)에 `app/web/graph.js` 는 **삭제 스테이징 상태**였다
> (`git status` 가 `D app/web/graph.js`). 아래 두 버그는 파일이 사라지면 함께
> 사라진다. 그래도 적어두는 이유는 **후속 화면이 같은 실수를 그대로 반복하기
> 쉬운 종류**이기 때문이다 — 둘 다 "그럴듯해 보이는 한 줄"이고, 문법 검사도
> 단위 테스트도 통과하며, **화면을 두 번 열어보기 전에는 드러나지 않는다.**

**① 색이 뛴다 — `app/web/graph.js:197-198`**

```js

this.hueOf = new Map(groups.map((g, i) => [g, (i * 137.508) % 360]))
```

색상이 **그룹 이름의 함수가 아니라 배열 인덱스의 함수**다.
그리고 그 인덱스는 `nodes` 배열의 등장 순서에서 나온다.
**앞쪽에 새 디렉터리 파일이 하나 생기면 그 뒤 모든 그룹의 색이 137.5°씩 밀린다.**

D17 은 이 위험을 spectral 의 죄로 적었다:

> 어제 파랗던 덩어리가 오늘 빨개지면 그동안 쌓은 머릿속 지도가 무효가 된다.

**그런데 spectral 을 안 써도 우리 코드가 이미 그 일을 하고 있다.**

고치는 법 — 이름을 해싱한다. 의존성 0, 12줄:

```js
// 🔴 색은 반드시 **이름**의 함수여야 한다. 인덱스의 함수면 목록이 한 칸 밀릴 때
//    모든 색이 밀린다. 사용자는 같은 저장소를 매일 다시 열고, 색이 곧 색인이다.
function hueOfName(name) {
  let h = 2166136261 >>> 0            // FNV-1a
  for (let i = 0; i < name.length; i++) {
    h ^= name.charCodeAt(i)
    h = Math.imul(h, 16777619) >>> 0
  }
  return (h % 12) * 30               // 12칸으로 양자화 — 근접 충돌을 무의미하게 만든다
}
```

12칸으로 **양자화**하는 것이 핵심이다. 연속 hue 를 쓰면 이름이 한 글자 달라져도
색이 미묘하게 달라져 "같은 색인가?"를 사람이 판단해야 한다. 12칸이면 같거나 다르다.

**② 위치가 뛴다 — `app/web/graph.js:203-211`**

```js
const u = Math.random() * 2 - 1
...
x: old?.x ?? rr * s * Math.cos(th),
```

새 노드는 **무작위** 좌표에서 시작하고, 힘 배치라 그 한 점이 이웃 전체를 흔든다.
파일 하나 추가에 화면 절반이 재배치된다.

계층 배치로 가면 이 문제는 **없어진다** — 좌표가 `(rank, slot)` 의 순수 함수가 되고
난수가 들어갈 자리가 없다.

**그리고 Zapier 에게서 배운 진짜 답 — 배치를 저장한다**

```
.axmap/layout.json
{
  "version": 1,
  "byPath": {
    "controller/raft/raft.go": { "rank": 2, "slot": 5 },
    "router/xgress_edge/hosted.go": { "rank": 3, "slot": 1 }
  }
}
```

규칙 세 줄:

1. 여는 순간, 저장된 `rank` 가 **지금 계산한 `rank` 와 같으면 저장된 `slot` 을 쓴다.**
2. 다르면(진짜로 도달 구조가 바뀌었으면) 그 노드만 다시 자리를 잡는다.
3. 전체 재계산은 **사람이 `자동 정렬` 을 누를 때만.** ← Zapier `Auto layout`

이러면 "어제와 같은 그림"이 알고리즘의 안정성이 아니라 **파일 하나로** 보장된다.
그리고 그 파일은 `git diff` 로 볼 수 있다 — **배치가 왜 바뀌었는지 증명 가능해진다.**
D4 가 원하는 "검토 가능한 artifact" 의 성질을 배치까지 확장하는 셈이다.

### 3.4 연결선 — 라이브러리 없이

**직교(orthogonal) 를 쓴다. 베지에는 트리 밖 간선에만.**

이유: 계층 배치에서 부모와 자식은 **다른 겹**에 있고 x 가 다르다.
베지에로 그리면 여러 자식으로 가는 곡선이 부모 근처에서 겹쳐 어느 것이 어느 것인지
구분되지 않는다. Zapier 가 두 화면 모두에서 직교 버스를 쓰는 이유가 그것이다.

**버스 분기 경로 만들기 — 전부 합쳐 30줄, 의존성 0**

```js
/**
 * 부모 하나 → 자식 여럿을 **버스 하나**로 잇는다.
 *
 * 🔴 자식마다 따로 선을 뽑지 않는 이유: 그러면 N 개의 독립된 관계로 읽힌다.
 *    줄기를 공유해야 "여기서 한 번 갈린다"로 읽힌다. Zapier 가 Zap 편집기와
 *    Canvas 양쪽에서 같은 선택을 했고, 그 이유가 이것이다.
 *
 * 순수 함수다 — DOM 도 시계도 없다 (CLAUDE.md).
 */
export function busPath(parent, kids, r = 6) {
  const py = parent.y + parent.h           // 부모 아래
  const ky = Math.min(...kids.map(k => k.y))
  const bus = (py + ky) / 2                // 버스 높이 = 중간
  const px = parent.x + parent.w / 2
  const xs = kids.map(k => k.x + k.w / 2)
  const lo = Math.min(px, ...xs)
  const hi = Math.max(px, ...xs)

  // 부모 스텁 + 버스
  let d = `M${px},${py} L${px},${bus} M${lo},${bus} L${hi},${bus}`

  // 자식마다 낙하. 모서리는 이차 베지에 한 번으로 둥글린다 —
  // A(호)를 쓰면 방향에 따라 sweep-flag 를 뒤집어야 해서 틀리기 쉽다.
  for (const kx of xs) {
    const s = Math.sign(kx - lo) || 1
    d += ` M${kx - s * r},${bus} Q${kx},${bus} ${kx},${bus + r} L${kx},${ky}`
  }
  return d
}
```

자식이 하나뿐이면 `lo === hi === px === xs[0]` 이 되어 **저절로 세로 직선**이 된다
(Canvas 에서 관측한 "정렬되면 직선으로 퇴화"와 같은 동작). 특수 케이스를 안 짜도 된다.

**트리 밖 간선(교차 링크)** — 3차 베지에, 옅게, 아래 레이어에.

```js
export function crossPath(a, b) {
  const ax = a.x + a.w / 2, ay = a.y + a.h
  const bx = b.x + b.w / 2, by = b.y
  const k = Math.max(40, Math.abs(by - ay) * 0.4)
  return `M${ax},${ay} C${ax},${ay + k} ${bx},${by - k} ${bx},${by}`
}
```

**화살촉** — `<defs>` 에 `<marker>` 하나, 재사용.
🔴 **척추에는 붙이지 않는다**(위→아래가 곧 방향, Zap 편집기와 같음).
**교차 링크에만 붙인다** — 거기서는 방향이 자명하지 않고,
`ladder.mjs` 가 `directed === false` 로 표시한 엣지는 **양끝에 붙여** "방향을 모른다"를
명시한다. D5 의 "도구는 자기 확신 수준을 절대 속이지 않아야 한다"의 시각적 이행이다.

**색 — `shell.css` 토큰만으로**

```css
.wires .tree  { stroke: #8a8378; stroke-width: 1.5; fill: none; }   /* --ink3 보다 조금 진하게 */
.wires .cross { stroke: var(--ink3); stroke-width: 1; opacity: .35; fill: none; }
.wires .cross[data-o="cochange"] { stroke: var(--accent); opacity: .5; }  /* D12 숨은 결합 */
```

Zapier 의 `#7166a2` 를 그대로 쓰지 않는다 — 우리 팔레트는 따뜻한 중성색이고
인디고는 이질적이다. **훔치는 것은 색이 아니라 "대비 4.4:1 로 조용히"라는 규율**이다.

## 4. 공수와 첫 증분

### 4.1 🔴 가장 값진 첫 증분 — 새 그림을 만들지 않는다

> **`ladder` 가 이미 내는 텍스트를, Zap 편집기의 조판 규율로 다시 그린다.**
> 알고리즘 없음 · 군집 없음 · 물리 없음 · 저장 없음 · 라이브러리 없음.

구체적으로:

1. `ladder(nodes, edges, starts)` 결과를 그대로 받는다. **`ladder.mjs` 를 고치지 않는다.**
2. 각 노드를 **두 줄짜리 균일 폭 카드**로 그린다:
   - 줄 1: `origin` 배지(바닥띠 대신 좌측 4px 세로 막대) + 그룹 이름 칩 + `여는 파일 N개`
   - 줄 2: **`겹.순번` + 파일명** — `2.5 controller/raft/raft.go`
3. `parent` 를 따라 **버스 분기**로 잇는다 (3.4 의 `busPath`).
4. 겹마다 카드를 `slot` 순으로 가로 배치. 겹 안 60장 초과 시 **그룹 카드로 접는다.**
5. `title` 속성을 모든 카드에 붙인다 (ladder 조건이 명시적으로 요청한 것).
6. 어떤 것도 움직이지 않는다. `requestAnimationFrame` 을 걸지 않는다.

**왜 이것이 첫 번째인가 — 벤치가 시킨 것이다.**

`answers-graph.md` 의 가장 아픈 문장:

> 걸음 ②에서 `노드 2 / 엣지 0`, 걸음 ③에서 `노드 8 / 엣지 3` — 화면의 3분의 2가
> 검은 여백인 채로, 정작 그 걸음의 답(시작점 8개, 겹 474개)은 전부 왼쪽 좁은 패널에
> 글자로 쏟아졌다. **답이 가장 많이 나오는 걸음에서 그림이 가장 비어 있다**

🔴 **이건 렌더링 문제가 아니라 데이터 공급 문제다.**
Zapier 식 캔버스를 만들어도 그 캔버스에 노드 2개만 흘려보내면 똑같이 빈다.
첫 증분은 **왼쪽 패널이 글자로 쏟아내던 것을 가운데 큰 자리로 옮기는 일**이고,
그것이 이 조사가 찾은 유일한 "그림이 일을 하게 만드는" 경로다.

그리고 스스로 이렇게 적었다:

> **(D)** "엣지가 두 종류 섞여 있다"는 사실은 그림에서는 **선 색이 두 가지인 것으로
> 한눈에 보였을** 성질이고, 텍스트에서는 스키마를 직접 파봐야만 드러났다.
> **(F)** `go.mod` 가 목록 1위인 것은 텍스트에서는 그냥 1위지만, 그림에서는
> **"선이 하나도 안 붙은 큰 점"** 으로 보여 즉시 걸러졌을 것이다.

**정답률(7/7)은 그림을 기각하지만, 오류율과 검증 비용은 기각하지 않는다.**
두 항목 다 **"이 데이터에 무엇이 있는지"** 를 아는 문제이지 "이 파일이 무엇인지"가 아니다.
D5 가 "확신 있게 틀린 답이 가장 해롭다"고 한 그 실패가 텍스트 조건에서 **2번** 났다.

> 정직한 종합: **그림은 M1~M7 의 답을 만들지 못한다.
> 그림이 값을 하는 자리가 있다면 "무엇을 못 보고 있는지"를 알려주는 것이다.**
> 그리고 그건 노드-링크 그림의 고전적 강점(누락·고립·이상치)과 정확히 겹친다.

### 5.3 외부 문헌 — 유추의 방향을 뒤집는 두 편

**Ghoniem · Fekete · Castagliola (2005), *Information Visualization*** —
노드-링크 대 인접행렬 통제 실험. 그래프 크기 20 / 50 / 100 노드, 밀도 0.2 / 0.4 / 0.6.

> 정점이 20개를 넘으면 대부분의 과제에서 **행렬이 노드-링크를 이긴다.**
> 노드-링크가 일관되게 앞선 유일한 과제는 **경로 찾기(path finding)** 이고,
> **그 우위조차 100노드에서 사라진다.**

🔴 이건 우리에게 두 가지를 동시에 말한다.

- **좋은 소식:** 우리의 M3(*"진입점에서 핵심 기능까지 어떻게 이어지나 — 경로를 순서대로"*)는
  **정확히 path finding 이다.** 노드-링크가 이기는 그 하나의 과제다.
  BENCH.md 가 M3 를 "경로 표현이 직접 겨냥하는 지표"로 고른 것은 문헌과 맞아떨어진다.
- **나쁜 소식:** **100노드에서 그 우위가 사라진다.** ziti 는 2,019개다.
  → 60장 상한(2.3)과 그룹 접기가 선택이 아니라 **이 우위를 살리는 조건**이다.

**Petre (1995), *Why looking isn't always seeing*, CACM 38(6)** —

> 그래픽 표현의 효율은 과제에 좌우될 뿐 아니라, **배치와 factoring 정도 같은
> 부차적으로 보이는 요소(secondary notation)에 극도로 민감**하다.
> 그래픽 표기의 독해력은 **학습되어야** 한다.

두 문장이 각각 우리 관측과 겹친다.

- "배치에 극도로 민감" → 온보딩 실험의 *"위치가 무엇을 뜻하는지 모르겠다. 가까우면 뭔데?"*
  힘 배치는 위치에 **뜻이 없어서** 진 것이다. `ladder.mjs` 의 처방(세로 = 겹)이 정확히 이것이다.
- "독해력은 학습된다" → **우리 사용자는 오늘 입사한 사람이다**(BENCH.md 프롬프트).
  학습할 시간이 없다. 그러므로 우리 그림은 **범례 없이 즉시 읽혀야 한다.**
  Zapier 의 `1.` `2.` `3.` 번호와 조건 칩이 바로 그 장치다.

**Deutsch limit** — *"시각 요소를 화면에 50개 넘게 둘 수 없다"* (L. Peter Deutsch,
Fred Lakin 명명). Zapier 워크플로는 대개 30단계 미만이라 이 한계에 닿지 않는다.
우리는 40배 초과한다.

**소프트웨어 시각화 평가 SLR** (Merino 등, *Journal of Systems and Software*, 2018) —

> 경험적으로 평가된 접근이 **극히 적고**, 이는 학계·산업계 양쪽에서 소프트웨어 시각화의
> 수용을 저해한다. "사례 연구"라는 이름의 상당수는 **효과에 대한 증거를 거의 담지 않은**
> 사용 시나리오였다.

즉 **"소프트웨어를 그리면 이해가 는다"는 주장에는 널리 인용될 만한 통제 실험 근거가 없다.**
우리 벤치(다섯 조건 · 고정 프롬프트 · 호출 번호 계측)는 이 분야 기준으로 오히려 엄격한 편이다.
**바깥에서 우리 결과를 뒤집을 증거를 찾지 못했다.**

**요구사항 이해 아이트래킹 실험** (Sharafi 등, ICPC 2013, 참가자 28명) —

> 그래픽 표현이 텍스트보다 반드시 효율적이지는 않다. 적어도 **그 그래픽 표현에
> 익숙하지 않은 개발자에게는.**

**설계 소통 실험족** (Jolak 등, *Empirical Software Engineering*, 2020, 학생 240명, 4개 대학) —
여기서만 그림이 이겼다. 그런데 이긴 항목이 무엇인지가 중요하다:

> 그래픽 설계 기술이 개발자 간 **활발한 토론(Active Discussion)** 을 촉진하고
> 설계 세부의 **회상(Recall)** 을 높였다. 그러나 설계 결정을 전달하는 데
> **명확히 우월한 표기는 없었다.**

🔴 **"토론"과 "회상"에서 이기고 "전달"에서는 안 이긴다.**
이것이 5.4 의 핵심이다.

### 5.4 그래서 — Zapier 유추는 얼마나 튼튼한가

**약하다. 다만 예상과 다른 방향으로 약하다.**

Zapier 사용자는 캔버스에서 워크플로를 **짓는다**. 저작 도구다.
그 증거가 화면에 그대로 박혀 있다 — 연결선 중점의 `+`, 가장자리 연결 앵커,
`Change app`, `Auto layout`, `Publish`, 실행 취소, 버전(`v1. published by Joe S.`).
**Zapier 화면에서 순수하게 읽기용인 요소는 거의 없다.**

우리 사용자는 남의 저장소를 **읽는다**. 그러므로 위 어포던스는 전부 못 옮긴다(2.2).

**그런데 이 조사에서 발견한 진짜 대응은 저작 대 독해가 아니라 이것이다.**

Zapier 의 Copilot 프레임(`Canvas_iterate` so_8)에서 화면은 이렇게 나뉜다:

```
┌──────────────────┬───────────────────────────────────┐
│  Copilot  [AI]   │                                   │
│                  │   [Lead Form] ──→ [Leads]  [Lead  │
│  ✅ Lead Analyzer│                            Analyz]│
│  Agent Created…  │                                   │
│                  │                                   │
│  🧠 Analyze Lead │        (카드 3장, 화살표 1개)      │
│  Quality — Score │                                   │
│  leads 1-10…     │                                   │
│  📊 Prioritize…  │                                   │
│  💡 Provide      │                                   │
│  Insights…       │                                   │
│  🎯 Recommend…   │                                   │
│                  │                                   │
│  [Continue]      │                                   │
│  ┌────────────┐  │                                   │
│  │Ask me any…│  │                                   │
└──────────────────┴───────────────────────────────────┘
   ← 설명은 여기 →      ← 그림은 확인만 한다 →
```

**Zapier 조차 설명을 그림에 넣지 않는다. 옆에 붙인 산문 패널에 넣는다.**
그리고 그 패널은 접히지 않는 상시 배치다.

우리 `reveal` 조건 보고서와 문장 하나까지 같다:

> 이 화면의 값어치는 "그림"이 아니라 **"한 번에 한 걸음씩, 문장으로 근거를 대주는 것"** 에 있었다.

> **그러므로 "Zapier 처럼 만들자"의 올바른 번역은
> "가운데에 캔버스를 놓자"가 아니라
> "글 패널을 1등 시민으로 두고, 그림은 그 글이 방금 말한 것을 확인해 주게 하자" 이다.**

`shell.css` 는 이미 그 배치다 — 오른쪽 520px 대화 칸이 상시 열려 있고,
`#center` 는 *"🔴 지금은 비어 있다. 그래프가 들어올 자리다"* 로 남아 있다.
**그 자리에 들어갈 것은 대화 패널과 경쟁하는 화려한 캔버스가 아니라,
대화가 방금 말한 파일들을 순서대로 보여주는 조용한 카드 사다리다.**

### 5.5 이 조사가 반증될 수 있는 지점

정직하게 적어둔다. 아래 중 하나라도 관측되면 이 문서의 권고는 틀린 것이다.

1. #1 증분을 넣고 벤치를 돌렸는데 **M3 도달 호출이 변형 ①(9~10)보다 나아지지 않는다.**
   → 카드 조판은 텍스트 목록보다 나은 것이 없다. 3장 전체를 버린다.
2. 60장 상한을 걸었더니 **답이 그 60장 바깥에 있는 일이 반복된다.**
   → 상한이 아니라 선별이 문제다. 화면이 아니라 `ladder.mjs` 의 정렬을 고쳐야 한다.
3. `layout.json` 을 넣었는데 **저장된 배치가 저장소 현실과 어긋나 오히려 거짓말을 한다.**
   → 안정성과 정확성이 충돌한다. **정확성이 이긴다** (D5, fail-closed).
